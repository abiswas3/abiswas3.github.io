The Monad Type Class

Notes on Chapter 4.2: The Monad Type Class from Functional Programming in Lean.

Working code: FunctionalProgramming/monad-typeclass.lean

In the previous post we wrote bind and unit four times — once for Option, once for Error, once for WithLog, once for State. The book called bind "andThen" and unit was some, Error.ok, okLog, or okState depending on the type. Each time it was the same pattern. The Monad type class eliminates this repetition.

The Type Class

class Monad (m : Type → Type) where
  pure : α → m α
  bind : m α → (α → m β) → m β

That's it.

  • pure is our unit/ok (Lifter)
  • bind is our andThen. (Composer)

The type class just says: "any type m that provides these two operations is a monad." Recall from the previous posts that m was Option, Except ε (which has two type parameters — the error type ε is fixed, so Except ε is a Type → Type), WithLog logged, State σ, List, etc. Note that m must be Type → Type — it takes a type parameter. That's why it's Except ε (not Except), State σ (not State), etc.

Instances

Now instead of writing separate andThenError, andThenLog, andThenState functions, we register each as a Monad instance:

Option:

instance : Monad Option where
  pure x := some x
  bind opt next := match opt with
    | none => none
    | some x => next x

Except:

instance : Monad (Except ε) where
  pure x := Except.ok x
  bind attempt next := match attempt with
    | Except.error e => Except.error e
    | Except.ok x => next x

WithLog:

instance : Monad (WithLog logged) where
  pure x := { log := [], val := x }
  bind result next :=
    let { log := thisOut, val := thisRes } := result
    let { log := nextOut, val := nextRes } := next thisRes
    { log := thisOut ++ nextOut, val := nextRes }

State:

instance : Monad (State σ) where
  pure x := fun s => (s, x)
  bind first next := fun s =>
    let (s', x) := first s
    next x s'

These are exactly the same definitions we wrote before — just registered as instances of a type class.

The Payoff: Polymorphic Code

The whole point: we can now write functions that work with any monad. Compare with the previous post where we had to write firstThird separately for Option and Error.

def firstThirdFifthSeventh [Monad m]
    (lookup : List α → Nat → m α)
    (xs : List α) : m (α × α × α × α) :=
  lookup xs 0 >>= fun first =>
  lookup xs 2 >>= fun third =>
  lookup xs 4 >>= fun fifth =>
  lookup xs 6 >>= fun seventh =>
  pure (first, third, fifth, seventh)

The [Monad m] constraint says: "this works for any m that is a monad." >>= is the infix notation for bind — so x >>= f is bind x f, same as our andThen x f or x ~~> f.

Now we define two different lookup functions — one for Option, one for Except:

def lookupOption (xs : List α) (i : Nat) : Option α :=
  xs[i]?

def lookupExcept (xs : List α) (i : Nat) : Except String α :=
  match xs[i]? with
  | none => Except.error s!"Index {i} not found (maximum is {xs.length - 1})"
  | some x => Except.ok x

Same function, different effects:

#eval firstThirdFifthSeventh lookupOption [1, 2, 3, 4, 5, 6, 7, 8]
-- some (1, 3, 5, 7)

#eval firstThirdFifthSeventh lookupOption [1, 2, 3]
-- none (silent failure — list too short)

#eval firstThirdFifthSeventh lookupExcept [1, 2, 3, 4, 5, 6, 7, 8]
-- Except.ok (1, 3, 5, 7)

#eval firstThirdFifthSeventh lookupExcept [1, 2, 3]
-- Except.error "Index 4 not found (maximum is 2)"

Pass in lookupOption and you get silent failure. Pass in lookupExcept and you get error messages. One function, two behaviours — determined entirely by which monad m is.

mapM: Mapping with Effects

A common pattern — apply a monadic function to every element of a list:

def mapM [Monad m] (f : α → m β) : List α → m (List β)
  | [] => pure []
  | x :: xs => f x >>= fun hd =>
      mapM f xs >>= fun tl =>
      pure (hd :: tl)

This is List.map but where the function can have side effects. Because it's polymorphic over m, it works with any monad:

  • With Option: stops at the first none
  • With Except: stops at the first error
  • With State: threads state through each application
  • With WithLog: accumulates logs from each application

The Identity Monad

What if you need no effects at all but have a function that requires a Monad?

def Id (t : Type) : Type := t

instance : Monad Id where
  pure x := x
  bind x f := f x

Id is the "do nothing" monad. pure is the identity function. bind is just function application. It's the monad equivalent of multiplying by 1.

The Monad Contract

Every Monad instance should satisfy three laws:

  1. Left identity: bind (pure v) f = f v — pure then bind is the same as just calling f
  2. Right identity: bind v pure = v — bind then pure does nothing
  3. Associativity: bind (bind v f) g = bind v (fun x => bind (f x) g) — chaining order doesn't matter

The first two are the identity laws from the Piponi post: unit * f' = f' and f' * unit = f'. The third (associativity) says chaining order doesn't matter — you can group compositions however you like. Same laws, different notation.

A broken example: instance : Monad Option where pure x := some x; bind _ _ := none. This satisfies the types but violates left identity — bind (pure v) f gives none instead of f v. The monad laws are not enforced by the compiler; they are a contract you must uphold.
