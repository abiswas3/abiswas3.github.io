Proving Imperative Programs In Lean

Ari 2026-03-26
lean-notesmonadsverification

Working code: FunctionalProgramming/VerifiedImperative.lean. Based on Markus Himmel's blog post.

Prerequisites

This post assumes you know what do notation is and what the Id monad does. See the monad series if not.

Lean can prove that programs are correct. Not just test them — prove them, for all possible inputs. This post builds up the machinery to do that for imperative-looking do blocks.

What does it mean to prove code correct?

Take a function that increments a register:

structure CPU where
  acc : Nat
  pc  : Nat

def step (cpu : CPU) : CPU := Id.run do
  let mut acc := cpu.acc
  let mut pc := cpu.pc
  acc := acc + 1
  pc := pc + 1
  return { acc, pc : CPU }

"Proving it correct" means stating a precise claim and proving it holds for all inputs:

theorem step_correct (cpu : CPU) :
    step cpu = { acc := cpu.acc + 1, pc := cpu.pc + 1 : CPU }

This says: for any CPU state, step increments both acc and pc by 1. Not just for one test case — for every possible CPU state.

How do you prove things about code?

You need a way to reason about what code does. The idea is old — from 1969 — and it's called a Hoare triple:

$$\{P\} ; C ; \{Q\}$$

  • C = the code
  • Q = what you want true AFTER
  • P = what must be true BEFORE

Read it as: "if P holds before running C, then Q holds after."

Simple example

Code:   x := 5
After:  x = 5        ← this is Q
Before: True          ← this is P (no requirements)

$$\{True\} \quad x := 5 \quad \{x = 5\}$$

Using current values

Code:   out := out + i
After:  out = 6                ← Q
Before: out + i = 6            ← P

Why out + i = 6? The assignment replaces out with out + i. So if out + i = 6 before (say out = 4, i = 2), then out = 6 after.

$$\{out + i = 6\} \quad out := out + i \quad \{out = 6\}$$

Computing P from Q: Weakest Precondition

Given code C and desired postcondition Q, weakest precondition (WP) computes the P for you. The rule for assignment is substitution:

$$WP(x := E, ; Q) = Q[x \mapsto E]$$

Take Q, replace every x with E. That's P. This rule comes from Dijkstra (1975)1.

1

The full WP calculus (assignment, sequential, conditional, loop) was developed in Dijkstra's Guarded Commands paper (1975) and his book A Discipline of Programming. For accessible lecture notes with worked examples, see CMU 15-414: Weakest Preconditions or Caltech CS 102: WP Notes. For the mechanized treatment, see Concrete Semantics Ch. 12.

Examples:

  • $WP(x := 5, ; x = 5) = (5 = 5) = True$
  • $WP(out := out + i, ; out = 6) = (out + i = 6)$
  • $WP(x := x * 2, ; x = 10) = (x * 2 = 10)$, so $x = 5$

For sequential code, chain backwards:

$$WP(S_1;; S_2, ; Q) = WP(S_1, ; WP(S_2, ; Q))$$

Compute what $S_2$ needs, then compute what $S_1$ needs to deliver that.

Code:   x := x + 1; x := x * 2
Q:      x = 10

WP(x := x * 2,  x = 10)  =  x * 2 = 10  =  x = 5
WP(x := x + 1,  x = 5)   =  x + 1 = 5   =  x = 4

So P = x = 4. And indeed: 4 → 5 → 10. ✓

mvcgen: WP for do blocks

Lean's mvcgen tactic automates this WP reasoning for do blocks. For the CPU example:

theorem step_correct (cpu : CPU) :
    step cpu = { acc := cpu.acc + 1, pc := cpu.pc + 1 : CPU } := by
  generalize h : step cpu = x       -- name the result
  apply Id.of_wp_run_eq h           -- use WP instead of unfolding the do block
  mvcgen                             -- compute WP through each assignment
  all_goals grind                    -- finish off the proof

What each line does:

  • generalize — gives the result a name so we can reason about it
  • Id.of_wp_run_eq — tells Lean "reason about this do block using WP, don't unfold it into raw code"
  • mvcgen — walks backwards through the assignments, computing WP at each step
  • grind — an automated tactic that proves the resulting goals (arithmetic, equalities, library facts)

No loop, no invariant. mvcgen handles straight-line code entirely on its own.

What's happening under the hood?

After mvcgen, the Infoview shows something like:

⊢ₛ
  wp⟦have acc := cpu.acc;
      have pc := cpu.pc;
      have acc := acc + 1;
      have pc := pc + 1;
      pure { acc := acc, pc := pc }⟧
    (PostCond.noThrow fun a =>
      { down := a = { acc := cpu.acc + 1, pc := cpu.pc + 1 } })

Reading this:

  • wp⟦...⟧ — "weakest precondition of this code." The code inside is your do block desugared into individual assignments (have = each let mut or :=)
  • PostCond.noThrow fun a => ... — the postcondition: "no exceptions, and the return value a satisfies..."
  • a = { acc := cpu.acc + 1, pc := cpu.pc + 1 } — your theorem statement, wrapped in the assertion language

The whole thing reads: "compute the WP of this straight-line code such that the result equals { acc := cpu.acc + 1, pc := cpu.pc + 1 }." Since there's no loop, grind substitutes backwards through each have and it resolves to True — done.

The problem with loops

WP works by substitution — it walks backwards, one statement at a time. But a loop runs an unknown number of times:

def mySum (l : Array Nat) : Nat := Id.run do
  let mut out := 0
  for i in l do
    out := out + i
  return out

How many times does out := out + i execute? Depends on l. WP can't just substitute — it doesn't know when to stop.

The solution: you provide a loop invariant — a property that:

  1. Holds before the loop starts
  2. Stays true after each iteration
  3. After the loop, implies what you want to prove

For mySum, the invariant is: "out equals the sum of elements processed so far."

l = #[1, 2, 3]

Before loop:  out = 0, processed = []       → sum([]) = 0 = out       ✓
After i=1:    out = 1, processed = [1]      → sum([1]) = 1 = out      ✓
After i=2:    out = 3, processed = [1,2]    → sum([1,2]) = 3 = out    ✓
After i=3:    out = 6, processed = [1,2,3]  → sum([1,2,3]) = 6 = out  ✓
Loop done:    processed = entire array       → out = l.sum              ✓

You provide the invariant. mvcgen checks it works by generating three proof obligations (base case, inductive step, conclusion). grind proves them.

mySum proof (detailed)

theorem mySum_correct (l : Array Nat) : mySum l = l.sum := by
  generalize h : mySum l = x
  apply Id.of_wp_run_eq h
  mvcgen
  invariants
  · ⇓⟨xs, out⟩ => ⌜xs.prefix.sum = out⌝
  with grind

nodup (early return)

def nodup (l : List Int) : Bool := Id.run do
  let mut seen : Std.HashSet Int := ∅
  for x in l do
    if x ∈ seen then
      return false
    seen := seen.insert x
  return true

theorem nodup_correct (l : List Int) : nodup l ↔ l.Nodup := by
  generalize h : nodup l = r
  apply Id.of_wp_run_eq h
  mvcgen
  invariants
  · Invariant.withEarlyReturn
      (onReturn := fun ret seen => ⌜ret = false ∧ ¬l.Nodup⌝)
      (onContinue := fun xs seen =>
        ⌜(∀ x, x ∈ seen ↔ x ∈ xs.prefix) ∧ xs.prefix.Nodup⌝)
  with grind

pairsSumToZero

def pairsSumToZero (l : List Int) : Bool := Id.run do
  let mut seen : Std.HashSet Int := ∅
  for x in l do
    if -x ∈ seen then
      return true
    seen := seen.insert x
  return false

theorem pairsSumToZero_correct (l : List Int) :
    pairsSumToZero l ↔ l.ExistsPair (fun a b => a + b = 0) := by
  generalize h : pairsSumToZero l = r
  apply Id.of_wp_run_eq h
  mvcgen
  invariants
  · Invariant.withEarlyReturn
      (onReturn := fun ret seen =>
        ⌜ret = true ∧ l.ExistsPair (fun a b => a + b = 0)⌝)
      (onContinue := fun xs seen =>
        ⌜(∀ x, x ∈ seen ↔ x ∈ xs.prefix) ∧
         ¬xs.prefix.ExistsPair (fun a b => a + b = 0)⌝)
  with simp_all <;> grind
