These are Notes on Chapter 4.1: One API, Many Applications from Functional Programming in Lean. What we will do here is re-express most things from the official Lean documentation in the language of our first note on monads.

We concluded last time that a monad is (m, unit, bind) — a type ("context", "side-effects" or a "container"), a lifter from original type to aforementioned type, and a way to compose functions whose return types are wrapped in this context type. -- vague i know!! Please skim the above post to make sure this makes sense.

Next, we work through the examples in the functional programming book -- and translate them to our mental model.

1. Option: Silent Failure

We want to get the first and third element of an array. We start with the happy world again. Imagine if someone promised us that the arrays were always at least 3 elements large. Then we can just write this computation as a composition of get the first element first, and then get the third. But we do not live in a world with nice promises. So we need to do error handling.

Option is just an inductive type:

inductive Option (α : Type) where
  | none : Option α
  | some : α → Option α

Option α is either none or some x, where x : α. List indexing with xs[i]? returns an Option.

So we write

def firstThird (xs : List α) : Option (α × α) :=
  match xs[0]? with
  | none => none
  | some first =>
    match xs[2]? with
    | none => none
    | some third => some (first, third)

#eval firstThird [1, 2]        -- none
#eval firstThird [1, 2, 3, 4]  -- some (1, 3)

If we wanted the first, third, and fifth elements, the nesting gets worse:

def firstThirdFifth (xs : List α) : Option (α × α × α) :=
  match xs[0]? with
  | none => none
  | some first =>
    match xs[2]? with
    | none => none
    | some third =>
      match xs[4]? with
      | none => none
      | some fifth => some (first, third, fifth)

Same boilerplate every level: match, handle none, unwrap some, continue. The thing we need to write the above as composition is once again a router — someone who makes sure none is not sent to the "get third element" function. They call this function andThen but it's just bind from our first post.

bind (andThen) restores composition:

def andThen (opt : Option α) (next : α → Option β) : Option β :=
  match opt with
  | none => none
  | some x => next x

Let's parse andThen in the language of our first post. bind takes two things:

  1. A value in the "context" type — here opt : Option α. This is the side-effect-carrying data.
  2. The next function to apply — here next : α → Option β. It takes the useful part (not none) and returns another Option.

If opt is none, andThen short-circuits — returns none without calling next. If opt is some x, it unwraps x and passes it to next. Same router pattern as the debuggable bind from our first post — just short-circuiting around none instead of concatenating strings.

unit is some — wraps a value x into Option, lifting it into the side-effect world.

Now:

def firstThirdSuccinct (xs : List α) : Option (α × α) :=
  andThen xs[0]? (fun first =>
    andThen xs[2]? (fun third =>
    some (first, third)))

#eval firstThirdSuccinct [1, 2, 3]  -- some (1, 3)

Some Decoration

If andThen or bind looks ugly, we can replace it with an infix operator ~~> for andThen, it gets even cleaner: Since bind takes two arguments — the data with side-effects and the next function — it's a natural binary operator.

infixl:55 " ~~> " => andThen

def firstThirdFifthInfix (xs : List α) : Option (α × α × α) :=
  xs[0]? ~~> fun first =>
  xs[2]? ~~> fun third =>
  xs[4]? ~~> fun fifth =>
  some (first, third, fifth)

#eval firstThirdFifthInfix [1, 2, 3, 4, 5]  -- some (1, 3, 5)

That looks a lot cleaner? Maybe — I am not sure how much. Lean actually gives us official machinery for this: the binary operator >>= (which we'll see in the type class post).

2. Except: Error Messages

The third example (WithLog) will look almost identical to our debuggable functions from the first post. But first, a variation on Option.

With Option, failure is silent — you get none and no idea why. What if we want an error message? We define a new inductive type with two constructors:

inductive Error (ε : Type) (α : Type) where
  | error : ε → Error ε α
  | ok : α → Error ε α
deriving Repr

Error ε α is either Error.error msg (failure with a message of type ε) or Error.ok x (success with a value of type α). Compare with Option: none becomes Error.error msg, some x becomes Error.ok x.

Same problem as before — we can't compose because get returns Error String α, not α:

def get (xs : List α) (i : Nat) : Error String α :=
  match xs[i]? with
  | none => Error.error s!"Index {i} not found (maximum is {xs.length - 1})"
  | some x => Error.ok x

If we wanted firstThird with error messages, we'd have the same nested matching as before — but now matching on Error.error/Error.ok instead of none/some. Same boilerplate, same routing problem.

So we write bind again. Parse it the same way as Option:

  1. Takes attempt : Error e α — the side-effect-carrying data (either an error or a value)
  2. Takes next : α → Error e β — the next function to run on the useful part

If attempt is an error, short-circuit — forward the error without calling next. If it's ok x, unwrap x and pass it to next. Same router, different data type.

def andThenError (attempt : Error e α) (next : α → Error e β) : Error e β :=
  match attempt with
  | Error.error msg => Error.error msg   -- short-circuit: forward the error
  | Error.ok x => next x                 -- unwrap and route to next

unit is Error.ok — lift a plain value into the error-handling world with no error.

Now composing:

def firstThirdError (xs : List α) : Error String (α × α) :=
  andThenError (get xs 0) fun first =>
    andThenError (get xs 2) fun third =>
    Error.ok (first, third)

#eval firstThirdError [1, 2, 3, 4] -- Error.ok (1, 3)
#eval firstThirdError [1]          -- Error.error "Index 2 not found (maximum is 0)"

Compare with Option: the structure is identical. andThen routes around none, andThenError routes around Error.error. The "side effect" is different (silent failure vs error message) but the routing pattern is the same.

3. WithLog: Accumulating a Log

This is the one that looks almost identical to our debuggable functions from the first post. There we had ℝ × String — a value paired with a debug string. Here we have a value paired with a list of log entries:

structure WithLog (logged : Type) (α : Type) where
  log : List logged
  val : α
deriving Repr

WithLog logged α holds a value val : α and a log log : List logged. Compare with our debuggable ℝ × String — same idea, but a List instead of a String.

The composition problem is identical to the debuggable case: if we have two computations that each produce logs, we need to concatenate the logs when composing them.

bind does exactly what our debuggable bind did — unwrap, apply next, concatenate the logs:

  1. Takes result : WithLog α β — a value with its log
  2. Takes next : β → WithLog α γ — the next function, which will produce its own log

Unwrap the value from result, pass it to next, concatenate both logs.

def andThenLog (result : WithLog α β) (next : β → WithLog α γ) : WithLog α γ :=
  let { log := thisOut, val := thisRes } := result
  let { log := nextOut, val := nextRes } := next thisRes
  { log := thisOut ++ nextOut, val := nextRes }

Compare with the debuggable bind from the first post:

  • There: (result, String.append log1 log2) — concatenate strings
  • Here: { log := thisOut ++ nextOut, val := nextRes } — concatenate lists

Same pattern.

unit wraps a value with an empty log — the "do nothing" entry point:

def okLog (x : β) : WithLog α β := { log := [], val := x }

Compare with the debuggable unit x = (x, "") — empty string becomes empty list.

Notice that WithLog has two blobs of data — a value and a log. So we essentially need two lifters:

  • okLog lifts from the value side: { log := [], val := x } — enters with a value, empty log
  • save lifts from the log side: { log := [data], val := () } — enters with a log entry, no useful value
def save (data : α) : WithLog α Unit :=
  { log := [data], val := () }

Just like we defined ~~> as infix for andThen in the Option section, we define ~~>L as infix for andThenLog:

infixl:55 " ~~>L " => andThenLog

Usage — sum a list while logging the even numbers we encounter:

def sumAndFindEvens : List Int → WithLog Int Int
  | [] => okLog 0
  | i :: is =>
    (if isEven i then save i else okLog ()) ~~>L fun () =>
    sumAndFindEvens is ~~>L fun sum =>
    okLog (i + sum)

#eval sumAndFindEvens [1, 2, 3, 4, 5]
-- { log := [2, 4], val := 15 }

Reading line by line:

  • | [] => okLog 0 — base case: empty list, return 0 with an empty log

  • | i :: is => — recursive case: i is the head, is is the tail

  • (if isEven i then save i else okLog ()) — if i is even, log it with save; otherwise do nothing with okLog (); both return WithLog Int Unit

  • ~~>L fun () => — this is andThenLog <left side> (fun () => <right side>). It runs the left side, runs the right side, concatenates the logs, and discards the Unit value

  • sumAndFindEvens is — recurse on the tail

  • ~~>L fun sum => — bind: sum is the result of the recursive call

  • okLog (i + sum) — return i + sum with an empty log (the accumulated logs are already handled by ~~>L)

4. State: Mutable Variables

This is the one that looks like our random seed example from the first post. There we had StdGen → α × StdGen — a function that takes a seed and returns a value plus an updated seed. Here the idea is the same but generalised: instead of a seed, we have any state σ.

def State (σ : Type) (α : Type) : Type :=
  σ → (σ × α)

State σ α is a function that takes a state of type σ and returns an updated state plus a value. This IS the random seed pattern — just with σ instead of StdGen.

The composition problem: if two functions both read and write state, the state from the first must be threaded into the second. Exactly the seed-threading problem from the first post.

bind threads the state through:

  1. Takes first : State σ α — a stateful computation
  2. Takes next : α → State σ β — the next computation, which also needs state

Run first with the current state, get back a new state and a value, pass both to next.

def andThenState (first : State σ α) (next : α → State σ β) : State σ β :=
  fun s =>
    let (s', x) := first s    -- run first, get new state s' and value x
    next x s'                  -- run next with value x and state s'

Compare with bindState from the first post — identical structure.

unit returns a value without changing the state:

def okState (x : α) : State σ α :=
  fun s => (s, x)

Compare with unitState x = fun seed => (x, seed) — same thing.

Extra operations — getState reads the current state, setState overwrites it:

def getState : State σ σ :=
  fun s => (s, s)       -- return the state as the value, state unchanged

def setState (s : σ) : State σ Unit :=
  fun _ => (s, ())      -- overwrite the state, return nothing useful

Usage — number the nodes of a binary tree using a counter as state:

def numberHelper : BinTree α → State Nat (BinTree (Nat × α))
  | BinTree.leaf => okState BinTree.leaf
  | BinTree.branch left x right =>
    numberHelper left ~~>S fun numberedLeft =>
    getState ~~>S fun n =>
    setState (n + 1) ~~>S fun () =>
    numberHelper right ~~>S fun numberedRight =>
    okState (BinTree.branch numberedLeft (n, x) numberedRight)

def number (t : BinTree α) : BinTree (Nat × α) :=
  (numberHelper t 0).2

#eval number (BinTree.branch
  (BinTree.branch BinTree.leaf "a" BinTree.leaf) "b"
  (BinTree.branch BinTree.leaf "c" BinTree.leaf))
-- branch (branch leaf (0, "a") leaf) (1, "b") (branch leaf (2, "c") leaf)

Read this line by line: number the left subtree, get the current counter, increment it, number the right subtree, assemble the result. The state (the counter) is threaded through by andThenState — we never pass it manually.

The Pattern

Terminology

Different sources use different names for the same things:

Our name (Piponi)FP in Lean bookThis postLean's actual API
bindandThenandThen, andThenError, andThenLog, andThenState>>= (or Bind.bind)
unitoksome, Error.ok, okLog, okStatepure (or Pure.pure)

The book uses generic names andThen and ok for all four (in separate namespaces). In our Lean file we use distinct names to avoid conflicts. Lean's Monad type class unifies them all under pure and >>=.

In the Piponi post we saw three monads:

Type m αbindunitSide effect
Debuggableα × Stringunwrap, apply, concat strings(x, "")debug logging
MultivaluedList αapply to each, flatten[x]multiple values
RandomisedStdGen → α × StdGenthread seed throughfun s => (x, s)randomness

The FP in Lean book gives us four more — all the same structure:

Type m αbindunitSide effect
OptionOption αif none stop, else unwrapsomesilent failure
ExceptError ε αif error stop, else unwrapError.okerror messages
WithLogWithLog logged αrun both, concat logsokLoglogging
Stateσ → σ × αthread state throughokStatemutable state

The triple (m, unit, bind) is a monad:

  • m is the context (failure, error, log, state)
  • unit is the identity (enter the monadic world doing nothing)
  • bind is the composer (chain operations, handling the plumbing)
