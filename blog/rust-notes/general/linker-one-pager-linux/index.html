Basic Setup

A hands-on tutorial on how linkers work, adapted from David Drysdale's Beginner's Guide to Linkers for Linux (x86-64). Code lives here. We start with this simple C program that declares most of the symbols you would expect in a program.

 1/* Definition of an uninitialized global variable */
 2int x_global_uninit;
 3
 4/* Definition of an initialized global variable */
 5int x_global_init = 1;
 6
 7/* Static uninitialized global -- only visible in this file */
 8static int y_global_uninit;
 9
10/* Static initialized global -- only visible in this file */
11static int y_global_init = 2;
12
13/* Declaration: this variable is defined in another file */
14extern int z_global;
15
16/* Declaration: this function is defined in another file */
17int fn_a(int x, int y);
18
19/* Static function definition -- only callable from this file */
20static int fn_b(int x)
21{
22  return x+1;
23}
24
25/* Function definition */
26int fn_c(int x_local)
27{
28  int y_local_uninit;
29  int y_local_init = 3;
30
31  x_global_uninit = fn_a(x_local, x_global_init);
32  y_local_uninit = fn_a(x_local, y_local_init);
33  y_local_uninit += fn_b(z_global);
34  return (y_global_uninit + y_local_uninit + y_global_init);
35}
36

For us to be able to run this program, we need to compile this down to machine code that the CPU understands. However certain functions and variables, like fn_a are not defined at all. So the how does the compiler find its implemenation? One would expect the compiler would complain, and we will not get machine code. Surprisingly, compilation goes through without any errors.

cc -c c_parts.c -o c_parts.o

It compiles fine -- cc -c only produces an object file, it does not try to make a runnable program. But if you try to run the object file directly:

./c_parts.o
bash: ./c_parts.o: cannot execute binary file: Exec format error

An object file is not an executable1. It has no entry point, no memory layout, and unresolved blanks. Something else needs to finish the job.

What really happens is that when the compiler sees a declaration (a definition without an implementation), it treats the declaration as a promise that the implementation for this function (or variable) exists somewhere, just not in this file.

We can peek inside the object file with objdump. It shows the sections (how the object file is organized) and the disassembly (the machine instructions the compiler generated):

objdump -d --section-headers c_parts.o
c_parts.o:	file format elf64-x86-64

Sections:
Idx Name             Size     VMA              Type
  0 .text            00000083 0000000000000000 TEXT
  1 .data            00000008 0000000000000000 DATA
  2 .bss             00000004 0000000000000000 BSS
  3 .comment         0000002c 0000000000000000
  4 .note.GNU-stack  00000000 0000000000000000
  5 .eh_frame        00000058 0000000000000000

Disassembly of section .text:

0000000000000000 <fn_c>:
       0: 55                    push   %rbp
       1: 48 89 e5              mov    %rsp,%rbp
       ...
      2a: e8 00 00 00 00        call   2f <fn_c+0x2f>
       ...
      6e: c3                    ret

000000000000006f <fn_b>:
      6f: 55                    push   %rbp
       ...
      82: c3                    ret

(Output trimmed for readability.) A few things to notice:

  • The VMA column stands for Virtual Memory Address -- where the section would start in the process's virtual memory (see objdump docs). In an object file these are all zero or relative offsets because the linker hasn't assigned final addresses yet. The Size column is in bytes (hex). We will get to who the linker is.
  • The object file has separate sections: .text for code, .data for initialized globals, .bss for uninitialized globals.
  • fn_c starts at offset 0x0 and fn_b at 0x6f in the .text section -- these match the nm offsets we are about to see.
  • The instruction call 2f is a function call to fn_a -- but the target address is just 0x2f (pointing at itself). That's a blank. The compiler didn't know where fn_a lives, so it wrote a placeholder. The linker will patch this later.

To see that the compiler actually leaves the implementation blank, we can look at the symbol table. A symbol table is a data structure inside the object file that maps names (like fn_a, x_global_init) to their addresses and metadata. For every function or global variable defined in the file, the symbol table records where it lives (using relative addressing). For every name that is declared but not defined, the symbol table records it as undefined -- a blank that needs to be filled later. The objdump output showed us raw bytes and instructions. The symbol table is what gives those bytes names -- without it, we'd just see addresses and opcodes with no way to know which function or variable is which. (For more background, see the ELF symbol table specification or this Wikipedia overview.)

We can dump the symbol table with nm. Here is what c_parts.c puts into it:

nm c_parts.o
# address          type  name
                 U      fn_a
000000000000006f t      fn_b
0000000000000000 T      fn_c
0000000000000000 D      x_global_init
0000000000000004 C      x_global_uninit
0000000000000004 d      y_global_init
0000000000000000 b      y_global_uninit
                 U      z_global

See those U entries for fn_a and z_global? No address2, just U for undefined. Those are the blanks. The other type letters tell you what kind of definition each symbol is (full list in the nm man page):

TypeMeaning
UUndefined -- a blank. The object file references this name but does not define it.
TA function definition. Code lives in the .text section.
tSame as T, but marked static (visible only within this file -- what "visible" means here will become clear once we introduce the linker).
DAn initialized global variable. Data lives in the .data section.
dSame as D, but marked static (visible only within this file).
CCommon -- an uninitialized global variable. In practice, int x; at file scope shows up as C, not B. The linker may merge duplicates across files (a historical C convention; disable with -fno-common).
BAn uninitialized global variable placed in the .bss section (zeroed at runtime). Appears after linking, or when compiled with -fno-common.
bSame as B, but marked static (visible only within this file).

Lowercase = static (the name is not exported from this object file -- the linker, which we are about to introduce, will not let other files reference it). Uppercase = not static (the name is exported and other object files can reference it).

The things we see in the symbol table are the global variables, function names and declared functions (and variables).

  • int x_global_init = 1; -- definition of a global variable, initialized.
  • int x_global_uninit; -- definition of a global variable, uninitialized.
  • static int y_global_init = 2; -- definition of a static global variable, initialized.
  • static int y_global_uninit; -- definition of a static global variable, uninitialized.
  • extern int z_global; -- declaration. No storage allocated, no code generated. A promise that the definition exists elsewhere.
  • int fn_a(int x, int y); -- declaration of a function. Same idea: a promise, no code generated.
  • static int fn_b(int x) { ... } -- definition of a static function. Code is generated.
  • int fn_c(int x_local) { ... } -- definition of a function. Code is generated.
Aside: No underscore prefix on Linux

On macOS, nm shows C symbols with a leading underscore: _fn_a, _x_global_init, etc. This is a Mach-O convention inherited from classic Mac toolchains. On Linux (ELF), there is no underscore prefix -- fn_a appears as fn_a, not _fn_a. All the symbol names in this article reflect the Linux convention.

2

The addresses in the first column are offsets, not final memory addresses. fn_b at 0x6f means "111 bytes from the start of the .text (code) section in c_parts.o." At this stage we have no idea where in the final process's virtual memory the .text section will land -- but that does not matter. These are relative positions: fn_b starts 111 bytes after the beginning of .text, wherever that ends up. Deciding the final placement is the job of the linker -- a program we are about to describe.

What about local variables?

int y_local_uninit; and int y_local_init = 3; inside fn_c do not appear in the symbol table. These are local variables. A local variable may be initialized or uninitialized (in which case its value is whatever garbage is on the stack), but either way the compiler already knows its offset from the stack pointer. There is no promise of "I exist somewhere, my location will be filled in later" -- so there is no reason to put local variables in the symbol table.

The static keyword and the definition-vs-declaration distinction affect how each name shows up in the nm output above -- uppercase vs lowercase class letters, U for blanks. We will come back to this.

The Missing Pieces

Now say the things c_parts.c is referencing -- fn_a and z_global -- were defined in another file. Save this as c_rest.c:

 1/* Definition of the variable c_parts.c declared as extern */
 2int z_global = 11;
 3
 4/* A separate static with the same name -- no conflict, file-local */
 5static int y_global_init = 2;
 6
 7/* Declaration: refers to x_global_init from c_parts.c */
 8extern int x_global_init;
 9
10/* Definition of the function c_parts.c declared */
11int fn_a(int x, int y)
12{
13  return(x+y);
14}
15
16int main(int argc, char *argv[])
17{
18  const char *message = "Hello, world";
19  return fn_a(x_global_init, y_global_init);
20}

Compile c_rest.c the same way -- compile only, no linking:

cc -c c_rest.c -o c_rest.o
objdump -d --section-headers c_rest.o
c_rest.o:	file format elf64-x86-64

Sections:
Idx Name             Size     VMA              Type
  0 .text            00000050 0000000000000000 TEXT
  1 .data            00000008 0000000000000000 DATA
  2 .rodata          0000000d 0000000000000000
  3 .comment         0000002c 0000000000000000
  4 .note.GNU-stack  00000000 0000000000000000
  5 .eh_frame        00000058 0000000000000000

Disassembly of section .text:

0000000000000000 <fn_a>:
       0: 55                    push   %rbp
       ...
      12: c3                    ret

0000000000000013 <main>:
      13: 55                    push   %rbp
       ...
      3f: e8 00 00 00 00        call   44 <main+0x31>
       ...
      4f: c3                    ret

Same structure: .text for code, .data for initialized globals, plus a .rodata section for the "Hello, world" string literal. Again, call 44 is a blank -- main calls fn_a but the compiler doesn't know where fn_a lives yet.

Dump the symbol table:

nm c_rest.o
# address          type  name
0000000000000000 T      fn_a
0000000000000013 T      main
                 U      x_global_init
0000000000000004 d      y_global_init
0000000000000000 D      z_global

fn_a is T (function definition) and z_global is D (initialized global) -- exactly what c_parts.o left as U blanks. x_global_init is U here -- c_rest.c declared it with extern and uses it, but the definition lives in c_parts.o. Notice y_global_init appears here too as d (lowercase -- static), just like in c_parts.o.

Now we have two separate object files. c_parts.o depends on symbols defined in c_rest.o, but neither file knows the other exists. The compiler processed each file in isolation. Somebody needs to combine these two symbol tables, match every U blank in one file to a definition in the other, and produce a single executable with real addresses.

That somebody is the linker.

The linker

The linker is a program called ld on Linux (and macOS).3 It takes object files as input and produces an executable. Let's invoke it directly:

ld c_parts.o c_rest.o -o sample1 -lc -dynamic-linker /lib64/ld-linux-x86-64.so.2

The flags:

  • c_parts.o c_rest.o -- the two object files to combine.
  • -o sample1 -- name of the output executable.
  • -lc -dynamic-linker /lib64/ld-linux-x86-64.so.2 -- boilerplate needed because libc is a shared library on Linux. We explain what these flags mean and why they're necessary in the Shared libraries section.
cc does this for you

When you run cc c_parts.o c_rest.o -o sample1 (without -c), cc invokes ld behind the scenes and supplies -lc, -dynamic-linker, and other platform flags automatically. Using ld directly makes visible what cc hides.

The linker:

  1. Collects the symbol tables from both c_parts.o and c_rest.o
  2. Matches every U (undefined) symbol to a matching definition (T, D, B, etc.)
  3. Assigns real virtual addresses to every symbol
  4. Writes the final executable

Examine the result:

nm sample1 | grep -v "^$"
What does the grep do?

grep -v "^$" filters out blank lines -- nm prints empty lines between sections in the executable, and removing them keeps the output compact.

Compare the two input symbol tables side by side with the merged result:

Both files have U blanks that the other file fills: c_parts.o needs fn_a and z_global from c_rest.o, and c_rest.o needs x_global_init from c_parts.o. Both files have their own y_global_init as d (lowercase -- static).

After linking -- the merged symbol table in sample1:

# address            type  name
0000000000401150 T      fn_a
0000000000401138 t      fn_b
00000000004010b0 T      fn_c
0000000000401163 T      main
0000000000404000 D      x_global_init
0000000000404014 B      x_global_uninit
0000000000404004 d      y_global_init
000000000040400c d      y_global_init
0000000000404010 b      y_global_uninit
0000000000404008 D      z_global

No more U symbols. Every blank has been filled. The U fn_a from c_parts.o matched the T fn_a from c_rest.o. The U z_global matched D z_global. The U x_global_init from c_rest.o matched the D x_global_init from c_parts.o.

Notice the addresses have changed. In the object files, addresses like 0x6f were offsets relative to a section (e.g. "111 bytes into .text"). Now they are virtual addresses -- locations in the process's virtual memory space, not physical memory. ld decided where every section lands in the process's address space and rewrote all the offsets into final addresses. For example, fn_b went from offset 0x6f in c_parts.o to virtual address 0x401138 in the executable.

Now the lowercase/uppercase distinction from earlier makes sense. Look at y_global_init -- it appears twice in the merged table, at two different addresses (0x404004 and 0x40400c). Both c_parts.c and c_rest.c defined static int y_global_init = 2;, and because both are static (lowercase d), ld treats them as separate, file-local symbols that do not conflict. Each file gets its own copy.

But what happens if both files define the same non-static global variable? We address this next.

Duplicate symbols

What if two files both define the same global (non-static) name? Let's try it.

Case 1: Initialized duplicates

Two files both define int shared with a value:

1int shared = 10;
2
3int get_a(void)
4{
5  return shared;
6}
1int shared = 20;
2
3int get_b(void)
4{
5  return shared;
6}

Compile both, then try to link:

cc -c dup_a.c -o dup_a.o
cc -c dup_b.c -o dup_b.o
ld dup_a.o dup_b.o dup_main.o -o dup_test -lc -dynamic-linker /lib64/ld-linux-x86-64.so.2
dup_b.o: in function `get_b':
dup_b.c:(.text+0x0): multiple definition of `shared'; dup_a.o:dup_a.c:(.text+0x0): first defined here
ld: 1 duplicate symbols

ld refuses. Two definitions, one name -- which value should shared have, 10 or 20?

Case 2: Uninitialized duplicates (common symbols)

Now try the same thing but without initializers:

1int shared;
2
3int get_a(void)
4{
5  return shared;
6}
1int shared;
2
3int get_b(void)
4{
5  return shared;
6}

Both show up as C (common) in the symbol table:

nm dup_common_a.o | grep shared
nm dup_common_b.o | grep shared
0000000000000004 C shared
0000000000000004 C shared

Link them:

ld dup_common_a.o dup_common_b.o dup_main.o -o dup_common_test -lc -dynamic-linker /lib64/ld-linux-x86-64.so.2

No error. ld silently merges both C shared into a single symbol:

nm dup_common_test | grep shared
0000000000404000 B shared

This is a historical C convention -- uninitialized globals are "common" symbols that ld is allowed to merge. You can disable this with -fno-common, which makes the compiler emit B instead of C, and then ld will error on duplicates just like the initialized case:

cc -fno-common -c dup_common_a.c -o dup_common_a.o
cc -fno-common -c dup_common_b.c -o dup_common_b.o
ld dup_common_a.o dup_common_b.o dup_main.o -o dup_test -lc -dynamic-linker /lib64/ld-linux-x86-64.so.2
dup_common_b.o: in function `get_b':
dup_common_b.c:(.text+0x0): multiple definition of `shared'; dup_common_a.o:dup_common_a.c:(.text+0x0): first defined here
ld: 1 duplicate symbols

Static libraries

When you have useful functions you want to reuse across programs, you can bundle object files into a static library (.a file on macOS/Linux).

Split the math functions into separate files, plus one extra function we won't use:

1int add(int x, int y)
2{
3  return x + y;
4}
1int multiply(int x, int y)
2{
3  return x * y;
4}
1int subtract(int x, int y)
2{
3  return x - y;
4}

And a program that uses add and multiply but not subtract. Save as use_mathlib.c:

 1extern int add(int x, int y);
 2extern int multiply(int x, int y);
 3
 4int main(void)
 5{
 6  int a = add(3, 4);
 7  int b = multiply(a, 2);
 8  return b;
 9}

Compile each source file into its own .o:

cc -c add.c -o add.o
cc -c multiply.c -o multiply.o
cc -c unused.c -o unused.o

Now bundle all three .o files into a single .a archive:

ar rcs libmathstuff.a add.o multiply.o unused.o

The flags: r inserts files into the archive, c creates the archive if it doesn't exist, s writes a symbol index. A .a file is just multiple .o files concatenated together with a table of contents at the front. The table of contents (the symbol index) maps symbol names to which .o file defines them -- so ld can look up add and immediately know it's in add.o without cracking open every .o in the archive.

We can see what's inside:

ar -t libmathstuff.a
add.o
multiply.o
unused.o

We can even objdump the .a file directly -- it processes each .o inside:

objdump --section-headers libmathstuff.a
libmathstuff.a(add.o):	file format elf64-x86-64

Sections:
Idx Name             Size     VMA              Type
  0 .text            00000014 0000000000000000 TEXT
  1 .comment         0000002c 0000000000000000
  2 .note.GNU-stack  00000000 0000000000000000
  3 .eh_frame        00000038 0000000000000000

libmathstuff.a(multiply.o):	file format elf64-x86-64

Sections:
Idx Name             Size     VMA              Type
  0 .text            00000014 0000000000000000 TEXT
  1 .comment         0000002c 0000000000000000
  2 .note.GNU-stack  00000000 0000000000000000
  3 .eh_frame        00000038 0000000000000000

libmathstuff.a(unused.o):	file format elf64-x86-64

Sections:
Idx Name             Size     VMA              Type
  0 .text            00000014 0000000000000000 TEXT
  1 .comment         0000002c 0000000000000000
  2 .note.GNU-stack  00000000 0000000000000000
  3 .eh_frame        00000038 0000000000000000

Three separate object files, each with its own .text section. The archive is just a container.

Now compile the program and look at its blanks:

cc -c use_mathlib.c -o use_mathlib.o
nm use_mathlib.o
                 U add
0000000000000000 T main
                 U multiply

main is defined, but add and multiply are U -- blanks. No mention of subtract because use_mathlib.c never references it. Let's link:

ld use_mathlib.o -L. -lmathstuff -o use_mathlib -lc -dynamic-linker /lib64/ld-linux-x86-64.so.2

The flags:

  • -L. -- add the current directory to ld's library search path. By default ld only looks in system directories like /usr/lib and /lib. Without -L., ld would not find libmathstuff.a in the current directory.
  • -lmathstuff -- look for a library called libmathstuff. ld prepends lib and tries .so first, then .a. Since we only have the .a, it uses that.

Check the result:

nm use_mathlib | grep -v "^$"
0000000000401168 T add
0000000000401128 T main
0000000000401188 T multiply

add and multiply are no longer U -- ld found them in libmathstuff.a, pulled in add.o and multiply.o, and copied their code directly into the executable. But subtract is nowhere to be seen. ld looked at the archive's symbol index, saw that nothing needed subtract, and left unused.o out entirely.

./use_mathlib; echo $?
14

(3+4=7, 7*2=14, returned as the exit code.)

This is the point of a .a over just passing .o files directly. If we had written ld use_mathlib.o add.o multiply.o unused.o ..., ld would include all three. With -lmathstuff, ld is selective -- it only pulls in the .o files it actually needs.

Order matters. ld processes arguments left to right, maintaining a list of unresolved U symbols as it goes. When it encounters a library (-l), it searches the library's symbol index for definitions that match the current unresolved list. If -lmathstuff appears before use_mathlib.o, the unresolved list is empty at that point, so nothing gets pulled in. Rule of thumb: libraries go last.

-l prefers .so over .a

When both libmathstuff.so and libmathstuff.a exist in the same directory, -lmathstuff will pick the .so. To force static linking, pass the .a path directly instead of using -l: ld use_mathlib.o libmathstuff.a -o use_mathlib ... Or use -Bstatic -lmathstuff -Bdynamic to temporarily force static linking for just that library.

What the OS does with the executable

The linker's job is done. ld wrote sample1 and exited. Now when you run ./sample1, the OS kernel and ld-linux (the dynamic linker we introduced earlier) take over.

First, let's look at what ld left behind. The sections in the executable:

objdump --section-headers sample1
sample1:	file format elf64-x86-64

Sections:
Idx Name          Size     VMA              Type
  0 .text         00000108 00000000004010b0 TEXT
  1 .rodata       0000000d 00000000004011c0 DATA
  2 .eh_frame     00000090 00000000004011d0 DATA
  3 .data         00000010 0000000000404000 DATA
  4 .bss          00000008 0000000000404010 BSS

Compare this to the object files: the VMA column now has real virtual addresses (like 0x4010b0), not zeros. ld placed every section at a specific location in the process's address space. Where sections get placed, in what order, and at what alignment is controlled by a linker script -- ld has a default one built in, but it can be overridden with ld -T script.ld.

What happens when you run ./sample1

ld is done. sample1 is a file on disk. When you type ./sample1, the following sequence happens:

  1. Your shell calls execve("./sample1", ...) -- this is a system call that asks the kernel to replace the current process with a new program.4

  2. The kernel reads the ELF header of sample1. It sees the file is ET_EXEC (an executable) and reads the program headers to find out which segments need to be loaded and where. You can see exactly what the kernel sees with readelf -h:

    readelf -h sample1
      Magic:   7f 45 4c 46 02 01 01 00 ...
  Class:                             ELF64
  Type:                              EXEC (Executable file)
  Entry point address:               0x4010b0
  ...
  Number of program headers:         6

    The Entry point address is where execution will eventually start. The program headers describe the segments to load.

  3. The kernel creates a new virtual address space for the process. At this point the process has no code, no data, no stack -- just an empty address space.

    Virtual Address Space
─────────────────────
0xFFFF...FFFF (high)
┌───────────────────┐
│                   │
│                   │
│   unmapped        │
│   no permissions  │
│   nothing here    │
│                   │
│                   │
└───────────────────┘
0x0000...0000 (low)

  4. The kernel maps the executable's segments into memory. The ELF file contains LOAD segments that tell the kernel exactly what to put where. You can see these with readelf -l:

    readelf -l sample1
    Program Headers:
  Type    Offset   VirtAddr           FileSiz  MemSiz   Flg
  LOAD    0x000000 0x0000000000400000 0x001260 0x001260 R
  LOAD    0x001000 0x0000000000401000 0x000108 0x000108 R E
  LOAD    0x002000 0x0000000000402000 0x0000a0 0x0000a0 R
  LOAD    0x003000 0x0000000000404000 0x000010 0x000018 RW
  INTERP  0x000318 0x0000000000400318 0x00001c 0x00001c R
        [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]

    The R E segment is .text -- readable and executable, but not writable. The RW segment is .data and .bss -- readable and writable.5 The .data bytes are copied from the executable file. The .bss bytes are zeroed (the OS allocates zero-filled pages, which is why uninitialized globals start as zero without taking up space in the file).

    After this step the address space looks like:

    Virtual Address Space
─────────────────────
0xFFFF...FFFF (high)
┌───────────────────┐
│   unmapped         │
│                    │
├────────────────────┤
│   .bss     (rw-)   │  ← zeroed by kernel
│   .data    (rw-)   │  ← copied from file
├────────────────────┤
│   .text    (r-x)   │  ← code, read-only
├────────────────────┤
│   unmapped         │
└────────────────────┘
0x0000...0000 (low)

  5. The kernel sees the INTERP program header -- visible in the readelf -l output above as [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]. This is the -dynamic-linker path we passed to ld. The kernel loads ld-linux into the address space too.

    Virtual Address Space
─────────────────────
0xFFFF...FFFF (high)
┌───────────────────┐
│   unmapped         │
│                    │
├────────────────────┤
│   ld-linux  (r-x)  │  ← loaded by kernel
├────────────────────┤
│   unmapped         │
├────────────────────┤
│   .bss     (rw-)   │
│   .data    (rw-)   │
├────────────────────┤
│   .text    (r-x)   │
├────────────────────┤
│   unmapped         │
└────────────────────┘
0x0000...0000 (low)

  6. The kernel jumps to ld-linux, not to the program's code. ld-linux is now running inside the new process.

  7. ld-linux loads shared libraries. It reads the NEEDED entries in the executable (these came from -lc) and loads libc.so.6 into the address space. It resolves U symbols in the executable to addresses in libc.so. You can see the NEEDED entries with:

    readelf -d sample1 | grep NEEDED
     0x0000000000000001 (NEEDED)   Shared library: [libc.so.6]
    Virtual Address Space

Local variables and heap allocations are invisible to ld. ld only dealt with code and global data -- the stack and heap are set up by the OS at runtime.

Shared libraries

With static libraries, ld copies code into every executable that uses it. If ten programs link against libmathstuff.a, ten executables each contain their own copy of add and multiply. Shared libraries solve this -- the code stays in a separate file on disk, and the OS loads it once into memory at runtime.

On Linux, shared libraries are .so files (shared objects). On macOS, .dylib files.

This is also the right place to explain the -lc -dynamic-linker flags we've been passing to ld throughout this tutorial. -lc tells ld to link against libc.so -- the C standard library. ld prepends lib and appends .so, so -lc becomes libc.so. This library provides _start (the real entry point the kernel jumps to), which calls __libc_start_main, which eventually calls your main. Without -lc, the executable has no entry point and will crash.

-dynamic-linker /lib64/ld-linux-x86-64.so.2 is needed because libc.so is a shared library. The kernel doesn't know how to load .so files itself -- it needs ld-linux to do that. This flag embeds the path to ld-linux into the executable's ELF header. When you run ./sample1, the kernel sees that path, loads ld-linux first, and ld-linux then loads libc.so and resolves symbols before jumping to _start. The two flags go together: -lc says what to link, -dynamic-linker says how to load it at runtime.

Build a shared library from the same .o files we used for the static library:

cc -shared -o libmathstuff.so add.o multiply.o unused.o

Inspect it:

nm libmathstuff.so | grep " T "
00000000000010f0 T add
0000000000001110 T multiply
0000000000001130 T subtract

All three functions are in the shared library -- add, multiply, and subtract. Unlike a static library, there is no selective inclusion. The entire .so is one unit.

Now delete the .a file (so -l doesn't pick it up) and link against the shared library:

rm libmathstuff.a
ld use_mathlib.o -L. -lmathstuff -o use_mathlib_dyn -lc -dynamic-linker /lib64/ld-linux-x86-64.so.2

Check the result:

nm use_mathlib_dyn | grep -v "^$"
                 U add
0000000000401140 T main
                 U multiply

Compare this to the static library result where add and multiply were T (code copied in). Here they are still U -- undefined. The executable does not contain the code for add or multiply. Instead, the executable records a dependency: "at runtime, find libmathstuff.so and resolve these symbols from it."

We can see this dependency with ldd (the Linux equivalent of macOS's otool -L):

	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f4a12100000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f4a12350000)

Two .so dependencies now: our libmathstuff.so and libc.so.6. When the OS runs use_mathlib_dyn, the same sequence from What happens when you run ./sample1 plays out -- the kernel loads the executable, finds ld-linux via the INTERP header, and ld-linux loads both .so files into the address space and resolves the U symbols.

Dynamically loaded libraries (plugins)

Shared libraries are loaded at program startup -- as we saw in What happens when you run ./sample1, ld-linux resolves all .so dependencies before main runs (steps 6-8). But you can also load a shared library while the program is already running. This is the plugin pattern.

The API on macOS/Linux:

  • dlopen(path, flags) -- load a .so at runtime, returns a handle
  • dlsym(handle, "name") -- look up a symbol by name string, returns a pointer
  • dlclose(handle) -- unload the library

Save this as plugin_user.c:

 1#include <stdio.h>
 2#include <dlfcn.h>
 3
 4int main(void)
 5{
 6  void *handle = dlopen("./libmathstuff.so", RTLD_LAZY);
 7  if (!handle) {
 8    printf("dlopen failed: %s\n", dlerror());
 9    return 1;
10  }
11
12  int (*add)(int, int) = dlsym(handle, "add");
13  int (*multiply)(int, int) = dlsym(handle, "multiply");
14  int (*subtract)(int, int) = dlsym(handle, "subtract");
15
16  if (!add || !multiply || !subtract) {
17    printf("dlsym failed: %s\n", dlerror());
18    return 1;
19  }
20
21  printf("add(3, 4) = %d\n", add(3, 4));
22  printf("multiply(3, 4) = %d\n", multiply(3, 4));
23  printf("subtract(10, 3) = %d\n", subtract(10, 3));
24
25  dlclose(handle);
26  return 0;
27}

Build and run:

cc plugin_user.c -o plugin_user -ldl
./plugin_user
add(3, 4) = 7
multiply(3, 4) = 12
subtract(10, 3) = 7
Linking with -ldl

On Linux, dlopen, dlsym, and dlclose live in libdl.so, so you need -ldl:

cc plugin_user.c -o plugin_user -ldl

On some newer glibc versions, these symbols have been moved into libc.so.6 itself, so -ldl may be optional -- but it's good practice to include it for portability.

Look at the symbol table of plugin_user:

nm plugin_user | grep -v "^$"
                 U dlclose
                 U dlerror
                 U dlopen
                 U dlsym
0000000000401160 T main
                 U printf

No add, no multiply, no subtract -- not even as U. The executable has no idea libmathstuff.so exists. It only knows about dlopen, dlsym, etc. (which come from libdl/libc). The connection to libmathstuff.so is made entirely at runtime, by passing the string "add" to dlsym.

ldd plugin_user
	linux-vdso.so.1 (0x00007ffcc3bfe000)
	libdl.so.2 => /lib/x86_64-linux-gnu/libdl.so.2 (0x00007f4a12300000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f4a12100000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f4a12350000)

Only system libraries. No mention of libmathstuff at all. Compare this to ldd use_mathlib_dyn above, which listed libmathstuff.so as a dependency. That's the difference: shared libraries are declared at link time and show up in ldd; plugins are loaded at runtime and are invisible to ldd.

RTLD_LAZY means "resolve symbols one by one as they are called."6 RTLD_NOW means "resolve all symbols immediately when dlopen is called." RTLD_LAZY makes dlopen faster but defers errors; RTLD_NOW is safer because it fails early if a symbol is missing.

dlsym works because the shared library contains a symbol table -- the same name-to-address mapping we've been looking at with nm. dlsym does the same lookup at runtime: given the string "add", find the address of add in the loaded .so.

This is how Sail plugins work

The Sail compiler uses exactly this mechanism. The sail binary calls dlopen to load backend plugins like sail_plugin_lean.cmxs (OCaml's equivalent of a .so). The plugin's initialization code registers new command-line flags (like --lean) with the compiler. Without the plugin loaded, the sail binary doesn't know the --lean flag exists.

Aside: what is ELF?

Throughout this tutorial, objdump has been printing file format elf64-x86-64. ELF (Executable and Linkable Format) is the container format Linux uses for all binary files. It's the Linux equivalent of macOS's Mach-O format.

Every .o file, .so file, and executable we've created in this tutorial is an ELF file -- but they are different types of ELF:

ELF typeFlagWhat it isExample
RelocatableET_RELSections and symbols, but no entry point and no final addresses. Cannot be run.c_parts.o
ExecutableET_EXECEntry point and virtual addresses assigned by the linker. Can be run.sample1
Shared objectET_DYNLike an executable but can be loaded at any address.libmathstuff.so

You can check a file's ELF type with readelf -h:

readelf -h c_parts.o | grep Type
readelf -h sample1 | grep Type
readelf -h libmathstuff.so | grep Type
  Type:  REL (Relocatable file)
  Type:  EXEC (Executable file)
  Type:  DYN (Shared object file)

Same container format, different contents. The ELF header tells the OS and tools what kind of file it is and how to use it. For the full specification, see the ELF spec.

Aside: how symbol resolution actually works (PIC, GOT, PLT)

Throughout this tutorial we've said ld-linux "resolves" symbols at runtime. What does that mean concretely?

PIC (Position Independent Code) is a compilation choice, not an inherent property of the code. When you pass -fPIC to the compiler, it generates code that uses GOT indirection instead of hardcoding absolute virtual addresses. You can apply -fPIC to any C file. Shared libraries require it (otherwise the .text section would need patching at load time). Regular executables don't need it, but can opt in with -fPIE / -pie to enable ASLR on the executable itself.

When compiled with PIC, the code in .text never contains absolute addresses for external symbols -- so it never needs to be modified, and can stay read-only and shared across processes (see 5).

To see why this matters, consider what happens when main calls add, where add lives in libmathstuff.so. In both cases the C source is the same: add(3, 4). The difference is what the compiler and linker generate.

Without PIC (the old way), ld hardcodes the virtual address of add into the call instruction:

.text of main:
    call 0x7f4a12340100       ← virtual address of add() baked into the instruction

The problem: the virtual address where libmathstuff.so gets loaded can change between runs. The kernel uses ASLR (Address Space Layout Randomization) for security, or another library might already occupy that region of virtual memory. If libmathstuff.so loads at 0x7f4a12340000 this time, add is at 0x7f4a12340100. Next time it might load at 0x7f4a99990000, and add would be at 0x7f4a99990100. The hardcoded call 0x7f4a12340100 in .text would jump to the wrong virtual address. The loader would have to rewrite the instruction in .text to patch in the correct address. Once .text is modified, it can't be shared across processes and can't be read-only.

With PIC (what modern systems do), the compiler and linker generate something different. The call add(3, 4) in the source becomes a call to a small stub (the PLT entry for add), and that stub reads the real address from a table (the GOT). Two new data structures appear in the binary:

The GOT (Global Offset Table) is a table of pointers that lives in the writable data segment. Each slot holds the virtual address of one external function or variable. ld creates the GOT with empty slots, and ld-linux fills them in at runtime. For our use_mathlib_dyn example (which calls add and multiply from libmathstuff.so), the GOT looks like:

GOT (in .data, writable)
┌───────┬──────────────────────────────────────────────┐
│ slot  │ contents (filled by ld-linux at runtime)     │
├───────┼──────────────────────────────────────────────┤
│ [0]   │ (reserved for ld-linux internal use)         │
│ [1]   │ (reserved for ld-linux internal use)         │
│ [2]   │ (reserved for ld-linux internal use)         │
│ [3]   │ 0x7f4a12340100  → add() in libmathstuff.so  │
│ [4]   │ 0x7f4a12340120  → multiply() in libmathstuff│
│ [5]   │ 0x7f4a12100450  → printf() in libc.so.6     │
│  ...  │  ...                                         │
└───────┴──────────────────────────────────────────────┘

Each slot is just a pointer (8 bytes on x86-64). The addresses can differ each time the process is started (due to ASLR), so ld-linux must write them fresh every time the program runs. The GOT is writable precisely because it needs to be patched at process startup.

The PLT (Procedure Linkage Table) is a set of small stubs that live in the .text section of the executable (i.e. use_mathlib_dyn, the binary doing the calling -- not libmathstuff.so). ld generates one PLT stub per external function. Each stub reads an address from the corresponding GOT slot and jumps there:

PLT (in .text, read-only)
┌─────────────────────────────────┐
│ add_PLT_stub:                   │
│   load address from GOT[3]      │
│   jump to it                    │
├─────────────────────────────────┤
│ multiply_PLT_stub:              │
│   load address from GOT[4]      │
│   jump to it                    │
├─────────────────────────────────┤
│ printf_PLT_stub:                │
│   load address from GOT[5]      │
│   jump to it                    │
└─────────────────────────────────┘

The PLT stubs are identical in structure -- they differ only in which GOT slot they read.7 The stubs themselves never change (read-only .text). Only the GOT entries (writable .data) get patched.

Here's what ld generates for add(3, 4):

.text (read-only):                  .data (writable):
┌──────────────────────┐            ┌─────────────────────────────┐
│ main:                │            │ GOT[0]: ...                 │
│   call add_PLT_stub ────────┐    │ GOT[1]: ...                 │
│                      │      │    │ GOT[2]: ...                 │
│                      │      │    │ GOT[3]: 0x7f4a12340100 ◄──┐ │
└──────────────────────┘      │    └─────────────────────────────┘ │
                              │                                     │
┌──────────────────────┐      │    address of add() in              │
│ add_PLT_stub:        │◄─────┘    libmathstuff.so, written         │
│   load GOT[3] ───────────────────by ld-linux at runtime ─────────┘
│   jump to it         │
└──────────────────────┘

main calls add_PLT_stub (a fixed offset within the same .text section -- no absolute address needed). The stub loads whatever address is in GOT[3] and jumps there. ld-linux wrote the real address of add into GOT[3] at startup.

The .text instructions are identical no matter where libmathstuff.so gets loaded. The code says "jump to whatever address is in GOT slot 3" -- it never says "jump to 0x7f4a12340100." Only the GOT entry (in writable .data) changes. That's what "no absolute addresses in .text" means.

Lazy binding (RTLD_LAZY)

With lazy binding (the default), ld-linux does not fill in GOT entries at startup. Instead, ld sets each GOT entry to point at the resolver.8

First call to add:

main                PLT                  GOT                    ld-linux
  │                  │                    │                       │
  │  call add_stub   │                    │                       │
  │─────────────────>│                    │                       │
  │                  │  load GOT[3]       │                       │
  │                  │───────────────────>│                       │
  │                  │                    │                       │
  │                  │  GOT[3] currently points to ld-linux's     │
  │                  │  resolver (not add -- add hasn't been      │
  │                  │  looked up yet)                             │
  │                  │                    │                       │
  │                  │  jump to GOT[3] ──────────────────────────>│
  │                  │                    │                       │
  │                  │                    │  resolver:             │
  │                  │                    │  1. look up "add" in   │
  │                  │                    │     libmathstuff.so    │
  │                  │                    │  2. find add() is at   │
  │                  │                    │     0x7f4a...100       │
  │                  │                    │  3. write 0x7f4a...100 │
  │                  │                    │     into GOT[3]        │
  │                  │                    │  4. jump to 0x7f4a...100
  │                  │                    │                       │
  │<────────────────────────────────── now running add() ─────────┘

Second call to add:

main                PLT                  GOT
  │                  │                    │
  │  call add_stub   │                    │
  │─────────────────>│  load GOT[3]       │
  │                  │───────────────────>│ GOT[3] = 0x7f4a...100
  │                  │                    │       (already patched)
  │<──────────────────────────────────────── jump to add()

The first call is slow (resolver runs), every subsequent call is fast (one indirect jump). No resolver involved.

Eager binding (RTLD_NOW)

With RTLD_NOW, ld-linux patches all GOT entries during dlopen (or at program startup). Every call goes directly from the start -- no resolver, no first-call penalty. Slower startup, but no surprise failures later if a symbol is missing.

The key insight

The .text section is never modified. All patching happens in GOT entries, which live in the writable data segment. This is what makes it possible for multiple processes to share the same physical pages of library code in RAM.
