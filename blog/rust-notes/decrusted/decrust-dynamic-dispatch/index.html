Monomorphisation

Monomorphisation definition: The process by which rust takes generic code and transforms it into specific code. This is a fairly abstract definition, so let's look at something concrete. We start with a very simple generic function that takes as arguments any tupe that can be turned into a reference to a string.

pub fn strlen(s: impl AsRef<str>) -> usize {
    s.as_ref().len()
}

Another way to write the above function is as follows.

pub fn strlen2<S>(s: S) -> usize
where
    S: AsRef<str>,
{
    s.as_ref().len()
}

Although the above two functions are not exactly the same, they do the same thing, and for the purposes of this post, one can imagine them to be the same thing.

Now what happens when call this function. As shown below, we see that the function is generic. It does not just accept a string reference, it accepts any type that can be turned into a string reference. The String type implements AsRef<str>, as if you have a String you trivially have a reference to a reference to a str (as the internal representation of a String quite literally is a reference to a str). Here we immediately see why generics are useful, we can use the function in a more ergonomic way.

pub fn foo() {
    strlen("Zinedine Zidane"); // Arguments with type &'static str
    strlen(String::from("Lionel Messi")); // Arguments with type String
}

Behind the scenes, the compiler actually generates two copies of the strlen function. One for when the argument is a &str and one for when the argument is a String -- into something like this

pub fn strlen_refstr(s: &str) -> usize{
    s.len()
}

pub fn strlen_string(s: String) -> usize{
    s.len()
}

To see this for real we can do the following

That is each type T with which we invoke strlen(T) gets its own unique function. This process of writing one generic function, and the compiler turning that function into many individual functions is monomorphisation. This process is not restricted to just generic functions, but also happens for generic types. If one were to write some hashmap with generic types, and then later invoke the hashmap with concrete implementations of said generic types, the compiler would create unique structs for combination of types.

As we saw in the assembly output, the compiler does not create a unique function for any possible type, but rather all the types it sees during compilation. In the above example, foo used two different concrete types, and hence we see two different implementations of strlen

This is also why it is somewhat hard to compile rust code and ship binaries that they can use as a library. The contract is that the rust compiler generates a unique function signature for each type with which we call strlen. But the user that uses the library may end up using a type that is not defined in the library source. Therefore we need the original source code to generate all instances.

Monomorphisation is great because we may end up with very efficient code.

Hashmap with key as string and key being number. Compiler would inline the definition of the hashing function for each key type. This allows for optimisations to the function -- having one generic implementation would prevent this. Expand on this more. 10:10 time stamp is where this stops.

Static Dispatch

Let's define our own trait

pub trait Hei{
    pub fn hei(&self);
}

Let's go ahead and implement this trait for &str

impl Hei for &str {
    fn hei(&self) {
        println!("Hi {}", self);
    }
}

** NEEDS RE-WRITE** When the compiler tries to generate this code - it first determines the type of "J", which is a reference to str, it looks at which methods are available for the str ref, it cannot find hei, then it looks at the traits in scope, finds Hei and sees that &str implements Hei, and therefore calls the hei method described in the implementation.

Now lets imagine a generic version.

pub fn bar(h: impl Hei){
    h.hei()
}

Now this is trickier. When the compiler generates machine code for this -- it does not know the type of h. It just knows that it implements the trait Hei.

Let's say we had some function

pub fn foo_again() {
    bar("J");
}

In the monomorphisation world when we call bar("J"), the compiler can see the argument is a &'static str and it will generate a concrete version of bar, something like bar_str(h: &str)

pub fn bar_str(h: &str){
    h.hei()
}

The compiler sees that h is a reference to a str, so it knows exactly which hei to call -- the hei we wrote when we implemented Hei for &str This is known as static dispatch, at compile time the compiler knows what the actual type of h in the function bar is.

Dynamic Dispatch

What is the alternative? What if we did not want the compiler to generate these concrete function signatures for each type that implemented Hei.

As an example say I had wanted vector of things that implemented Hei. Now traditionally Rust requires that all elements of a vector have the same type -- more concretely say I wanted a function bar_again

pub fn bar_again<H: Hei>(h_slice: &[H]) {
    for h in h_slice {
        h.hei();
    }
}

impl Hei for String {
    fn hei(&self) {
        println!("Hi {}", self);
    }
}

pub fn foo_again_and_again() {
    bar_again(&["Messi", "Ronaldo"]); // This works fine
    bar_again(&[String::from("Messi"), String::from("Ronaldo")]); // This works fine
    bar_again(&["Messi", String::from("Ronaldo")]); // The compiler will complain
}

Firstly it complains because we are not allowed to have a vector with different types. But more importantly, the way we wrote bar_again we said it would take as input a slice with elements of the type H such that H implements Hei. More specifically, it says the arguments are of a single type H -- this type can be &str or String, either is fine as they both implement Hei, but we can only substitute H with one of them.

But what I wanted to write was a function bar_again where I did not care what the concrete type of my argument was. I just want that they are a type that implements Hei. In other words, I want this line of code to not throw an error.

bar_again(&["Messi", String::from("Ronaldo")]); // Want this to be O.K

This is where we get in the business of dynamic dispatch and trait objects. The book has a chapter on this -- they use the Gui draw example where we want an iterator of things that is drawable. TODO: clean up

What I want is something like this

pub fn bar_again(&[dyn Hei]){
    // same code
}

We use this dyn keyword to tell the compiler, forget about the concrete type of the argument (aka type erasure), all I want is that it implements the Hei trait. Unfortunately, this does not compile. You can try it here.

We now spend a significant portion of this post understanding why we get this error, and what it means. And how do we fix the error, and get what we are after.

To get what we are after, we must first understand the Sized trait.

Sized Trait

The size trait has no methods. It is a marker trait. The description says types with a constant size known at compile time. Most types in the std library are sized. There are very types that are not sized. In fact sized types are so common, that when we write

struct Foo<T>(T);

the compiler implicitly makes T sized, so it just re-writes it as

struct Foo<T: Sized>(T);

We must explicitly tell the compiler a type is not sized by writing

struct Foo<T: ?Sized>(T);

Two examples of types that are not sized are [u8] and str. Note these are not references to slices, but the slice themselves. To understand why most types implement the Sized trait, let's revisit the strlen function we wrote.

pub fn strlen<S: AsRef<str>>(s: S) -> usize {
    s.as_ref().len()
}

When a function calls str_len. strlen takes an argument, so the caller must pass in an argument to strlen. This argument is passed to the strlen either by putting in on the processes stack or via a register. Either ways to do this, the compiler must know exactly how much space the argument takes, so it can see if it fits into a register or so it call allocate the correct amount of space on the stack, for strlen to read off. If this argument is a type that is not Sized there is no way for the compiler to allocate the right amount of space, and we cannot pass an argument to strlen.

As an example, in monomorphisation, when the compiler generated

pub fn strlen_str(s: String) -> usize {
    s.as_ref().len()
}

Here s is of type String which is really two numbers and a pointer.

  • Length of the string,
  • Size of allocated memory,
  • and a pointer to the memory location where the first character of the string is stored.

All 3 of these things have fixed sized -- they are 3 usize worth of space. So the compiler creates 3 words of space on the stack when calling strlen_str.

So what was our issue with &[dyn Hei] ? Well we are saying any type that implements Hei is fair game as an argument. Well we do not know the size of this any type. What if we define some type FooFoo that implements Hei but requires are Gigabyte of space? How does the compiler know how much space to allocate on the stack when it generates the assembly code for our library, which exposes the bar_again function. Even if we had something like this

fn strlen2(s: dyn AsRef<str>) -> usize {
    s.as_ref().len()

This would still not work, as we do not know how much space to allocate on the stack.

Now how do we make dyn Hei sized? Well we can use a pointer.

pub fn bar_again(&[&dyn Hei]){
}

or

pub fn bar_again(&[Box<dyn Hei>]){
}

Making Things Sized Via Pointers

Pointers are always fixed size -- as they are just pointers. The reason the above code works and passes is if you look at the definition of Box here, we see that Box does not require the type it is pointing to, to have fixed size.

pub struct Box<T: ?Sized>{/*Things*/}

This compiles. You can try in here.

pub fn dyn_bar_again(h_slice: &[Box<dyn Hei>]) {
    for h in h_slice {
        h.hei();
    }
}

So does this. You can try in here.

pub fn dyn_strlen(s: Box<dyn AsRef<str>>) -> usize {
    // *s turns Box<dyn AsRef<str>> → dyn AsRef<str> (owned)
    // s.as_ref().as_ref().len() will also work as Box can be de-referenced too.
    (*s).as_ref().len()
}

pub fn bar_bar() {
    let x = Box::new(String::from("Lionel Mess"));
    let y: Box<dyn AsRef<str>> = x; // Type erasure; this is a trait object. 
    dyn_strlen(y);
}

Note in both cases h and y are just pointers to something on the heap. The thing on the heap which implements the traits Hei and AsRef<str> respectively, may or may not be sized, we will never know, but the compiler does not care. It can create one Box pointers worth of space on the stack.

Note that once we convert x which is a pointer to a concrete type i.e. String to a trait object y which is a pointer to dyn AsRef<str>, the only identity that y has is that it implements Hei; it has lost all of the original properties of String. Furthermore, there is no safe way of going back from dyn AsRef<str> to String. In other words, we have erased the type of x.

Going Back To Thinking About Machine Code

We go back to the original problem which we successfully resolved.

pub fn dyn_bar_again(h_slice: &[Box<dyn Hei>]) {
    for h in h_slice {
        h.hei();
    }
}


pub fn foo_again_and_again() {
    bar_again(&["Messi", "Ronaldo"]); // This works fine
    bar_again(&[String::from("Messi"), String::from("Ronaldo")]); // This works fine

    //bar_again(&["Messi", String::from("Ronaldo")]); // The compiler will complain
    let x: Box<dyn Hei> = Box::new("Messi");
    let y: Box<dyn Hei> = Box::new(String::from("Ronaldo"));
    dyn_bar_again(&[x, y]); // It WORKS!!!
}

We know this compiles and things work as expected But how? How does the compiler know which hei() to call? There is no monomorphisation going on anymore. When the compiler looks at the arguments to dyn_bar_again it just sees types that are Box<dyn Hei>. So how do we find the unique hei() methods of &str and String now?

Enter Virtual Dispatch Tables

Put more concretely we have the following two scenarios.

pub fn say_hei_static<H: Hei>(s: H){
    // things 
}

pub fn say_hei(s: &dyn Hei){

}

In the static scenario, we know that the compiler will create say_hei_static_concrete_type for whatever type s we invoke this function with. But in the second case of say_hei the type is just a pointer to a dyn Hei -- that is the type.

This is where we get into virtual dispatch tables or simply, V-tables. Earlier we said that Box<dyn Hei> was just a pointer to a type that implements Hei. But that is strictly not true. It is what we call a fat pointer to a type that implements Hei. The rust book has chapter on Dynamically sized types and the sized trait in the advanced section. But it does not go into as much detail as we'd like. TODO: put in reference docs from 53:21

What we mean by a fat pointer is the following: &dyn Hei

  1. Pointer to type
  2. Pointer to a vtable

So what is a vtable? dyn Hei, vtable: struct HeiVtable{ hei: *mut Fn(*mut ()), // whatever the T is. }

So a different VTable gets created for each concrete type that gets converted into a trait object.

// &str -> &dyn Hei
// 1. A pointer to &str
// 2. Pointer to &HeiVtable{
//      hei: &<str as Hei>::hei // address of the hei function of &str 
//    }
s.hei() // becomes s.vtable.hei(s.pointer_one)

Why Not To Dynamic Dispatch

A few reasons why trait objects are more constrained than full generics. Consider the following example:

Combining Traits


// This won't compile. 
// why -- cos for this type we need the Vtable for the concrete type that's converted
// both where the hei and as_ref method -- one is the vtable for hei and one is the vtable for 
// as_ref 
// so we will need 3 wide pointer - data and 2 Vtables. 
// this is possible but Rust doesn't allow it
pub fn baz(s: &dyn (Hei + AsRef<str>)){

    s.hei();
    println!("Len {}", s.as_ref().len());

}

But I do not need to do this mallarkey as I can simply just do this

pub trait HeiAsRef: Hei + AsRef<str> {}

pub fn baz(s: &dyn HeiAsRef){
    // code
}

Now for this each type that implements this trait, we get one Vtable. So when this type gets made into a trait object, we just point to 1 VTable, and my fat pointer remains of width two.

Second Limitation: Associated Types

Let's change things

pub trait Hei {
    type Name;
    fn hei(&self);
}

impl Hei for &str {
    type Name = ();
    fn hei(&self) {
        println!("Hi {}", self);
    }
}

impl Hei for String {
    type Name = ();
    fn hei(&self) {
        println!("Hi {}", self);
    }
}

pub fn dyn_bar_again(h_slice: &[Box<dyn Hei>]) { // <-- This complains 
    for h in h_slice {
        h.hei();
    }
}
Diagnostics:
1. the value of the associated type `Name` in `Hei` must be specified [E0191]
2. specify the associated type: `Hei<Name = Type>` [E0191]

The issue: I can't just pass any dyn Hei regardless of the associated type Name. I need to pass the associated type, and once I do, for that fixed associated type, we have a trait object that implements Hei with the associated type locked in.

pub fn dyn_bar_again(h_slice: &[Box<dyn Hei<Name = ()>>]) {
    for h in h_slice {
        h.hei();
    }
}

Object Safety

Here's a complete list of all the conditions that must be met for a trait to be made into a trait object. We go over most of them.

All methods must have a receiver


pub trait Hei {
    fn hei(&self);
    fn weird() {}
}

This also does not compile. The error says Hei is not object safe.

It gives two suggestions :

  • help: consider turning weird into a method by giving it a &self argument
  • help: alternatively, consider constraining weird so it does not apply to trait objects

But what does this mean? Weird does not take a pointer to self -- so how do we call weird?

pub fn say_hei(s: &dyn Hei){
    (dyn Hei)::weird() // 
}

Well the way trait objects resolve function location is by looking at VTables for the concrete type implementing the trait. Weird is part of no Vtable. You might think that weird is a single default implementation so it's fine -- just have all the Vtables include the location of weird. However what happens when one of the specific implementations overrides this weird. What do we do then?

As weird does not take self as a parameter, there is no way to tell from (dyn Hei)::weird() which weird() function to call? But what if you really wanted weird? That is you wanted Hei to be trait object safe, but for concrete types that implement Hei and are NOT converted into a Hei trait object, I want to be able to call weird

pub trait Hei where Self::Sized { 
    fn hei(&self);
    fn weird() where Self::Sized {} // Opt out
    fn weird_again(&self) where Self::Sized {} // Opt out
}

pub trait Hei where Self::Sized { // make Trait not object safe
    fn hei(&self);
    fn weird() where Self::Sized {} 
    fn weird_again(&self) where Self::Sized {} 
}

So when something that implements Hei is made into a trait object, that object will not have the ability to call weird and weird_again

Methods Cannot Be Generic

For a trait to be object safe, its methods cannot contain generics. Let's look at the trait Extend

pub trait Extend<A> {
    // Required method
    fn extend<T>(&mut self, iter: T) // Generic T is the type of iterator
       where T: IntoIterator<Item = A>; // A is the type we are iterating over

    // Provided methods
    fn extend_one(&mut self, item: A) { ... }
    fn extend_reserve(&mut self, additional: usize) { ... }
}
}

Let's see what happens when we run this code.

use std::iter::Extend;

pub fn add_true(v: &mut dyn Extend<bool>){
    
    v.extend(std::iter::once(true));
}

Try Here On Playground

error[E0038]: the trait `Extend` is not dyn compatible

It does not compile. Why? Even though we fix A with bool. From monomorphisation we know that for every type of iterator T, we get a different extend_T. So what gets put in the Vtable ? The type of the function does not describe which iterator to use. Nothing in the function declaration of add_true says to use the extend implemenation for std:iter::once. Specifically when we initialise Extend concretly with A=bool to make a concrete type, and then try to make this into a trait object, there are numerous ways to call the extend method for this trait object. Nothing tells us which iterator to use when going from a type that implements Extend<bool> to the trait object &dyn Extend<bool>.

Trait Cannot Have A Function That Returns Self

Let's consider the following example.

fn clone(v: &dyn Clone)}
    // fn clone(&self) -> Self 
    let x = v.clone();
}

The reason is simple. Trait objects like dyn Clone are not sized -- That's why we had to hide them behind pointers like &dyn Clone. The return type of clone is Self. Not a pointer to self but Self itself. Return values are put on the stack. Thus, the compiler must know the size of the return value. Self here is dyn Clone (as we have erased the concrete type by making a trait object), and dyn Clone is not sized. The compiler will throw an error.
