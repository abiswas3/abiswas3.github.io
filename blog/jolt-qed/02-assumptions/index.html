    The Jolt-qed project verifies, in Lean, that each Jolt bytecode expansion has the same effect as the RISC-V instruction it replaces. These equivalence theorems are not unconditional: they rely on explicit hypotheses about the RISC-V/Jolt state, plus a small number of trusted edits to the generated RISC-V model so that it matches the Jolt CPU. This post records those proof assumptions and trusted-code changes.

    Changes to the Trusted RISC-V Model

    The Lean RISC-V model lives in LeanRV64D/, with the top-level entry point in LeanRV64D.lean. It was generated by automatically transpiling the Sail specification of a RISC-V CPU to Lean[1]. The Sail-to-Lean post explains how we obtained this generated code. We treat that generated model as trusted throughout the project, except for the two changes below.

    1. We say that the RISC-V CPU should not support misaligned memory addressing. We do this because Jolt does not support misaligned addressing, and it would be impossible to prove equivalence otherwise. The Ethereum zkVM Standards v0 recommend that zk-VMs use RV64IM+Zicclsm as the target baseline, where Zicclsm is included to support misaligned loads and stores. We highlight this drawback off the bat.
    -- WARNING: CHANGE IN TRANSPILED CODE
def plat_enable_misaligned_access : Bool := false
    1. Jolt does not support the Zicfiss and Zicfilp extensions. Leaving them on makes it impossible to prove equivalences about writing to control status registers.
    -- WARNING: (change to sail, Jolt does not support Zicfilp extension).
| Ext_Zicfilp => false
-- WARNING: (change to sail, Jolt does not support Zicfiss extension).
| Ext_Zicfiss => false

    These are the only changes we make to the generated RISC-V model.

    Equivalence Statement Structure

    Shown below is the equivalence statement for the sra instruction. It says that running the Jolt instruction sraProgram with arguments rd rs2 rs1 on the current Jolt state js, and then projecting down to the RISC-V state, is identical to running sra rd rs2 rs1 on the RISC-V state of the current Jolt CPU. In simple words, we could either run the original RISC-V instruction or run the Jolt expansion on the same starting state, and the effect is the same. If we showed this for all RISC-V instructions, then we would show that Jolt faithfully simulates RISC-V. Now to prove this theorem, we use an assumption bundle. The goal of this post is to explain what an assumption bundle is.

     1/-- Main program-level equivalence for `SRA`. -/
 2def sraProgramEqSailStatement
 3    (rs2 : regidx)
 4    (rs1 : regidx)
 5    (rd : regidx)
 6    (js : SailJoltState)
 7    (_h : BinarySourceReadWithLinkedCSRs rs2 rs1 js) -- <--- Assumption bundle
 8  : Prop :=
 9  System.systemProjectResult
10      ((JoltISA.execProgram (JoltISA.sraProgram rs2 rs1 rd)).run js) =
11    (execute_RTYPE rs2 rs1 rd rop.SRA).run js.sail

    Assumption bundles are conjunctions of assumptions defined in JoltBytecode/Assumptions.lean and collected in JoltBytecode/Bundles.lean. Each equivalence statement in Jolt-qed uses an assumption bundle. Bundles describe exactly which assumptions were used to prove equivalence for a given instruction. An assumption bundle is always made up of a list of assumptions[2].

    This specific assumption bundle is made up of the two groups of assumptions shown below.

    abbrev BinarySourceReadAssumptions
    (rs2 rs1 : regidx) (js : SailJoltState) :=
  Assumptions.BinarySourceReadAssumptions rs2 rs1 js.sail

private structure LinkedCSRRegisterAssumptions (js : SailJoltState) where
  mstatus_matches : Assumptions.MstatusVRegMatchesSail js
  mtvec_matches : Assumptions.MtvecVRegMatchesSail js
  mscratch_matches : Assumptions.MscratchVRegMatchesSail js
  mepc_matches : Assumptions.MepcVRegMatchesSail js
  mcause_matches : Assumptions.McauseVRegMatchesSail js
  mtval_matches : Assumptions.MtvalVRegMatchesSail js

    We will explain what these mean below, but the takeaway message is that every equivalence theorem uses an assumption bundle. Any assumption bundle can only be made up of core assumptions listed in Assumptions.lean.

    Bytecode Expansion Assumptions

    For the rest of the document, we list every assumption used in Jolt. If any assumption that is not listed here, or in Assumptions.lean, is used in a proof bundle, then that should be remedied immediately, and we should check whether the assumption is justified.

    Privilege Is Always Machine

    structure CurPrivilegeMachine (s : SailState) : Prop where
  value : s.regs.get? Register.cur_privilege =
    some (Privilege.Machine : RegisterType Register.cur_privilege)

    In simple English, the value in current_privilege indicates that the Jolt CPU runs in machine mode all the time. According to the Jolt Rust code base, Jolt always runs in machine mode. The above Lean code simply states that the value in the cur_privilege register is Privilege.Machine.

    MPP Bit Set To Machine

    structure MstatusMppMachine (js : SailJoltState) : Prop where
  value_eq :
    _get_Mstatus_MPP (js.vregs JoltISA.mstatusVReg) =
      privLevel_to_bits Privilege.Machine

    Jolt uses virtual register 39 to model the mstatus control status register of the Jolt CPU. Based on the Jolt source code, Jolt always runs in machine mode, and the MPP bit of the status register is always set to Machine.

    MISA User Enabled

    structure MisaUserEnabled (s : SailState) : Prop where
  exists_value : ∃ misa : BitVec 64,
    s.regs.get? Register.misa = some (misa : RegisterType Register.misa) ∧
    _get_Misa_U misa = 1#1

    Jolt initialises misa to 0x800000008014312f based on jolt/tracer/src/emulator/cpu.rs:399. The function _get_Misa_U reads bit 20 of the misa CSR, which, based on the written value, is 1. According to the RISC-V ISA, having bit 20 set to 1 implies user mode is enabled.

    MPRV Bit

    structure MstatusMprvZero (s : SailState) : Prop where
  value : ∃ mval : RegisterType Register.mstatus,
    s.regs.get? Register.mstatus = some mval ∧
    _get_Mstatus_MPRV mval = 0#1

    According to Jolt, the MPRV bit of the mstatus register is set to 0 in Jolt. As a direct consequence of this, we get bare translation: virtual addresses are the same as physical addresses, which is also true in the Jolt code base. In Lean, this is captured by the following three bare-translation theorems for loads, stores, and atomics. We only show the theorem statements here; the proofs are in JoltBytecode/InstructionEquivalence/ProofSupport/BundleLemmas.lean.

    Mtvec

    structure MtvecWriteDirectMode (value : BitVec 64) : Prop where
  mode_eq : _get_Mtvec_Mode value = 0b00#2

    The RISC-V ISA requires that we legalise values before writing to control and status registers. See this post for more details. When writing the contents of rs1 into the mtvec control and status register, if the value in rs1 has the two least significant bits set to 00, then we write rs1’s contents directly into mtvec. Otherwise, we need to legalise the value. The above assumption says the value in rs1 will always have the lower two bits set to 00.

    The ZeroOS/Jolt boot path writes _trap_handler to mtvec with

    csrw mtvec, t0

    ZeroOS defines _trap_handler under .align 2, which gives 4-byte alignment, so the lower two bits are 00. Evidence from ZeroOS source code is given below.

    The ZeroOS boot code writes to mtvec, and the trap handler definition is aligned.

    Warning

    This assumption holds when we use the write to mtvec operation as it is meant to be used in Jolt. If a malicious program were to write a different value to Jolt mtvec, Jolt does not have any mechanism to legalise the value. In that case, Jolt would not be following the RISC-V spec. We will rely on the proof mechanism to catch this.

    Align PC

    Jolt supports compressed instructions (+c / RV64IMAC), as seen here, so we can only guarantee that the least significant bit of PC is 0. The relevant assumption is that mepc[0] = 0. Thus, the legalisation operation according to the specification is a no-op because the lowest bit is already cleared.

    structure MepcReadAligned (value : BitVec 64) (s : SailState) : Prop where
  value_eq : align_pc value s = .ok value s

    This is the write-side counterpart of MepcReadAligned: CSRRW writes the new rs1 value, so the assumption must be about that source value rather than only the old stored mepc.

    structure MepcWriteLegalized (value : BitVec 64) : Prop where
  value_eq : legalize_xepc value = value

    Legalise MStatus

    structure MstatusWriteLegalized
    (old value : BitVec 64) (s : SailState) : Prop where
  value_eq : legalize_mstatus old value s = .ok value s

    Jolt does not legalise before writing to mstatus. The evidence is in the Jolt CSR expansions: CSRRW writes rs1 directly into the CSR virtual register, and CSRRS writes the OR of the old CSR value and rs1. See csrrw.rs and csrrs.rs.

We could have written directly to the Sail registers in our Jolt semantics, but to be faithful to the Jolt expansion, we write the virtual registers and record that correspondence as an assumption. The Jolt code confirms this.

    Memory Assumptions

    structure DwordPresent (addr : BitVec 64) (s : SailState) : Prop where
  bytes :
    ∃ bytes : Fin 8 → BitVec 8,
      ∀ k : Fin 8, s.mem.get? (addr.toNat + k.val) = some (bytes k)

    Lean models memory as a hash map from natural numbers to 8-bit bitstrings. The natural numbers are countably infinite, while the address space of any CPU is not. Additionally, because memory is modelled as a hash map, Lean needs a hypothesis that the key already exists before it can retrieve the value. This is a proof-engineering issue: the generated model represents memory as a partial map, so we must state that the relevant bytes are present. Thus, the following assumption says that addresses can be read from memory and that they return valid bytes across the entire doubleword window.

    abbrev LoadPmpOk (addr : BitVec 64) (width : Nat) (s : SailState) : Prop :=

    (physaddr.Physaddr addr) width false s = .ok none s

    Jolt’s Rust MMU explicitly says memory protection is not implemented. These predicates constrain the generated RISC-V model to the corresponding no-PMP-fault path.

    Rust source: https://github.com/abiswas3/jolt/blob/main/tracer/src/emulator/mmu.rs#L17.

    The above assumption says the entire doubleword block read by LD at physical address addr is not protected and can be read. The same applies to writing to memory. To prove equivalence, we need to tell the generated RISC-V model that the address is safe to read from or write to. The generated RISC-V model uses different checks for LD, SD, and atomic operations, so we need three sets of assumptions that say the same thing.

    abbrev NotReadableMmio (addr : BitVec 64) (width : Nat) (s : SailState) : Prop :=
  within_mmio_readable (physaddr.Physaddr addr) width s = .ok false s

structure NotReadableMmioWindow
    (base : BitVec 64) (width : Nat) (s : SailState) : Prop where
  ok :
    ∀ offset accessWidth : Nat, offset + accessWidth ≤ width →
      NotReadableMmio (base + BitVec.ofNat 64 offset) accessWidth s

abbrev NotWritableMmio (addr : BitVec 64) (width : Nat) (s : SailState) : Prop :=
  within_mmio_writable (physaddr.Physaddr addr) width s = .ok false s

/-- Every explicit sub-store inside a memory window avoids writable MMIO. -/
structure NotWritableMmioWindow
    (base : BitVec 64) (width : Nat) (s : SailState) : Prop where
  ok :
    ∀ offset accessWidth : Nat, offset + accessWidth ≤ width →
      NotWritableMmio (base + BitVec.ofNat 64 offset) accessWidth s

    Rust source: tracer/src/emulator/mmu.rs:139-213.

    Jolt splits VM memory into reserved low-memory regions for advice, inputs, outputs, panic, and termination, followed by ordinary RAM. These regions share one VM address space and are mapped into the memory witness layout. Ordinary RAM is backed by the emulator memory map, while advice/input/output are modelled by JoltDevice.

    Jolt does not support device MMIO such as UART, CLINT, PLIC, or disk; accesses to those ranges panic in the tracer. On the generated RISC-V side, memory operations can branch on memory-mapped device addresses, so the proof needs assumptions such as NotReadableMmio and NotWritableMmio to keep execution on the ordinary/Jolt-supported memory path.

    Jolt Constraint Assumptions

    The assumptions below are the assumptions used for proving completeness and soundness of the Jolt constraint system. Note, all the above assumptions described in the bytecode expansion process still apply. Without them, we do not get the RISC-V simulation claim.

    Completeness Assumptions

    We only have a single assumption that the completeness statement currently takes. It simply says the guest program is not empty.

    The assumption states that the program’s memory_init is not empty: the ELF loads at least one byte into memory.

    Soundness Assumptions

    Soundness is trickier. It uses one assumption and six temporary assumptions. We say temporary because, they are currently used to show that the Jolt constraint system is sound by we are not sure if every one of these assumptions is justified yet.

    The assumption says that every load or store used in the program, reads/writes to an effective address that fits in the address space.

    In Jolt the memory layout is given by the following rust structure.

pub fn compute_max_ram_k(memory_layout: &MemoryLayout) -> Result<usize, RamDomainError> {
    let lowest_address = memory_layout.get_lowest_address();
    let total_bytes = memory_layout.heap_end.checked_sub(lowest_address).ok_or(
        RamDomainError::HeapBelowLowest {
            heap_end: memory_layout.heap_end,
            lowest_address,
        },
    )?;
    let total_words =
        usize::try_from(total_bytes.div_ceil(8)).map_err(|_| RamDomainError::DomainTooLarge)?;
    total_words
        .checked_next_power_of_two()
        .ok_or(RamDomainError::DomainTooLarge)
}

    The verifier has access to this layout, and compute the largest legal address that can be read or written to. The verifier performs this computation using compute_max_ram_k(layout)shown above.

    — Assumption On Maxmimum Addressable Memory

    Let $m$ denote the output of compute_max_ram_k, and let $\ell$ denote the smallest address in the memory layout. The assumption states that $\ell + 8m \le 2^{64}$

    def JoltInstance.RamRegionFits {Source : Type} (joltInstance : JoltInstance Source) : Prop :=

    The Claim Says No Panic

    A Jolt claim says, loosely, that program prog on input in produces output out, and either panicked or did not. We restrict our formal guarantees only to claims where the prover claims the program did not panic.

    def JoltInstance.ClaimsNoPanic (joltInstance : JoltInstance SourceInstruction) : Prop :=
  joltInstance.panic = false

    In other words, if the provers’ claims was

    running prog on input in produces output out and the program panics i.e. panic region of memory is set to 1.

    This claim may or may not be true, but our soundness theorem provides no guarantees of soundness. This might seem egregious, and it is why such an assumption is a temporary restriction. On the other hand if the prover ever claims that the program does not panic, then we show that prover cannot lie without getting caught (assuming all other assumptions listed in this document hold)

    It is important to note that this split only exists in the world of Lean proofs.

    Jolt’s verifier runs verification algorithm for both types of claims. However, when the prover claims the program panicked, under the current constraint system we are able to find a proof that the verifier accepts but the provers’ claim is a lie. More simply the prover can cheat i.e. Jolt is not sound. The reason the prover can cheat for one claim, but not for other has little to do with the constraint system, and everything to do with another temporary assumption - Termination Then Stall. Loosely, we will show that Jolt prover can lie about when a program ends (it could claim a program ends before it actually ends). Under the termination then stall assumption, it cannot lie if it claims the program did not panic. When it claims that the program did panic, there is nothing that termination then stall assumption can do for us.

    Stores to the Panic Region Write 1

    Before describing the assumption, we give much needed context. Jolt partitions its memory into regions - (1) the device (2) ordinary RAM, where the stack, bytecode, heap and usable memory live.

    The device is further partitioned into regions, where each region has special meaning. The following picture illustrates a subset of the regions in the Jolt device. It shows the termination and panic region. When a program panics, the Jolt tracer writes 1 to the panic region. When a program terminates, it also writes 1 to the termination region before exiting.

    The core source of the grief is caused by the following issue.

    1. reading and writing to this region works slightly differently in the tracer than when writing to “normal” regions of memory.

    2. But the Jolt constraints treat this region as regular memory. There is no special constraint for these regions.

    In more detail, if the guest program has a store that writes to the panic region or the termination region, the store never updates memory, as depicted by the code snippet in Jolt. Furthermore, loading from that region does not return contents of memory, but rather returns the contents of the tracers panic flag.

    impl JoltDevice {

      | .VirtualLoadB _ _ base imm _ | .VirtualLoadH _ _ base imm _ | .VirtualLoadW _ _ base imm _ =>
          (∃ i, run.StoresPanicAt i) →
            ¬ JoltConstraints.Soundness.TouchesPanic pre.jolt_device
              ((JoltISA.sourceValue base pre + imm) &&& ~~~7)
      | _ => True
     address:  panic  panic+1  ...  panic+7
          +------+-------+-----+-------+
          |  b0  |  b1   | ... |  b7   |   the panic region: one doubleword
          +------+-------+-----+-------+

    Jolt’s constraints treat the region as ordinary memory, and the verifier checks that its final value equals the claimed panic bit. So if a program stores 0 there, the tracer says it panicked, but the constraints accept a “no panic” claim.

    The restriction states that, for every untrusted advice and runtime advice, every store to the panic region writes 1, and no load reads the region after such a store. Our theorems provide no guarantee about programs that store any other value there, or read it back after a store. A program built with Jolt’s SDK meets the restriction if its own code never writes to the panic region: the SDK’s only store there writes 1, and the program then stops.

    Jolt’s tracer allows a store of any value to the panic and termination regions; Jolt’s SDK stores 1. A store of a value v there affects three things: the tracer’s panic flag, the witness, and the tracer’s emulated memory, which later loads read.

    Store of v to the termination regionStore of v to the panic region
    Tracer’s panic flag, the boolean JoltDevice.panicThe tracer leaves the flag unchanged.If the store writes the byte at address panic, the tracer sets the flag to true, whatever v is.
    WitnessFrom that cycle on, the witness’s memory cell for the termination region holds v.From that cycle on, the witness’s memory cell for the panic region holds v.
    Emulated memoryThe tracer discards the store.The tracer discards the store.
    A later load from the regionThe load reads 0 in every byte.The load reads the flag in every byte: 1 once the flag is true.

    The panic flag is internal to the tracer; no witness polynomial holds it. So after a store, the witness and the emulated memory disagree on both regions: the witness holds v, while a load reads 0, or 1 in every byte.

    Without the ban on loads, a false “panicked” claim could pass when the program reads the panic region back and acts on the value:

            sb   t0, 0(s0)     # panic := 1        (t0 = 1)
        ld   t1, 0(s0)     # read the panic doubleword back
        beq  t1, t0, one   # branch on what was read
        ...                # output := 9
one:    ...                # output := 7
    The load returnsBranchFinal output
    Witness, from its RAM cell1taken7
    Jolt’s tracer, from the panic flag0x0101_0101_0101_0101not taken9

    The witness satisfies every constraint, so the verifier accepts “panicked, output 7”, but the real run ends with output 9.

    For a “no panic” claim this cannot happen: a store to the panic region must write 1, which leaves the panic doubleword at 1, but the claim requires 0. So no accepted “no panic” witness contains a panic store, and the load ban matters only for “panicked” claims, which claimsNoPanic already excludes.

    No Maximum-Length Trace

    The guest program’s developer sets a maximum trace length T' in the program’s attribute, #[jolt::provable(max_trace_length = T')]; if they don’t, T' = 2^24. Jolt passes T' unchanged into the program preprocessing, as the field max_padded_trace_length:

    pub struct JoltProgramPreprocessing {
    pub bytecode: BytecodePreprocessing,
    pub ram: RAMPreprocessing,
    pub memory_layout: MemoryLayout,
    pub max_padded_trace_length: usize,
}

    Let T be the true trace length: the number of instructions the run executes. Jolt’s prover pads the trace to T_1 = max(next_pow2(T + 1), 256) cycles, a power of two with at least one padding row, so T_1 ≥ T + 1 (ProverConfig::derive_from_dimensions). The prover proceeds only if T_1 ≤ T'. The length Jolt’s verifier checks is the trace length written in the proof; call it T_2.

    • T_2 is proof.trace_length, a number the prover puts in the proof. The verifier reads it with let trace_length = proof.trace_length; in validate_inputs, crates/jolt-verifier/src/verifier.rs.
    • It is the number of cycles in the committed witness. Every per-cycle witness polynomial has one value per cycle t < T_2. In Lean it is WitnessParams.traceLength.
    • The verifier checks it with validate_trace_length: T_2 must be a power of two between 256 and T'.
    • An honest prover sets T_2 = T_1. A cheating prover can put any T_2 in the proof, and only that check limits it.

    validate_inputs reads the length from the proof, then checks it:

    pub fn validate_inputs<PCS, VC, ZkProof>(
    preprocessing: &JoltVerifierPreprocessing<PCS, VC>,
    public_io: &JoltDevice,
    proof: &JoltProof<PCS, VC, ZkProof>,
    trusted_advice_commitment_present: bool,
) -> Result<CheckedInputs, VerifierError>
where
    PCS: CommitmentScheme,
    VC: VectorCommitment<Field = PCS::Field>,
{
    let trace_length = proof.trace_length;
    let ram_k = proof.ram_K;
    let trace_polynomial_order = proof.trace_polynomial_order;
    // ...
    validate_trace_length(trace_length, program.max_padded_trace_length())?;

    The check itself, where MIN_PADDED_TRACE_LENGTH is 256 in the base build (crates/jolt-verifier/src/config.rs):

    fn validate_trace_length(
    trace_length: usize,
    max_padded_trace_length: usize,
) -> Result<(), VerifierError> {
    if !trace_length.is_power_of_two()
        || trace_length < MIN_PADDED_TRACE_LENGTH
        || trace_length > max_padded_trace_length
    {
        return Err(VerifierError::InvalidTraceLength {
            got: trace_length,
            min: MIN_PADDED_TRACE_LENGTH,
            max: max_padded_trace_length,
        });
    }
    Ok(())
}

    T' is an upper bound, not a length: for example, with T' = 1500 the largest witness length is 1024, and with T' = 48 no witness length is allowed.

    def JoltInstance.NoMaxLengthTrace
    (joltInstance : JoltInstance SourceInstruction) : Prop :=
  ∀ (privateInputs : JoltPrivateInputs)
    (trace : JoltConstraints.Soundness.UntrustedAnswerTrace joltInstance privateInputs),
    trace.rows.size ≠ 2 ^ Nat.log2 joltInstance.max_padded_trace_length.toNat

    For every untrusted advice and runtime advice, no complete run of the program has T = P, where P = 2^⌊log2 T'⌋.

    On your guess: yes, T = P is an edge case where Jolt’s prover and verifier disagree.

    • The verifier accepts a proof with T_2 = P, where all P rows are real.
    • Jolt’s prover never produces that proof, because it needs T_1 = 2P > T’ and refuses.

    It’s a narrow kind of bad. The run is real and its outputs are correct. What fails is our language L’s condition that Jolt’s prover accepts the run. So the verifier accepts a run that Jolt’s own prover refuses to prove.

    Host Calls Succeed

    A host call is the guest program asking the machine that runs Jolt’s tracer, the host, to do something for it, much like a system call. The guest makes a host call with the Jolt instruction VirtualHostIO.

    VirtualHostIO is a 32-bit I-type instruction in RISC-V’s custom opcode space:

    FieldBitsValue
    opcode6–00x5B (1011011)
    rd11–7x0; Jolt’s decoder rejects any other register
    funct314–122 (010)
    rs119–15ignored; x0 in practice
    imm31–20ignored; 0 in practice

    The guest emits it as .insn i 0x5B, 2, x0, x0, 0, which encodes as 0x0000205B (jolt-platform/src/print.rs).

    Jolt’s tracer executes it in VirtualHostIO::exec (tracer/src/instruction/virtual_host_io.rs):

    let call_id = cpu.x[10] as u32;

if call_id == JOLT_ADVICE_WRITE_CALL_ID {
    let ptr = cpu.x[11] as u64;
    let len = cpu.x[12] as u64;
    let _ = cpu.handle_advice_write(ptr, len);
} else {
    let ptr = cpu.x[11] as u32;
    let len = cpu.x[12] as u32;
    let event = cpu.x[13] as u32;

    if call_id == JOLT_CYCLE_TRACK_CALL_ID {
        let _ = cpu.handle_jolt_cycle_marker(ptr, len, event);
    } else if call_id == JOLT_PRINT_CALL_ID {
        let _ = cpu.handle_jolt_print(ptr, len, event);
    }
}

    Written like ADDI rd, rs1, imm, the instruction is:

    VirtualHostIO x0, x0, 0
  reads:  x10 = call id, x11 = pointer, x12 = length, x13 = event
  writes: no register, no memory
  PC <- PC + 4

    Its fields rd, rs1 and imm are fixed; its inputs are the registers x10 to x13, as ecall reads a7.

    Here are the three things it can do, chosen by the call id in x10:

    1. Print (x10 = 0x505249): print the x12 bytes at address x11 as a string; x13 = 1 prints it, x13 = 2 adds a newline, and any other x13 panics.
    2. Cycle marker (x10 = 0xC7C1E): x13 = 1 starts, and x13 = 2 ends, a cycle counter named by the x12 bytes at address x11; any other x13 panics.
    3. Advice write (x10 = 0xADBABE): copy the x12 bytes at address x11 onto the runtime advice tape; x13 is ignored.

    Any other call id does nothing.

    The call ids are constants in jolt-platform/src (advice.rs, cycle_tracking.rs, print.rs). VirtualHostIO writes no register and no guest memory, and the PC advances by 4. exec ignores an error a handler returns (let _ = ...), but a panic, such as a print with an unknown x13, stops the tracer.

    def JoltInstance.HostCallsSucceed (joltInstance : JoltInstance SourceInstruction) : Prop :=
  ∀ (privateInputs : JoltPrivateInputs)
    (run : JoltConstraints.Soundness.UntrustedAnswerRun joltInstance privateInputs)
    (next : Fin run.bytecode.size) (pre : SailJoltState),
    run.NextStep next pre →
      match run.bytecode[next].instruction with
      | .VirtualHostIO => ∃ post, execHostIO pre = .ok RETIRE_SUCCESS post
      | _ => True

    This assumption assumes that every call to VirtualHostIO the program makes, for every untrusted advice and runtime advice, succeeds.

    The assumption exists because the constraints never check a host call, but Jolt’s tracer can fail on one. Jolt gives VirtualHostIO no circuit flags (jolt_instruction!(VirtualHostIO) in crates/jolt-riscv/src/instructions/virt/host_io.rs) and no lookup table (impl_lookup_table!(VirtualHostIO, None) in crates/jolt-lookup-tables/src/instructions/virt/host_io.rs), and its rd is x0. So on a VirtualHostIO row the constraints check only that the row writes no register, makes no RAM access, and moves the PC to the next instruction. They do not check the call id, the pointer, the length or the event, or whether the call succeeded. The row is still a real row of the trace, not the padding no-op: its IsNoop flag is 0.

    1. Jolt’s tracer can fail on a host call and stop the run: a cycle marker or a print whose x13 is invalid, or a pointer overflow while reading the string.
    2. When it fails, the tracer never completes the run, so no run of the program produces the claim, and the claim is not in L.
    3. A witness, however, can treat the failed call as a row that does nothing and continue to the end, and the verifier accepts it.
    4. So without the assumption, the verifier could accept a claim that no completed run produces, and our soundness theorem would be false.

    The assumption excludes every program where some host call could fail, so this case never arises.
