    Prelude: the role of untrusted advice in Jolt

    Untrusted advice is how prover-private data enters a Jolt proof. The prover places a byte string of its choosing in the guest’s advice region before the program starts. The program reads it like ordinary memory. The verifier never sees the bytes: it sees only a commitment to the advice.

    The claim a proof attests is existential over that private data. Acceptance means: there exist advice bytes and a tape such that the program, run on the public inputs with that private data, produces the claimed output.

    Example: proving knowledge of a secret s whose SHA-256 is d, without revealing s. The guest program reads the advice region, hashes it, and stores the digest as its output. The prover runs it with s in the advice region and claims outputs = d. Acceptance means the program hashed something to d — for SHA-256, that the prover knows a preimage of d. Privacy holds because the advice never enters the claim. Soundness holds because the output must genuinely follow from some byte string.

    The second half of that bargain is what fails here. The commitment the verifier checks is a commitment to field elements, and nothing in Jolt’s constraints forces those elements to be bytes. This report exhibits a proof where the committed advice word is not any byte string — it is the field element 2⁻¹ — and the verifier accepts an output that no advice bytes can produce.

    1. The program and its inputs

    In words: the program reads the first word of the untrusted advice, doubles it, and writes the doubled value as its output. That single doubling is the entire computation.

    The program is eight instructions at 0x80000000.

    auipc x1, 0            # x1 = 0x80000000
addi  x1, x1, -0x80    # x1 = 0x7FFFFF80 = input word address
ld    x5, -0x40(x1)    # x5 = untrusted advice word 0
add   x6, x5, x5       # x6 = 2 · x5
sd    x6, 0x8(x1)      # output word 0 = x6
addi  x11, x0, 1
sb    x11, 0x28(x1)    # termination byte = 1
jal   x0, 0            # stop: the PC repeats

    It runs with

    • max_input_size = 8, inputs = eight zero bytes,
    • max_trusted_advice_size = 64, trusted advice = none (no commitment),
    • max_untrusted_advice_size = 64, untrusted advice = the eight bytes 01 00 00 f8 c9 fa f0 21,
    • max_output_size = 24, and a 4096-byte stack and heap.

    The advice bytes are the little-endian encoding of 0x21F0FAC9F8000001, the low 64 bits of 2⁻¹ in the BN254 scalar field.

    With those sizes the device regions sit directly below RAM_START_ADDRESS:

    trusted advice    [0x7FFFFF00, 0x7FFFFF40)
untrusted advice  [0x7FFFFF40, 0x7FFFFF80)
input             [0x7FFFFF80, 0x7FFFFF88)
output            [0x7FFFFF88, 0x7FFFFFA0)
panic word        0x7FFFFFA0
termination word  0x7FFFFFA8

    The program reads no advice tape, so the tape is empty.

    Running the program on the supplied inputs outputs [2, 0, 0, 240, 147, 245, 225, 67] and does not panic. The output is the double of the advice word: 2 · 0x21F0FAC9F8000001 mod 2^64 = 0x43E1F593F0000002, the little-endian bytes of which are [2, 0, 0, 240, 147, 245, 225, 67]. Instead the Jolt prover generates a proof of the following claim

    Claim

    There exist prover-private inputs — an untrusted advice byte string and an advice tape — such that an honest execution of the program above, on the public inputs and with that private data, terminates without panic and with the device’s output bytes equal to [1, 0, 0, 0, 0, 0, 0, 0] (trailing zeros trimmed).

    2. Generating the cheating witness

    We generate the cheating witness by modifying the honest witness. Jolt’s tracer runs the program on the supplied advice bytes and produces the honest execution: every row, PC, flag and memory access. We keep all of it and change a small set of cells. A witness is an assignment of field elements to the proof’s columns, and no constraint asks where a value came from.

    Everything else in the witness is the honest value: every other row, every other register, every other memory word, the PCs, the flags, the byte-store expansion, the padding.

    The only cell that uses the field wrap is the ADD row’s RightLookupOperand — the row’s lookup query, the sum of its two operands. The honest value is the integer sum A_lo + A_lo = C. The cheating value is the field sum A + A = 1, which wraps at the field characteristic p instead of at 2⁶⁴. Every other changed cell keeps the books consistent with that one substitution.

    3. The constraints that matter pass

    All arithmetic below is in the field F_p. Each constraint is stated in words, then with the cheating values filled in.

    The ADD row, cycle 3.

    On an ADD row, the right lookup operand is the sum of the left and right instruction inputs. RightLookupOperand = LeftInstructionInput + RightInstructionInput 1 = A + A This holds because A = 2⁻¹, so A + A = 1 in the field. With honest operands the sum is the integer A_lo + A_lo = C; the constraint never asks the operands to be 64-bit numbers, so A is admissible.

    The lookup query must select an entry of the range table, whose entry at index i is i mod 2⁶⁴. The ADD row queries index 1, and the entry at index 1 is 1. LookupOutput = 1

    On a row that writes its lookup output to the destination register, the rd write value is the lookup output. RdWriteValue = LookupOutput 1 = 1

    The product of the instruction inputs equals the product column. Product = LeftInstructionInput · RightInstructionInput 4⁻¹ = A · A This holds because A · A = 4⁻¹ in the field, which is the value the product column carries.

    On an ADD row, the left lookup operand is zero. LeftLookupOperand = 0

    The one-hot lookup selectors select the chunks of the index 1, so the selectors and the lookup operand agree.

    The load row, cycle 2.

    The load’s read value, write value and rd write value are one value. RamReadValue = RamWriteValue = RdWriteValue A = A = A

    The read value is the value of the selected RAM word. RamReadValue = RamVal(advice word, cycle 2) A = A

    The register file.

    A register read returns the register table’s value. Rs1Value(3) = RegistersVal(x5, 3) A = A Rs2Value(3) = RegistersVal(x5, 3) A = A Rs2Value(4) = RegistersVal(x6, 4) 1 = 1

    The register table advances by the increment column. RegistersVal(x5, 3) = RegistersVal(x5, 2) + RdInc(2) A = 0 + A RegistersVal(x6, 4) = RegistersVal(x6, 3) + RdInc(3) 1 = 0 + 1

    The store row, cycle 4.

    The store writes its rs2 value to memory. RamWriteValue = Rs2Value 1 = 1

    The RAM table advances by the increment column. RamVal(output word, 5) = RamVal(output word, 4) + RamInc(4) 1 = 0 + 1

    The memory-checking folds.

    The initial value of the advice word is the committed advice leaf, and the fold closes. RamValFinal(advice word) = RamValInit(advice word) + Σ increments A = A + 0

    The output word’s fold closes. RamValFinal(output word) = 0 + RamInc(4) 1 = 0 + 1

    The final value of the output word equals the claimed output word. RamValFinal(output word) = 1

    Every other constraint sees only honest values, and holds as in the honest proof. No step anywhere asks that a value be below 2⁶⁴: not the committed advice word, not the load’s read value, not the register table. That is the one check Jolt never makes.

    4. How to reproduce this

    Everything below is at commit 5def437f, clear mode (the default Dory path, no zk feature), Rust 1.95. The prover, the verifier, the commitment scheme, the sumchecks and the transcript are Jolt’s own and unmodified. All modifications sit at the seams where Jolt’s pipeline derives witness values from the honest trace, substituting the cells of §2.

    The guest and the host. Assemble the eight-instruction program of §1 at 0x80000000. Run it with the memory configuration, inputs, advice bytes and claim of §1. Jolt’s tracer produces the honest trace. The host preprocesses, proves and verifies through jolt_sdk::preprocess_program, jolt_sdk::prove_program and jolt_verifier::verify.

    Where the witness is substituted. The proof’s field-element tables are served from one surface: the trace backend’s oracle, crates/jolt-witness/src/backend/trace/oracle.rs, function oracle_table. After each honest table is materialized, overwrite the cells of §2: the advice commitment’s first leaf, the load row’s three values, the ADD row’s operands, sum, lookup output, product and rd write, the store row’s values and increment, the RegistersVal and RamVal grids, RamValFinal, and the ADD row’s one-hot lookup selectors — at both chunk granularities, retargeted from the index C to the index 1. Locate the three rows semantically — the load of the advice word, the ADD doubling the loaded register, the store to the output word — not by fixed cycle indices.

    The kernel tier. Run the reference kernel tier, JoltBackend::reference(), not the optimized one. The reference tier derives every sumcheck table and every opening from the oracle. The optimized tier re-derives its tables from integer-typed row bundles (u64/i128), which cannot express a 253-bit cell. Jolt’s parity tests pin the two tiers to identical round polynomials, so the proof object is the same either way.

    The commitment stream and the stage-5 RAF. Two further surfaces derive values from integer row data and need the same substitutions. The commitment streaming — crates/jolt-kernels/src/reference/commitment.rs, the FusedColumns and MaterializedColumn consumers — feeds the increment columns through PCS::feed_i128 and the lookup one-hots as hot addresses. Substitute the same increment cells as field values, and retarget the ADD row’s lookup-index chunks to the chunks of 1. The stage-5 instruction-read RAF kernel — crates/jolt-kernels/src/reference/instruction_read_raf.rs — reads the per-cycle lookup index from a typed bundle. Set the ADD row’s index to 1.

    The device. The trace device’s output bytes are the public I/O that both the prover and the verifier read. Record the claimed bytes [1, 0, 0, 0, 0, 0, 0, 0] for the output-region store — common/src/jolt_device.rs, JoltDevice::store.

    The check. Run once with the honest witness: the program outputs [2, 0, 0, 240, 147, 245, 225, 67], and jolt_verifier::verify returns Ok(()) on that claim. Run once with the substitutions: the proof claims outputs [1, 0, 0, 0, 0, 0, 0, 0], and jolt_verifier::verify returns Ok(()).

    What the plumbing is for. A malicious prover needs none of it: it commits its own polynomials directly and runs the generic sumcheck machinery. The substitutions exist only so that the proof object comes out of Jolt’s own prover. The reproduction is Jolt’s own code accepting Jolt’s own lie.
