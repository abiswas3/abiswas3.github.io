Background

This is a continuation post.

1

Throughout this post, Sail refers to the trusted Sail to Lean transpilation of the RISC-V CPU.

At its core both Jolt and Sail1 model memory with a hash map as shown below. The keys are natural-number addresses, and the values read and written at the bottom of the memory stack are bytes. However, there still exists subtle differences between the two memory models. In Jolt, memory is divided into two regions based on address ranges - RAM and the Jolt device. The Jolt device region is memory-mapped I/O: loads are allowed from input, trusted advice, untrusted advice, output, panic, and termination pages, while stores are limited to output, panic, and termination pages. This is enforced by the tracer's device-page access check.

Sail on the other hand treats all addresses as the same by its definition of state. Regions of memory are instead tagged to be special via hypotheses. To make sense of the differences, we start with understanding the Sail memory pipeline.

The Sail Memory Pipeline

To understand how the Sail code accesses memory, we start with the execution of the load instructions. These are the sequence of steps needed to go from method definition to actually accessing the hash map.

Address Translation

Line 282: translateAddr: Here we need to go from our virtual address to a physical address. Now in Jolt, as discussed above, they are the same. In other words the translation is the identity function. Sail on the other hand leaves this decision open-ended based on the implementation. It gives us this extremely elaborate function for translating virtual to physical addresses.

Reading From Physical Memory

So far the helpers were for reading from virtual memory.

In Line 287 with mem_read we read from physical memory.

def mem_read (access : (MemoryAccessType mem_payload)) (paddr : physaddr) (width : Nat) (aq : Bool) (rel : Bool) (res : Bool) : SailM (Result (BitVec (8 * width)) ExceptionType) := do

which is a wrapper around mem_read_priv But before it can call mem_read_priv it needs a term of type Privilege which is computed via (← (effectivePrivilege access (← readReg mstatus) (← readReg cur_privilege)))

Privilege is just an inductive type that describes the privilege mode of the RISC-V CPU.

245inductive Privilege where | User | VirtualUser | Supervisor | VirtualSupervisor | Machine
246  deriving BEq, Inhabited, Repr

To get the current privilege of the CPU, we need to read the mstatus and cur_privilege registers which are fed into the following code as m and priv

def effectivePrivilege (access : (MemoryAccessType mem_payload)) (m : (BitVec 64)) (priv : Privilege) : SailM Privilege := do
  if (((bne access (InstructionFetch ())) && ((_get_Mstatus_MPRV m) == 1#1)) : Bool)
  then (privLevel_bits_forwards ((_get_Mstatus_MPP m), 0#1))
  else (pure priv)

This function decides which privilege level to use for the memory access. The if branch says: if this is not an instruction fetch and the MPRV bit in mstatus is set, use the privilege stored in the MPP field of mstatus. The else branch says: otherwise, keep using the current privilege priv. Quoting the RISC-V ISA

The MPRV (Modify PRiVilege) bit modifies the effective privilege mode, i.e., the privilege level at which explicit memory accesses execute. When MPRV=0, explicit memory accesses behave as normal, using the translation and protection mechanisms of the current privilege mode. When MPRV=1, load and store memory addresses are translated and protected, and endianness is applied, as though the current privilege mode were set to MPP. Instruction address-translation and protection are unaffected by the setting of MPRV. MPRV is read-only 0 if U-mode is not supported.

— RISC-V ISA: Section 3.1.1.6.4

So this brings us to two questions. First, what should the current privilege be? The answer in Jolt is simple: it is always Machine. The Rust tracer initializes both the CPU and MMU in PrivilegeMode::Machine. The trap instructions are consistent with this model: ECALL says Jolt has no S/U privilege levels, and MRET says there is only one privilege level, Machine.

Second, what should the MPRV bit be set to? It should be 0. The MMU initializes mstatus to 0, and ECALL writes mstatus = 0x1800, which sets MPP = Machine but leaves bit 17, MPRV, unset. See the MMU initialization and ECALL's mstatus write.

This gives us our first set of memory assumptions.

def phys_access_check (access : (MemoryAccessType mem_payload)) (priv : Privilege) (paddr : physaddr) (width : Nat) (res_or_con : Bool) : SailM (Option ExceptionType) := do

  | (.some e, none) => (pure (some e))
  | (none, .some e) => (pure (some e))
  | (.some e0, .some e1) => (pure (some (← (highestPriorityAlignmentOrAccessFault e0 e1))))
AI note: PMP/PMA checks

Jolt does not implement RISC-V PMP/PMA as Sail does here. The tracer's MMU says that memory protection is not implemented yet in the MMU struct comment.

What Jolt does have are its own concrete memory-layout checks: assert_effective_address checks RAM/device bounds and allowed device pages in the Jolt MMU address check, and multi-byte RAM loads assert natural alignment in load_halfword/load_word/load_doubleword. Those are not the same mechanism as Sail's PMP/PMA layer.

Teaching picture: pmpCheck is a permission check: for Load Data, the matched PMP entry must allow reads, unless Machine mode bypasses an unlocked entry; see pmpCheckRWX and pmpCheck. pmaCheck is a physical-memory-attribute check: the physical address must fall in a PMA region, the region must be readable for Load Data, and the region's alignment policy decides whether misalignment is an access fault or an alignment fault; see pmaCheck.

For this part of the Sail pipeline, the exact proof obligation is therefore: show that Sail's general phys_access_check returns none, so execution reaches read_ram. The call site is phys_access_check, and the successful RAM path is read_ram.

AI note: Jolt regions

Jolt's checks are region/address based. A LW is permitted if the effective address lies in an allowed load region: RAM, input, advice, output, panic, termination, or zero-padding. See the device-page allowlist in assert_effective_address.

The caveat is that RAM and device-region loads are not literally identical in the implementation. RAM loads go through self.memory.read_byte; device-region loads go through jolt_device.load. See load_raw.

AI note: CLINT/HTIF

Sail's within_mmio_readable is checking two modeled MMIO devices. within_clint checks whether the whole physical read lies inside Sail's CLINT physical address range, whose base and size are fixed by plat_clint_base and plat_clint_size.

within_htif_readable is Sail's Host-Target Interface check. HTIF is a simulator/test-harness convention for communication between a bare-metal RISC-V test program and the host simulator, commonly through a tohost word. In Sail, HTIF becomes readable MMIO only after enable_htif writes some base into htif_tohost_base. Then within_htif_writable/readable checks whether the requested physical range overlaps the 8-byte tohost slot [base, base + 8). If that check succeeds, Sail follows the mmio_read -> htif_load path instead of read_ram.

Jolt does not implement CLINT as a readable memory device: CLINT loads panic as unsupported in load_raw, and the time CSR path also panics with CLINT is unsupported in read_csr_raw. Jolt has a narrow tohost compatibility hook for external riscv-tests style ELF binaries, but this is not Sail's HTIF MMIO mechanism and is not the normal Jolt proving path. Jolt detects such a test by looking for an ELF symbol named tohost; if present, it stores that address in self.tohost_addr and polls that address with load_doubleword_raw; see the tohost symbol setup and run_test polling. It decodes the loaded word using HTIF-style fields (device, cmd, payload), but the memory access itself is still just a load from the ELF's tohost address. It is not routed through Sail's htif_tohost_base, within_htif_readable, or htif_load MMIO path. Normal Jolt proofs should therefore not treat this compatibility hook as evidence that the Sail HTIF MMIO branch is part of the Jolt memory model.

So the within_mmio_readable = false assumption is saying: this Sail proof is following the ordinary RAM path, not Sail's CLINT/HTIF MMIO path. That matches the normal Jolt memory path we are proving against.

Some Scratch notes

A CPU only knows one way to talk to the outside world: load and store to an address. There's no special "talk to the keyboard" instruction. So hardware designers play a trick: they wire certain devices to pretend to be memory addresses. That's Memory-Mapped I/O — I/O that's mapped onto the memory address space.

So your 64-bit address space is mostly real RAM, but a few address ranges are "fake": instead of storing bytes, they're wired to a gadget.

Examples

  • UART / serial port: store a byte to its address → that byte is sent out the serial line (your terminal prints it). That's literally how bare-metal printf works. This is the panic!("UART unsupported") in load_raw.
  • Timer (CLINT): load its address → the current time. Nothing was "stored" there; it's a live counter.
  • Keyboard controller: load → the last key pressed.

Physical Access Check

Both must say none to proceed. They answer two genuinely different questions.

PMA — "what is physically here?" (fixed by the hardware)

pmaCheck looks up the address in a table of Physical Memory Attribute regions (matching_pma). These are hardwired by the platform — the chip designer decides "addresses 0x8000_0000… are DRAM, 0x1000_0000… is a UART, this range is ROM," and so on. Each matched region carries fixed attributes:

  • readable, writable, executable
  • alignment policy (misaligned_fault)
  • atomicity/reservation/idempotency flags

The check is then:

  1. No matching region → access fault. There's literally no physical thing at that address.
  2. Misaligned and the region's policy is AccessFault → fault.
  3. Permission by attribute: Load Data needs attributes.readable; Store Data needs attributes.writable; InstructionFetch needs attributes.executable. ROM, for instance, is readable+executable but not writable — a store there faults here.

So PMA = "does a real memory region exist at this physical address, and does its intrinsic nature permit this kind of access?" It's a property of the silicon, not of software.

PMP — "am I allowed by the configured policy?" (programmable, per-privilege)

pmpCheck is Physical Memory Protection: a software-programmable firewall. Firmware/OS sets up to sys_pmp_count entries, each a pair — a pmpaddr register (encodes an address range, e.g. NAPOT/TOR) and a pmpcfg byte (R/W/X permission bits, the match mode, and a Lock bit). The loop, in priority order (entry 0 wins):

  • PMP_NoMatch → try the next entry.
  • PMP_PartialMatch → fault (an access may not straddle a protection boundary).
  • PMP_Match → this entry governs it. Grant iff pmpCheckRWX cfg access (the entry's R/W/X bit for this access type is set) or the Machine-mode bypass fires: priv == Machine && not locked. Otherwise access fault.
  • Fell through with no match: Machine → allowed; S/U → fault (default-deny for lower privilege). And if sys_pmp_count == 0, the whole thing is none — no PMP configured, nothing fenced.

So PMP = "given the protection regions firmware programmed and my current privilege level, may I touch this address?" It's the mechanism an OS uses to sandbox user code away from kernel memory.

The one-line contrast

  • PMA = fixed what-is-physically-here + intrinsic access nature (silicon).
  • PMP = configurable who-is-allowed-here per privilege (software policy).

Both can independently raise an ExceptionType; if both fault, phys_access_check picks the higher-priority one (highestPriorityAlignmentOrAccessFault).

Hardware Scratch Notes

  1. The CPU core (the hart). Just the RISC-V processor itself — a block that emits load/store requests onto a bus. It knows nothing about where things physically live.
  2. The SoC (System-on-Chip). The single physical chip that packages the core together with the address decoder, the memory controllers, and often some on-chip peripherals (UART, timer). This is the thing that actually routes "address 0x1000_0000" to the right place. Most of the memory-map decisions live here.
  3. The board (the motherboard / PCB). The physical circuit board the SoC is soldered onto. The DRAM is usually separate chips sitting next to the SoC, connected by copper traces ("wires") on the board. Connectors, the UART header pins, etc. are also here. How the board is populated and wired affects what's actually present at which address.
  4. Firmware + device tree. Software that boots first, configures registers, and hands the OS a device tree describing all of the above ("RAM: base 0x8000_0000, size 2 GB; UART here; …").

When I say "the platform decides the memory map," I mean (2)+(3)+(4) together: the SoC's decoder, how the board is wired and populated, and what the firmware sets up. So your guess is right — motherboard + chip + DRAM + wires, plus the config layer that tells software about it.

Concrete picture: think of a dev board like a SiFive HiFive (or a Raspberry-Pi-style board). There's a big SoC chip in the middle, DRAM chips beside it, a UART connector on the edge — all on one green PCB. That whole assembly, with its fixed wiring, is the platform, and it's what fixes "this address is RAM, that address is the UART."

The twist for Sail/Jolt: there is no board. It's all software. So "the platform" collapses into a configuration inside the model — the pma_regions register, the platform-config constants (plat_clint_base, etc.). Those play exactly the role the real SoC + board + device tree would: they're the stand-in that says "here's where RAM is, here's where the (modeled) CLINT is." For Jolt, that configuration is set so RAM is a readable region and the MMIO devices effectively aren't there.

So: platform = the physical target system (chip + DRAM + board + wiring) and its descriptive config — and in the proof world, just the config part survives as pma_regions / platform constants.
