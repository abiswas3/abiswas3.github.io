Disclaimer

Throughout this series, when we refer to "Sail" code, we mean the Lean 4 code generated by the Galois and Cambridge transpiler from the official RISC-V specification written in the Sail language.

All file references are relative to commit dd348a2 on branch embedded-sail-state of jolt-qed.

In the previous post, we walked through the proof of jolt_addiw_eq_sail — one specific instruction. But RISC-V has many instructions, and writing a bespoke proof for each would be tedious. The R-type-W instructions (ADDW, SUBW, SLLW, SRLW, SRAW) all follow the same pattern. Can we prove them all at once?

The Pattern

Every R-type-W instruction has the same shape on both sides:

Sail (native): execute_RTYPEW rs2 rs1 rd opw — reads rs1 and rs2 (both 64-bit), truncates each to 32 bits, applies the 32-bit operation, sign-extends the result back to 64 bits, writes to rd.

Jolt (decomposed): execute_RTYPE rs2 rs1 rd op followed by jolt_virtual_sign_extend_word rd — does the full 64-bit operation first, writes to rd, then reads rd back, truncates to 32 bits, sign-extends to 64, writes back.

The only things that differ per instruction are:

  1. The 64-bit operation f : BitVec 64 → BitVec 64 → BitVec 64 (e.g. (· + ·) for ADDW, (· - ·) for SUBW)
  2. The math lemma proving that truncation distributes over the operation: extractLsb (f a b) 31 0 = opw_result(extractLsb a 31 0, extractLsb b 31 0)

Everything else — the monadic plumbing, the state threading, the projectResult stripping — is identical.

The Generic Definition

The framework defines a single Jolt decomposition parameterised by the R-type opcode:

140def jolt_rtype_w (op : rop) (rs2 rs1 rd : regidx) : JoltMonad ExecutionResult := do
141  let _ ← liftSail (execute_RTYPE rs2 rs1 rd op)
142  jolt_virtual_sign_extend_word rd
143  pure RETIRE_SUCCESS

This is the same structure as jolt_addw, jolt_subw, etc. — just parameterised by op.

The Generic Concrete Lemma

The worker lemma is also generic. It takes a factoring hypothesis hf that says how execute_RTYPE decomposes for the given op:

147theorem jolt_rtype_w_concrete (op : rop)
148    (f : BitVec 64 → BitVec 64 → BitVec 64)
149    (hf : ∀ rs2 rs1 rd, execute_RTYPE rs2 rs1 rd op = do
150      let v1 ← rX_bits rs1; let v2 ← rX_bits rs2
151      wX_bits rd (f v1 v2); pure RETIRE_SUCCESS)
152    (rs2 rs1 rd : regidx) (hrd : rd ≠ regidx.Regidx 0)
153    (js : SailJoltState) (hwf : WellFormed js) :
154    ∃ (js' : SailJoltState) (v1 : BitVec 64) (v2 : BitVec 64),
155      rX_bits rs1 js.sail = .ok v1 js.sail ∧
156      rX_bits rs2 js.sail = .ok v2 js.sail ∧
157      (jolt_rtype_w op rs2 rs1 rd).run js = .ok RETIRE_SUCCESS js' ∧
158      js'.sail = stateAfterWrite js.sail rd
159        (sign_extend (m := 64) (Sail.BitVec.extractLsb (f v1 v2) 31 0))

Compare this with jolt_addiw_concrete from the previous post. The structure is identical — it says Jolt's decomposition succeeds and writes a specific value to rd. The differences are:

  • Two register reads (v1 from rs1, v2 from rs2) instead of one register + immediate
  • The value written is sign_extend(extractLsb(f v1 v2, 31, 0)) where f is a parameter, not hardcoded to addition
  • The factoring hypothesis hf is a parameter instead of being baked into the proof

The Generic Main Theorem

The main theorem adds one more parameter: the math lemma h_math connecting the 64-bit operation with the 32-bit W operation.

188theorem jolt_rtype_w_eq_sail (op : rop) (opw : ropw)
189    (f : BitVec 64 → BitVec 64 → BitVec 64)
190    (hf : ∀ rs2 rs1 rd, execute_RTYPE rs2 rs1 rd op = do
191      let v1 ← rX_bits rs1; let v2 ← rX_bits rs2
192      wX_bits rd (f v1 v2); pure RETIRE_SUCCESS)
193    (h_math : ∀ a b : BitVec 64,
194      Sail.BitVec.extractLsb (f a b) 31 0 =
195      (match opw with
196        | ropw.ADDW => Sail.BitVec.extractLsb a 31 0 + Sail.BitVec.extractLsb b 31 0
197        | ropw.SUBW => Sail.BitVec.extractLsb a 31 0 - Sail.BitVec.extractLsb b 31 0
198        | ropw.SLLW => ...
199        | ropw.SRLW => ...
200        | ropw.SRAW => ...))
201    (rs2 rs1 rd : regidx) (hrd : rd ≠ regidx.Regidx 0)
202    (js : SailJoltState) (hwf : WellFormed js) :
203    projectResult ((jolt_rtype_w op rs2 rs1 rd).run js) =
204    (execute_RTYPEW rs2 rs1 rd opw).run js.sail

h_math is the only per-instruction proof obligation that requires actual mathematics. For ADDW it says extractLsb (a + b) 31 0 = extractLsb a 31 0 + extractLsb b 31 0 — truncation distributes over addition. For SUBW, truncation distributes over subtraction. And so on.

Everything else — the monadic plumbing, the projectResult stripping, the wX_shape/wX_bits_eq_stateAfterWrite bridge — is handled once in this generic theorem.

The Proof

The proof follows exactly the same steps as the ADDIW proof from the previous post, with one extra step: rw [h_math].

204  obtain ⟨js', v1, v2, hj_rx1, hj_rx2, hj, hj_sail⟩ :=
205    jolt_rtype_w_concrete op f hf rs2 rs1 rd hrd js hwf
206  unfold execute_RTYPEW
207  simp only [EStateM.run, bind, EStateM.bind, pure, EStateM.pure, hj_rx1, hj_rx2]
208  show projectResult ((jolt_rtype_w op rs2 rs1 rd).run js) = _
209  rw [hj]
210  simp only [projectResult, project]
211  rw [hj_sail]
212  rw [h_math]      -- ← the one new step: apply the math lemma
213  obtain ⟨s', hw⟩ := wX_shape rd _ js.sail
214  rw [hw]
215  congr 1
216  exact (wX_bits_eq_stateAfterWrite rd _ js.sail s' hw).symm
The extra step

After rw [hj_sail], the LHS has stateAfterWrite js.sail rd (sign_extend (extractLsb (f v1 v2) 31 0)) and the RHS has stateAfterWrite js.sail rd (sign_extend (opw_result 31 0)).

The rw [h_math] step rewrites extractLsb (f v1 v2) 31 0 to the W-operation's expression (e.g. extractLsb v1 31 0 + extractLsb v2 31 0 for ADDW). After this, both sides have the same stateAfterWrite argument, and the rest is identical to the ADDIW proof.

Instantiation: ADDW

With the framework in place, proving ADDW is three things:

1. Factoring lemma — execute_RTYPE with rop.ADD factors as read-read-write:

10theorem execute_RTYPE_ADD_factored (rs2 rs1 rd : regidx) :
11    execute_RTYPE rs2 rs1 rd rop.ADD = (do
12      let v1 ← rX_bits rs1; let v2 ← rX_bits rs2
13      wX_bits rd (v1 + v2); pure RETIRE_SUCCESS) := by
14  simp [execute_RTYPE, bind_pure_comp]

2. The main theorem — one line:

23theorem jolt_addw_eq_sail (rs2 rs1 rd : regidx) (hrd : rd ≠ regidx.Regidx 0)
24    (js : SailJoltState) (hwf : WellFormed js) :
25    projectResult ((jolt_addw rs2 rs1 rd).run js) =
26    (execute_RTYPEW rs2 rs1 rd ropw.ADDW).run js.sail := by
27  exact jolt_rtype_w_eq_sail rop.ADD ropw.ADDW (· + ·) execute_RTYPE_ADD_factored
28    (by intro a b; exact extractLsb_add a b) rs2 rs1 rd hrd js hwf

The entire proof is a single exact — we instantiate the generic theorem with:

  • rop.ADD and ropw.ADDW — the R-type and R-type-W opcodes
  • (· + ·) — the 64-bit operation
  • execute_RTYPE_ADD_factored — the factoring proof
  • extractLsb_add — the math lemma (truncation distributes over addition)

That's it. No monadic plumbing, no simp, no projectResult. The framework handles all of that.

Instantiation: SUBW

SUBW is nearly identical. The only differences are the operation ((· - ·)) and the math lemma (extractLsb_sub):

17theorem extractLsb_sub (a b : BitVec 64) :
18    Sail.BitVec.extractLsb (a - b) 31 0 =
19    Sail.BitVec.extractLsb a 31 0 - Sail.BitVec.extractLsb b 31 0 := by
20  simp only [Sail.BitVec.extractLsb, BitVec.extractLsb]
21  apply BitVec.eq_of_toNat_eq
22  simp [BitVec.toNat_sub]
23  omega
32theorem jolt_subw_eq_sail (rs2 rs1 rd : regidx) (hrd : rd ≠ regidx.Regidx 0)
33    (js : SailJoltState) (hwf : WellFormed js) :
34    projectResult ((jolt_subw rs2 rs1 rd).run js) =
35    (execute_RTYPEW rs2 rs1 rd ropw.SUBW).run js.sail := by
36  exact jolt_rtype_w_eq_sail rop.SUB ropw.SUBW (· - ·) execute_RTYPE_SUB_factored
37    (by intro a b; exact extractLsb_sub a b) rs2 rs1 rd hrd js hwf
What each instruction must provide

To add a new R-type-W instruction to the framework, you need exactly two things:

  1. Factoring lemma: show that execute_RTYPE with your opcode factors as read-read-write with your f
  2. Math lemma: show that extractLsb (f a b) 31 0 equals the W-variant's 32-bit computation

The main theorem is then a one-line exact instantiating the generic framework. All the monadic plumbing, state threading, projectResult stripping, and wX_shape bridging is done once and reused.

What About Non-W R-type?

The non-W R-type instructions (SLL, SRA, SRL) are simpler — Jolt's decomposition directly matches the Sail instruction without the sign-extend-word step. A FormatR framework would be the same idea but without the jolt_virtual_sign_extend_word and without the h_math lemma — the value written to rd is just f v1 v2 on both sides.
