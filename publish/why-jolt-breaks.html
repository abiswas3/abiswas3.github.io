Background

In an earlier post, we analysed why a certain implementation of the improved Montgomery multiplication algorithm by Yuval Domb was not empirically faster out of the box. Our main finding after disassembling the code was that memory access overhead for 128 bit read/writes kills the speedups from having fewer multiplications. These large chunk reads/writes were likely due to intermediate \(n+1\) limbed values are stored in contiguous regions of memory (but it doesn’t have to). As a resolution, we found an alternate implementation tested by Yuval himself. In this implementation all intermediate values are storied in rust variables as opposed to constant sized vecs/arrays. This probably allows the compiler to optimise the assembly to use more registers (instead of read/writes), and this implementation is empirically faster than the current Arkworks CIOS implementation – the exact amount varies across, but it seems to be consistently faster across trials. We leave it as an exercise for the reader to stare the disassembled version of the two functions and figure out the differences. Cargo asm makes it very easy to look at static assembly.

Why does this happen?

Scanning the lines of code from the new implementation, we see that the final answer is not guaranteed to be less than the modulus \(p\) (as its never reduced). When you multiply two numbers that are both less than \(p\), The result may still cross over the modulus \(p\).

In Arkworks-CIOS the last line of multiplication involves subtracting \(p\) from the final answer if the answer is greater than \(p\). The line __subtract_modulus(a)simply computes \(p-a\) if \(a \ge p\).

First attempt: No big deal, we stick a __subtract_modulus(a) at the end of Yuval’s code and all should be good.

The tests still panics with the same error message

A few hours of debugging follow, we observe that even after subtracting \(p\) from the answer, the final answer is still sometimes greater than \(p\) i.e yuval’s algorithm outputs something that was greater than \(2p\).

Fine! stick in two conditional subtracts.

Jolt passes. Did we get lucky? One way to check is to try a lot of random inputs and try to break the test. 100,000 randomly seeded inputs, with 10 chained multiplication in each trial the tests ALWAYS PASS. Furthermore, the outputs of Arkworks-CIOS and the new implementation + 2 subtractions is exactly the same.

In the multiplication code for world coin, notice they have a reduce_ct function. Digging deeper we find that they subtracts 2p from a (the Montgomery product) only if the most significant bit of a is 1. Plugging in the this reduction instead of 2 conditional subtracts – Jolt tests fail again.

What is going on? Why do we need two subtractions? How do we know we don’t need 3 or 4 or 5?

100,000 trials is minuscule when compared to the input space of 256 bit numbers. What if there are edge cases that we can’t catch via fudging?

In what follows we derive a formal guarantee on how large the answer of the new Montgomery algorithm can be, therefore establishing the maximum number of conditional subtracts we must employ.

Montgomery Multiplication Maths

We begin with the basics of Montgomery multiplication, and then describe the CIOS algorithm. This gives all the background needed to get to our answer.

Below we actually describe the Separated Operand Scanning Algorithm (SOS), but deceptively refer to it as the Coarse Integrated Operand Scanning (CIOS) algorithm. This is done for ease of exposition only, the claims would hold regardless. See Acar’s thesis Chapter 2) for more details on these algorithms. We also do not discuss the optimisations made by the Gnark team as they are not relevant in this context.

Given a \(n\) limb modulus \(p\), integers \(a\) and \(b\) that are at most \(p-1\), Montgomery multiplication computes

\[ c \equiv abR^{-1} \mod p\]

where \(R=r^n\) and \(r = 2^w\), where \(w\) is the word size (typically 64-bits). To avoid explicitly computing modulo \(p\) by long division, we instead compute \((c + mp)/R \equiv cR^{-1}\mod p\) where \(m\) is an integer such that \(m+cp \equiv 0 \mod R\). A simple calculation solving for \(m\) gives us that \(m = -p^{-1}c \mod R\). For our purposes, \(p\) is prime so \(p\) and \(r\) are co-prime. Therefore, \(-p^{-1}\) is well defined, and thus so is \(m\).

Key Idea:

As \(R\) is a power of 2, the last division can be done by bit shift operations native to most instruction architectures.

The CIOS algorithm

What we describe above is the pseudocode description of the Montgomery reduction algorithm. In practice we do not actually compute \(m\) as a whole, then multiply it with \(p\) and add it to \(c\). We perform the computation limb by limb.
\(c\) can be written as as \(2n\) digit number:

\[ \begin{align} c &\equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p \\[10pt] cr^{-1} &\equiv ( c_{2n-1}r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r)r^{-1} + c_0 r^{-1} \mod p \\[10pt] \end{align} \]

The limb by limb process follows by repeating the following sub-routine \(n\) times.

Important Sub-Routine

Observe that \(c_0r^{-1} \equiv (c_0 + mp)r^{-1} \mod p\), where \(m\) such that \(c_0 + mp \equiv 0 \mod r\). Solving for \(m = -p^{-1}c_0 \equiv \mu c_0 \mod r\). Also as we are working modulo \(r\), it suffices to use \(m = \mu_{0}c_0\) discarding any carries, where \(\mu_{0}\) is the least significant word of \(\mu\).

We overload m a little in notation. This m is NOT the same m as the one defined in the pseudocode description on top. This m is just to make c0 + mp divisible by r.

Once we compute \(mp\), and add this to \(c\) to get \(c^{(1)}\), this should clear the least significant digit based on how we picked \(m\). See below

\[ \begin{align} c &\equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p \\[10pt] cr^{-1} &\equiv ( c_{2n-1}r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r)r^{-1} + c_0 r^{-1} \mod p \\[10pt] &\equiv ( c_{2n-1}r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r)r^{-1} + (c_0+ mp)r^{-1} \mod p \\[10pt] &\equiv (c + mp)r^{-1} \mod p \\[10pt] &\equiv ( c^{(1)}_{2n-1}r^{2n-1} + \ldots c^{(1)}_1r + 0)r^{-1} \mod p \\[10pt] &\equiv ( c^{(1)}_{2n-1}r^{2n-2} + \ldots c^{(1)}_1) \mod p \\[10pt] \end{align} \]

Repeat The Subroutine \(n\) times

Now we can play the subroutine again with \(c^{(1)}_1\) replacing the role of \(c_0\), and the updated value of \(m = \mu_0c_1^{(1)}\) (NOTE the same \(\mu_0\) is always used)

\[ \begin{align} cr^{-1} &\equiv ( c^{(1)}_{2n-1}r^{2n-2} + \ldots c^{(1)}_1 ) \mod p \\ cr^{-2} &\equiv ( c^{(1)}_{2n-1}r^{2n-3} + \ldots + c_1^{(1)}+ c_1^{(1)}r^{-1} \mod p \\ &\equiv ( c^{(2)}_{2n-1}r^{2n-3} + \ldots + c_1^{(2)} ) \mod p \end{align} \]

In fact we play this game \(n\) times

\[cR^{-1} \equiv cr^{-n} \equiv c^{(n)}_{2n-1}r^{n-1} + c^{(n)}_{n+1}r +c^{(n)}_{n} \mod p\]

To get the final answer.

Why Can’t This Answer Be Greater Than \(2p\) ?

What did we actually do in the above process ? Over \(n\) iterations, in each iteration, we computed \(m\), added \(mp\) to \(c\) and divided by \(r\). We denote the \(m\) in iteration \(i\) with \(m_i\) here. More explicitly,

\[ \begin{align} cR^{-1} &\equiv (\ldots((c + m_0p)r^{-1} + m_1p)r^{-1} + \dots + m_{n-1}p)r^{-1} \\[10pt] &= \frac{c + p\sum_{i=0}^{n-1} m_ir^{i}}{r^n} \\ &= \frac{c + m'p }{R} \\ &< \frac{Rp + pR}{R}\\ &= 2p \end{align} \]

Here \(m'\) is some integer expressed using \(n\) limbs, therefore strictly less than \(R\). This is exactly why, if the answer is greater than \(p\), one subtraction suffices. We NEVER need more than one subtraction!

Yuval’s New Multiplication Algorithm

The new algorithm is based on the subtle observation. Quoting the original blog:

Per round of the Montgomery reduction, we previously computed ci r−1 mod  p using n + 1 digit multiplications. An alternative method to achieve this, using only n digit multiplications, is by computing ρ1 = r−1 mod  p. One way to understand this algorithm is that, in each round, the current sum is divided by 𝑟, and the resulting fraction is converted into an n + 1-digit number ci ρ1, which is then added to the integer part of the division.

In simple words, in CIOS we were adding and then dividing1, now we first divide and then add things. See below:

\[ c \equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p\] Dividing \(c\) with \(r^{n-1}\), we get

\[ \begin{align} cr^{-(n-1)} &\equiv c_{2n-1}r^{n} + \ldots + c_{n-1} + c_{n-2}r^{-1} \ldots + c_1r^{-(n-2)}+ c_0r^{-(n-1)} \mod p \end{align} \]

If we pre-computed2 \(\rho_i \equiv r^{-i} \mod p\) for all \(i \in [n-1]\), we can re-write the above equation as

\[cr^{-n+1} \equiv \Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big) + \Big(c_{n-2}\rho_1\Big) \ldots + \Big(c_1\rho_{n-2}\Big)+ \Big(c_0\rho_{n-1}\Big) \mod p\]

Barring the left most bracketed term, the remaining bracketed terms are \(n+1\) limbed numbers referred to as the fractional part of the division in the quoted text and \(\Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big)\) is the integer part of the division. Using more standard terminology, the remainder and quotient.

These can be calculated independently and in parallel3.

Let \(s = \Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big) + \Big(c_{n-2}\rho_1\Big) \ldots + \Big(c_1\rho_{n-2}\Big)+ \Big(c_0\rho_{n-1}\Big)\). To compute the final answer, we do the standard thing od adding \(mp\) and dividing by \(r\) for the last step, where \(m= s_0\mu_0\) and \(s_0\) is the least significant word of \(s\).

\[ cR^{-1} \mod p \equiv (s+ mp)/r\]

Theorem

We claim that s < n ⋅ (rp).

Dividing \(c\) by \(r^{n-1}\) we get

\[ \begin{align} \frac{c}{r^{n-1}} &= Q + R \end{align} \] where \(R = \Big(c_{n-2}\rho_1\Big) \ldots + \Big(c_1\rho_{n-2}\Big)+ \Big(c_0\rho_{n-1}\Big)\) and \(Q = \Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big)\)

Now \(R < (n-1)rp\) as each bracketted term is at most \(rp\).

Also \(Q \le \lfloor \frac{c}{r^{n-1}}\rfloor < \frac{p^2}{r^{n-1}} < \frac{r^np}{r^{n-1}} = rp\)

Therefore, \(Q+R < n\cdot rp\)

From this we can conclude that

\[ cR^{-1} \mod p \equiv (s+ mp)/r < (nrp + rp)/r < (n+1)p\]

Therefore, it is often not sufficient to subtract \(p\) from the answer just once. For \(n=4\), this implies that the answer will be less than \(5p\).

So it appears that two _substract_modulus operations us still insufficient. Although we were never able to break the algorithm by fuzzing.

At a high level what is going on? When you add and divide – the numbers we add to the current sum are \(n\)$ limbed numbers. When you divide and add, the remainder consists of \(n-1\) numbers that are all \(n+1\) limbs. So we’re adding much bigger numbers to the current sum, which should indicate we should get much larger overflows.

Is \((n+1)p\) tight?

Remember we could not get a random test to fail. This would hint that the analysis could be improved. But 256 bits of input is too large a space to exhaustively test. So what do we do now?

Firstly, the upper bound actually partially depends \(p\).

In our proof we use \(R < (n-1)rp\). The real bound here is \[ R < r(\rho_1, \dots, \rho_{n-1})\]

\(\rho_i \equiv r^{-i} \mod p\) for all \(i \in [n-1]\) - this only changes if we change \(p\). For \(n=4\), there are only 3 \(\rho\)’s. If for some miraculous \(p\) it might be the case that all the \(\rho_i\)’s are very very small like at most 3. Now instead of \(3p\) extra bit \(R\) contributes, it’ll $ 3 + 3 +3 = 9$ (as the \(r\)’s cancel out)

As always we are dealing with the bn-254 curve for which we know \(p\) and \(\rho_1, \rho_2, \rho_3\).

Ok what about \(Q\) and \(m\) ? \(Q\) depends on \(c_7, \ldots, c_3\) and in the worst case they can all be \(r-1\). So it seems like there’s no wiggle room there? Or is there?

So far all the analysis has hinged on the fact that \(c_i = (r-1)\) for all \(i\).

Remember \(c = ab\) where \(a\) and \(b\) are numbers that are at most \(p\). Are there actually \(a\) and \(b\) values that lead to the worst case – all digits of \(c\) are \(r-1\). If not what is actually the worst \(c\) ?

Worst case check: How do we find such an \(a\) and \(b\) ?

# all digits of product a*b as big as possible
# c[7] = carry + carry = r-1
# c[6] = a3*b3 + carry = r-1 mod r
# c[5] = a3*b2+b3*a2 + carry = r-1 mod r
# c[4] = a3*b1+a2*b2+b3*a1 + carry = r-1 mod r
# c[3] = a3*b0+a2*b1+a1*b2+a0*b3 + carry= r-1 mod r
# c[2] = a2*b0+a1*b1+a0*b2 + carry = r-1 mod r
# c[1] = a1*b0+a0*b1 + carry = r-1 mod r
# c[0] = a0*b0 = r-1 mod r

This is the system of equations with 8 variables and 7 equations (well kind of the carries make my life a little tedious).

Analysing this system of equations will tell me what the the worst case values of the limbs of \(c\) can be. This in turn will tell us how whether the two subtracts were pure luck, or something more beautiful is going on :-)
