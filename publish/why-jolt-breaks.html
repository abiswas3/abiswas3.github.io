Why Do We Panic?

When we ran cargo test -p jolt-core -- sha3_e2e_hyperkzg we get the following panic.

thread '<unnamed>' panicked at /Users/aribiswas3/Work-With-A16z/arkworks-algebra/ff/src/fields/models/fp/montgomery_backend.rs:1360:9:
High limb expected to be 0 if S >= 1 before 2p comparison


failures:
    jolt::vm::rv32i_vm::tests::sha3_e2e_hyperkzg

test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 219 filtered out; finished in 4.79s

This is the code for the Conditional Subtraction for Barrett reduction, that causes the panic! If you look at line 1360, it specifically needs the Big integer listed as r_tmp not have its high bit set to 1. Now when you multiply two numbers, sometimes it may cause the result to cross over the modulus \(p\). In CIOS this is easily resolved by subtracting \(p\) from the product. Which is easily confirmd here, where the __subtract_modulus(a)simply computes \(p-a\) if \(a \ge p\).

fn __subtract_modulus(a: &mut F) {
    if a.is_geq_modulus() {
        __sub_with_borrow(&mut a.0, &#modulus);
    }
}

In Yuval’s new implementation, we find the sometimes the product \(ab\) is two times larger than \(p\), and might require subtracting \(p\) twice. The linked code does not do any subtraction, as this was just benchmarking code.

If we use the linked code directly, the current Arkworks library will sometimes complain at Line 1360 essentially saying the number passed is too big.

Adding this snippet of code to the optimised Montgomery multiplication code resolves this error but at the cost of some performance when compared to the linked code above (we are executing more instructions).

__subtract_modulus(ans)
__subtract_modulus(ans)

In the code for world coin, notice they have a reduce_ct function. This subtracts \(2p\) from \(a\) (the Montgomery product) only if the most significant bit of \(a\) is 1, as described Line

let msb = (a[3] >> 63) & 1;

This appears to be not strong enough of a condition for Arkworks to not complain :-( The remainder of this post discusses why subtracting twice is sufficient.

Why Do The Tests Now Pass

The SOS/CIOS Algorithm

Given \(n\) limb modulus \(p\), and integers \(a\) and \(b\) that are smaller than \(p\), Montgomery multiplication computes

\[ c \equiv abR^{-1} \mod p\]

where \(R=r^n\) and \(r = 2^w\), where \(w\) is the word size (typically 64-bits). To avoid explicitly computing modulo \(p\) by long division, we instead compute \((c + mp)/R \equiv cR^{-1}\mod p\) where \(m\) is an integer such that \(m+cp \equiv 0 \mod R\). A simple calculation solving for \(m\) gives us that \(m = -p^{-1}c \mod R\). For our purposes, \(p\) is prime so \(p\) and \(r\) are co-prime. Therefore, \(-p^{-1}\) is well defined, and thus so is \(m\).

Why subtract Modulus

Why does one __subtract_modulus suffice for CIOS? The answer can be found in Theorem 2 On Page 7. In the original paper, they make an argument for signed integers, but the same argument holds for unsigned integers as well. Note that \(c\), which is a product of two integers \(a\) and \(b\), which are both at most \(p\), is at most \(p^2\) and \(R\) is chosen to be the smallest power of \(2\) bigger than \(p\).

\[c < p^2 < Rp\] Therefore, \[c + mp < Rp + mp < Rp + Rp\] Finally, as \(c+mp\) is divisible by \(R\), we have \[(c+mp)/R < 2p\]

So clearly at the end of adding \(mp\) to \(c\), we may go over \(p\), but never over \(2p\). When we do go over \(p\), outputting \(c-p\) as the answer, ensures that the answer is always less than \(p\).

How Is CIOS actually computed

What we describe above is the essence of the Montgomery reduction, but we do not compute \(m\) and compute \(mp\) directly in practice. Instead perform reductions limb by limb.

Note that performing limb by limb operations, will give us a final value that c + m̂p which is also divisible by R, but m̂ is not necessarily the same m above. But that’s not really important, whatever m̂ we get is also less than R, so the same argument holds: (c + m̂p)/r < 2p.

\[\begin{align} c &\equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p \\ cr^{-1} &\equiv ( c_{2n-1}r^{2n-2} + \ldots c_1 + (c_0 r^{-1} \mod p) ) \mod p \end{align}\]

Next, we describe an important sub-operation that we will need \(n\) times.

Important Sub-Routine

We have \(c_0r^{-1} \equiv (c_0 + m_0p)r^{-1} \mod p\) where \(m\) such that \(c_0 + m_0p \equiv 0 \mod r\). Solving for \(m_0 = -p^{-1}c_0 \equiv \mu_0 c_0 \mod r\).

Also as we are working modulo \(r\), it suffices to use \(m_{0}[0] = c_{0}[0] \times \mu_{0}[0]\) discarding any carries, where \(c_{0}[0]\) and \(\mu_{0}[0]\) are the least significant words of \(c_0\) and \(\mu_0\) respectively.

Once we compute \(c_0 r^{-1} \equiv c_0 + m_0[0]p \mod p\), we add this to \(c\), which should clear the least significant digit i.e. \(c^{(1)} = c + (c_0 + m_0[0]p)\) is divisible by \(r\). Thus,

\[\begin{align} c &\equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p \\ cr^{-1} &\equiv ( c_{2n-1}r^{2n-2} + \ldots c_1 + (c_0 r^{-1} \mod p) ) \mod p \\ cr^{-1} &\equiv ( c^{(1)}_{2n-1}r^{2n-2} + \ldots c^{(1)}_1 ) \mod p \end{align}\]

Repeat The Subroutine \(n\) times

Now we can play the subroutine again with \(c^{(1)}_1\) replacing the role of \(c_0\).

\[\begin{align} cr^{-1} &\equiv ( c^{(1)}_{2n-1}r^{2n-2} + \ldots c^{(1)}_1 ) \mod p \\ cr^{-2} &\equiv ( c^{(1)}_{2n-1}r^{2n-3} + \ldots + c_1^{(1)}r^{-2}+ (c_1^{(1)}r^{-1} \mod p) ) \mod p \\ &\equiv ( c^{(2)}_{2n-1}r^{2n-3} + \ldots + c_1^{(2)}r^{-2} ) \mod p \end{align}\]

In fact we play this game \(n\) times

\[cR^{-1} \equiv cr^{-n} \equiv c^{(n)}_{2n-1}r^{n-1} + c^{(n)}_{n+1}r +c^{(n)}_{n} \mod p\]

Finally, if this number is over \(p\), we know it can’t be bigger than \(2p\), we subtract \(p\) from it, and we have our answer. See this line to see this is exactly what Arkworks does in its CIOS algorithm.

Yuval’s New Multiplication Algorithm

Now the new algorithm is based on this subtle but clever observation that

\[ cr^{-n+1} \equiv c_{2n-1}r^{n} + \ldots + c_{n-1} + c_{n-2}r^{-1} \ldots + c_1r^{-n+2}+ c_0r^{-n+1} \mod p\]

Now if we pre-compute \(\rho_i = r^{-i} \mod p\) for all \(i \in [n-1]\), we can re-write the above equation as

\[cr^{-n+1} \equiv \Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big) + \Big(c_{n-2}\rho_1\Big) \ldots + \Big(c_1\rho_{n-2}\Big)+ \Big(c_0\rho_{n-1}\Big) \mod p\]

Now each of these bracketed terms are \(n+1\) limbed numbers that can be calculated independently and in parallel1.

Note that the only thing we have done that is different from CIOS so far is that by pre-computing \(\rho_1, \dots, \rho_{n-1}\) we have shaved off the number of multiplications by an additive factor of \(n\). Let \(\tilde{R} = r^{-(n-1)}\), then by the same argument above, \[s = (c + \tilde{m}p) < 2Rp\]

For the Bn254 curve, \(n=4\) and looking at the implementation for world coin the above logic is clearly verified (the code uses \(t\) instead of \(c\)).

\(s_{r1} = c_0 \rho_{3}\)

Where the subarray! macro just starts at index 3 of array \(t\) and slices the next 5 higher indices.

\(s + mp < 2Rp + Rp < 3Rp\). Therefore, two subtractions suffice.
