Background

In an earlier post, we analysed why this implementation of the improved Montgomery multiplication algorithm by Yuval Domb was not empirically faster out of the box. After disassembling the code using the Intel Pin tool, we identified large memory reads/writes as the main source of slower run times. The analysis was specific to x86 architectures, but the empirical findings were consistent on Mac-M2 Air and Intel x86 Digital Ocean servers. This loss of performance, however, is an artefact of the implementation, not the algorithm itself. The new algorithm uses fewer multiplication operations than the CIOS algorithm, and therefore, there should be a faster implementation (at least in theory).

The large chunk reads and writes were likely due to the high-level Rust code storing intermediate \(n+1\) limbed values in contiguous regions of memory. This led to the compiler asking this of the generated assembly code as well. Contiguous memory storage is not required by the algorithm specification, it’s just an implementation detail.

As a resolution, we found an alternate implementation. In this implementation, all intermediate values are stored in Rust variables as opposed to constant-sized vecs/arrays. The code explicitly multiplies limb by limb and then adds them all up. See the figure below for a visual illustration of what this implementation does.

This allows the compiler to optimise the assembly to use more registers (instead of large read/writes to memory), and this implementation is empirically faster than the current Arkworks CIOS implementation (the exact amount varies across trials, but it seems to be consistently faster across trials).

This is not the only thing that is different about this implementation, but we will get to that in a bit.

For the remainder of the post, we refer to the original Arkworks CIOS algorithm for Montgomery multiplication as c-mult, the previous implementation of the new multiplication as s-mult, and the faster implementation as h-mult

Why does this happen?

Scanning the lines of code for h-mult,we observe that the final answer is not reduced \(\mod p\). When you multiply two numbers that are both less than \(p\), the result may still cross over the modulus \(p\).

In Arkworks-CIOS, the last line of multiplication involves subtracting \(p\) from the final answer if the answer is greater than \(p\). The line __subtract_modulus(a)simply computes \(p-a\) if \(a \ge p\).

In the multiplication code for s-mul, notice they have a reduce_ct function. Digging deeper, we find that they subtract \(2p\) from \(a\) (the Montgomery product) only if the most significant bit of \(a\) is 1.

We have three algorithms, and the final answer for each algorithm is the same (modulo p). But they are not the same numerical value. To summarise:

  • c-mult: that passes unit tests and subtracts \(p\) from \(a\) when \(a \ge p\).
  • h-mult: that fails unit tests and does not do any reduction.
  • s-mult: that fails unit tests and subtracts \(2p\) from \(a\) when the msb of \(a\) is 1.

Montgomery Multiplication Maths

We begin with the basics of Montgomery multiplication, and then describe the CIOS algorithm. This gives all the background needed to get to what is going on.

Below we actually describe the Separated Operand Scanning Algorithm (SOS), but deceptively refer to it as the Coarse Integrated Operand Scanning (CIOS) algorithm. This is done for ease of exposition only, the claims would hold regardless. See Acar’s thesis Chapter 2 for more details. We also do not discuss the optimisations made by the Gnark team as they are not relevant in this context.

Given a \(n\) limb modulus \(p\), integers \(a\) and \(b\) that are at most \(p-1\), Montgomery multiplication computes

\[ c \equiv abR^{-1} \mod p\]

where \(R=r^n\) and \(r = 2^w\), where \(w\) is the word size (typically 64-bits). To avoid explicitly computing modulo \(p\) by long division, we instead compute \((c + mp)/R \equiv cR^{-1}\mod p\) where \(m\) is an integer such that \(m+cp \equiv 0 \mod R\). A simple calculation solving for \(m\) gives us that \(m = -p^{-1}c \mod R\). For our purposes, \(p\) is prime so \(p\) and \(r\) are co-prime. Therefore, \(-p^{-1}\) is well defined, and thus so is \(m\).

Key Idea: As \(R\) is a power of 2, the last division can be done by bit shift operations native to most instruction architectures.

The CIOS algorithm

What we describe above is the pseudocode description of the Montgomery reduction algorithm. In practice we do not actually compute \(m\) as a whole, then multiply it with \(p\) and add it to \(c\). We perform the computation limb by limb.
\(c\) can be written as as \(2n\) digit number:

\[ \begin{align} c &\equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p \\[10pt] cr^{-1} &\equiv ( c_{2n-1}r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r)r^{-1} + c_0 r^{-1} \mod p \\[10pt] \end{align} \]

The limb by limb process follows by repeating the following sub-routine \(n\) times.

Important Sub-Routine

Observe that \(c_0r^{-1} \equiv (c_0 + mp)r^{-1} \mod p\), where \(m\) such that \(c_0 + mp \equiv 0 \mod r\). Solving for \(m = -p^{-1}c_0 \equiv \mu c_0 \mod r\). Also as we are working modulo \(r\), it suffices to use \(m = \mu_{0}c_0\) discarding any carries, where \(\mu_{0}\) is the least significant word of \(\mu\).

We overload m a little in notation. This m is NOT the same m as the one defined in the pseudocode description on top. This m is just to make c0 + mp divisible by r.

Once we compute \(mp\), and add this to \(c\) to get \(c^{(1)}\), this should clear the least significant digit based on how we picked \(m\). See below

\[ \begin{align} c &\equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p \\[10pt] cr^{-1} &\equiv ( c_{2n-1}r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r)r^{-1} + c_0 r^{-1} \mod p \\[10pt] &\equiv ( c_{2n-1}r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r)r^{-1} + (c_0+ mp)r^{-1} \mod p \\[10pt] &\equiv (c + mp)r^{-1} \mod p \\[10pt] &\equiv ( c^{(1)}_{2n-1}r^{2n-1} + \ldots c^{(1)}_1r + 0)r^{-1} \mod p \\[10pt] &\equiv ( c^{(1)}_{2n-1}r^{2n-2} + \ldots c^{(1)}_1) \mod p \\[10pt] \end{align} \]

Repeat The Subroutine \(n\) times

Now we can play the subroutine again with \(c^{(1)}_1\) replacing the role of \(c_0\), and the updated value of \(m = \mu_0c_1^{(1)}\) (NOTE the same \(\mu_0\) is always used)

\[ \begin{align} cr^{-1} &\equiv ( c^{(1)}_{2n-1}r^{2n-2} + \ldots c^{(1)}_1 ) \mod p \\ cr^{-2} &\equiv ( c^{(1)}_{2n-1}r^{2n-3} + \ldots + c_1^{(1)}+ c_1^{(1)}r^{-1} \mod p \\ &\equiv ( c^{(2)}_{2n-1}r^{2n-3} + \ldots + c_1^{(2)} ) \mod p \end{align} \]

In fact we play this game \(n\) times

\[cR^{-1} \equiv cr^{-n} \equiv c^{(n)}_{2n-1}r^{n-1} + c^{(n)}_{n+1}r +c^{(n)}_{n} \mod p\]

To get the final answer.

Why Can’t This Answer Be Greater Than \(2p\) ?

What did we actually do in the above process ? Over \(n\) iterations, in each iteration, we computed \(m\), added \(mp\) to \(c\) and divided by \(r\). We denote the \(m\) in iteration \(i\) with \(m_i\) here. More explicitly,

\[ \begin{align} cR^{-1} &\equiv (\ldots((c + m_0p)r^{-1} + m_1p)r^{-1} + \dots + m_{n-1}p)r^{-1} \\[10pt] &= \frac{c + p\sum_{i=0}^{n-1} m_ir^{i}}{r^n} \\ &= \frac{c + m'p }{R} \\ &< \frac{Rp + pR}{R}\\ &= 2p \end{align} \]

Here \(m'\) is some integer expressed using \(n\) limbs, therefore strictly less than \(R\). This is exactly why, if the answer is greater than \(p\), one subtraction suffices. We NEVER need more than one subtraction!

Yuval’s New Multiplication Algorithm

The new algorithm is based on the subtle observation. Quoting the original blog:

Per round of the Montgomery reduction, we previously computed ci r−1 mod  p using n + 1 digit multiplications. An alternative method to achieve this, using only n digit multiplications, is by computing ρ1 = r−1 mod  p. One way to understand this algorithm is that, in each round, the current sum is divided by 𝑟, and the resulting fraction is converted into an n + 1-digit number ci ρ1, which is then added to the integer part of the division.

In simple words, in CIOS we were adding and then dividing1, now we first divide and then add things. See below:

\[ c \equiv (c_{2n-1} r^{2n-1} + c_{2n-2} r^{2n-2} + \ldots + c_1r + c_0) \mod p\] Dividing \(c\) with \(r^{n-1}\), we get

\[ \begin{align} cr^{-(n-1)} &\equiv c_{2n-1}r^{n} + \ldots + c_{n-1} + c_{n-2}r^{-1} \ldots + c_1r^{-(n-2)}+ c_0r^{-(n-1)} \mod p \end{align} \]

If we pre-computed2 \(\rho_i \equiv r^{-i} \mod p\) for all \(i \in [n-1]\), we can re-write the above equation as

\[cr^{-(n-1)} \equiv \Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big) + \Big(c_{n-2}\rho_1\Big) \ldots + \Big(c_1\rho_{n-2}\Big)+ \Big(c_0\rho_{n-1}\Big) \mod p\]

Barring the left most bracketed term, the remaining bracketed terms are \(n+1\) limbed numbers referred to as the fractional part of the division in the quoted text and \(\Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big)\) is the integer part of the division. Using more standard terminology, the remainder and quotient.

These can be calculated independently and in parallel[^b].

Let \(s = \Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big) + \Big(c_{n-2}\rho_1\Big) \ldots + \Big(c_1\rho_{n-2}\Big)+ \Big(c_0\rho_{n-1}\Big)\). To compute the final answer, we do the standard thing od adding \(mp\) and dividing by \(r\) for the last step, where \(m= s_0\mu_0\) and \(s_0\) is the least significant word of \(s\).

\[ cR^{-1} \mod p \equiv (s+ mp)/r\]

What s-mul does is it implements the above algorithm exactly as described above.

Theorem

We claim that s < n ⋅ (rp).

Dividing \(c\) by \(r^{n-1}\) we get

\[ \begin{align} \frac{c}{r^{n-1}} &= Q + R \end{align} \] where \(R = \Big(c_{n-2}\rho_1\Big) \ldots + \Big(c_1\rho_{n-2}\Big)+ \Big(c_0\rho_{n-1}\Big)\) and \(Q = \Big(c_{2n-1}r^{n} + \ldots +c_{n-1} \Big)\)

Now \(R < (n-1)rp\) as each bracketed term is at most \(rp\).

Also \(Q \le \lfloor \frac{c}{r^{n-1}}\rfloor < \frac{p^2}{r^{n-1}} < \frac{r^np}{r^{n-1}} = rp\)

Therefore, \(Q+R < n\cdot rp\)

From this, we can conclude that

\[ cR^{-1} \mod p \equiv (s+ mp)/r < (nrp + rp)/r < (n+1)p\]

Therefore, it is often not sufficient to subtract \(2p\) from the answer, you might have to go as high as subtracting \(4p\).

Why Does h-mult Pass?

It makes sense why s-mul fails. From the above bounds its very possible that the final answer is much bigger than \(p\). But this does not explain why h-mul, which computes the same thing, passes?

The answer to this is that although h-mul are s-mul are based on the same algorithm, they are implemented slightly differently.

A hybrid algorithm

More specifically, h-mul is a hybrid between the completely expanded s-mul algorithm and the c-mul algorithm. We explain this difference in the context of \(n=4\). The h-mul algorithm can be described as an iteration of \(\log_2 n\) division operations. At each iteration, we reduce half of the remaining digits. We start with \(n=4\). Half of that is \(2\)

\[ \begin{align} cr^{-2} &\equiv \Big(c_{7}r^{5} + \ldots +c_{3}r + c_2 \Big) + \rho_2(c_1r + c_0) \end{align} \]

In the next step, we reduce by 1

\[ \begin{align} cr^{-3} &\equiv \Big(c_{7}r^{4} + \ldots +c_{3} \Big) + \rho_1(c_2 + \rho_2(c_1r + c_0)) \\ &\equiv Q + R \end{align} \]

From here on with just do CIOS.

For each time we involve an iteration, we blow up the current sum by \(rp\) We will prove this subsequently. In h-mul we only add twice to \(Q\) whereas in s-mul we add three times. This is why the number of subtractions in h-mul will always be 1 less than the one needed for s-mul.

If you stare at the code long enough, you’ll confirm that s-mul uses 3 precomputed constants U64_I3, U64_I2, U64_I1. On the other hand h-mul uses just U64_I2, U64_I1. These are the ρ’s.

We can play with this even further and do just 1 iteration, and then play CIOS.

\[ \begin{align} cr^{-2} &\equiv \Big(c_{7}r^{5} + \ldots +c_{3}r + c_2 \Big) + \rho_2(c_1r + c_0) \\[10pt] &\equiv Q +R \end{align} \]

In this case, the number of subtractions is always 1 less than that of h-mul. Of course, in CIOS we do not play any iteration at all, so we start with CIOS from the beginning.

Summarising: CIOS we play no iterations of reductions, in s-mul we play \(n-1\) iterations. In other algorithms, we can interpolate with the number of iterations/reductions.

Theorem

If we play the game for x iterations (number of times we divide the residual sum), then we save x multiplication operations compared to CIOS, but we add x extra addition operations compared to CIOS.

Missing Factor Of 1

At this point, there is one question left. We proved that in theory

  • s-mul needs at most 4 subtractions.
  • h-mul needs at most 3 subtractions.
  • c-mul needs at most 1 subtraction.

But why does two subtract work out for h-mul? Shouldn’t it be 3? The above bounds come from the following analysis:

\[ \begin{align} cr^{-2} &\equiv Q + \rho_2(c_1r + c_0) \\[10pt] &< Q + \rho_2(r^2) \\[10pt] cr^{-3} &< Q' + \rho_1r + \rho_2r \end{align} \]

Finally, the last CIOS gives us

\[cr^{-4} < \Big(Q' + r(\rho_1 + \rho_2) + mp \Big)/r < 4p\]

The 4 is the 1 improvement from 5 we promised. However, \(\rho_1\) and \(\rho_2\) are fixed. For the bn-254 scalar field prime, the limits of what \(p\) and \(Q'\) can be mean that max value of s-mul can at most \(3.25pr\).

This is why we can always do one subtraction less for h-mul and s-mul :-)
