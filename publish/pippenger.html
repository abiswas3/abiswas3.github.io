Pippenger For MSM

Ari
Published: 2025-06-19
  • cryptography
  • benchmarking

🧮 Problem Setting: MSM

Given \(n\) pairs \((s_i, P_i)\), compute:

\[ \sum_{i=1}^n s_i P_i \]

Each \(s_i\) is a scalar (e.g., an integer modulo a group order), and each \(P_i\) is a point on an elliptic curve.

🚶 Naive Double-and-Add (Per-Point Scalar Multiplication)

For each \(i\):

  • Compute \(s_i P_i\) using the binary representation of \(s_i\), applying point doubling and addition.
  • Cost: \(O(\log s_i)\) elliptic curve (EC) operations per scalar (e.g., about 256 if using 256-bit scalars).
  • Total cost: \(O(n \log s)\) EC operations (doublings and additions mixed).

This method treats each scalar multiplication independently and performs no optimization across different points or scalars.

🪣 Pippenger’s Algorithm (with window size \(c\))

Core Idea:

Exploit the structure of many scalar multiplications simultaneously to reduce the number of expensive elliptic curve additions.

Steps:

  1. Window decomposition: Split each scalar \(s_i\) into chunks (digits) of \(c\) bits.
    • You now have \(\ell = \left\lceil \frac{\log s}{c} \right\rceil\) windows per scalar.
  2. For each window \(j\) (from 0 to \(\ell - 1\)):
    • For each bucket \(b \in [1, 2^c - 1]\), accumulate the points \(P_i\) whose \(j\)-th window value is \(b\) into bucket \(B_b\).
    • After bucket accumulation: process buckets in increasing order of \(b\), doing running sums to amortize additions (this is Pippenger’s key trick).
  3. Shift window contributions: The contribution from window \(j\) must be multiplied by \(2^{cj}\), implemented via a few doublings.

Complexity:

  • Number of EC additions/doublings is reduced to:

    \[ O\left(\frac{n}{c} + 2^c\right) \]

    per window, times \(\ell = \left\lceil \frac{\log s}{c} \right\rceil\) windows.

[!note] wnaf optimisation We can reduce this to \(2^{c-1}\) using signed indices

  • Total complexity:
    \[ O\left( \left( \frac{n}{c} + 2^c \right) \cdot \frac{\log s}{c} \right) \]

  • For optimal \(c \approx \log n\), this becomes substantially faster than the naive method.

⚖️ Summary Comparison

Feature Naive Double-and-Add Pippenger with Window \(c\)
Time per scalar \(O(\log s)\) \(O\left(\frac{\log s}{c}\right)\) amortized
Total additions \(O(n \log s)\) \(O\left( \left( \frac{n}{c} + 2^c \right) \frac{\log s}{c} \right)\)
Parallelizable No Yes (bucket accumulation is parallelizable)
Memory usage Low Higher (buckets)
Use case Small \(n\), low concurrency Large \(n\), batched MSM

✅ Why Pippenger is Better:

  • Less redundant work: Pippenger combines contributions across scalars at the same window bits, avoiding separate EC operations for each scalar.
  • Better asymptotics: Especially as \(n\) grows large.
  • Highly parallelizable: Modern CPUs/GPUs benefit massively.

📌 Example:

Let’s say:

  • \(n = 2^{16} = 65536\)
  • \(\log s = 256\)
  • \(c = 16\)

Then:

  • Naive: \(O(65536 \cdot 256) \approx 16.7 \times 10^6\) EC operations
  • Pippenger:
    • Buckets: \(2^{16} = 65536\)
    • Windows: \(\frac{256}{16} = 16\)
    • Total EC operations: roughly \(\left(\frac{65536}{16} + 65536\right) \cdot 16 \approx 6.9 \times 10^5\) EC operations — much smaller
