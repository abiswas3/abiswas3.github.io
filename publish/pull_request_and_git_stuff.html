Setting Up Fast Mail

  • NS is like the internet’s phone book: it translates your domain name (randomwalks.xyz) into IP addresses or other service addresses.

  • The key DNS records involved here are:

    • A record: points a domain to an IP address.

    • CNAME record: points a domain to another domain name.

    • NS records: specify which DNS servers are authoritative for your domain.

What does dig do?

dig (Domain Information Groper) is a command-line tool used to query DNS (Domain Name System) servers. It helps you look up various DNS records for a domain, such as:

  • A records — IP addresses for a domain (e.g., example.com → 93.184.216.34)
  • MX records — Mail servers responsible for handling emails for the domain
  • TXT records — Text info like SPF, DKIM, or other verification strings
  • CNAME records — Alias names pointing to another domain

Basically, dig asks DNS servers: “Hey, what info do you have for this domain or subdomain?” and shows you their response.

1. Set up domain hosting in Fastmail

  • Log into your Fastmail account.

  • Go to Settings → Domains (or similar).

  • Add your domain, e.g. randomwalks.xyz.

  • Fastmail will give you DNS records to add to your domain registrar (Porkbun). Typically these are:

    • MX records (for mail delivery)

    • TXT records (for SPF, DKIM, DMARC — email authentication)

    • Possibly CNAME or additional TXT records

2. Add DNS records at Porkbun

  • Log into your Porkbun account.

  • Go to Domain Management → randomwalks.xyz → DNS Records.

  • Add the MX, TXT, and CNAME records Fastmail gave you exactly as instructed.

  • Repeat for polynomials.xyz if you want to use it too.

git rebase --onto upstream/feat/twist-shout-integration 773f3b9

What this means:

  • --onto upstream/feat/twist-shout-integration This tells Git: “Put the commits onto this branch upstream/feat/twist-shout-integration.”
    This is the new base where you want your commits to be reapplied.

  • 773f3b9 This is the upstream argument, specifying the commit before the commits you want to rebase. In other words, Git will find all commits reachable from your current HEAD that come after commit 773f3b9, and then replay those commits onto upstream/feat/twist-shout-integration. Basically, in my branch starting from 773f3b9 (but not including it), detach all the commits and stick it on top of upstream/feat/twist-shout-integration and the head of feat/msm_speedups points the head of this

  • No branch specified at the end When you omit the branch argument, Git defaults to rebasing your current checked-out branch (whatever HEAD points to).

Branch Forcing You’re an expert on relative refs now, so let’s actually use them for something.

One of the most common ways I use relative refs is to move branches around. You can directly reassign a branch to a commit with the -f option. So something like: git branch -f main HEAD~3 moves (by force) the main branch to three parents behind HEAD.

Note: In a real git environment git branch -f command is not allowed for your current branch.

Git Reset

git reset reverses changes by moving a branch reference backwards in time to an older commit. In this sense you can think of it as “rewriting history;” git reset will move a branch backwards as if the commit had never been made in the first place.

Command What it does Safe on shared branches?
git revert Makes a new commit that undoes another one ✅ Yes
git reset Moves HEAD and changes history ⚠️ No (on shared branches)

  • git revert B creates a new commit (D) that undoes the changes introduced by B.
  • But! C still exists. So D actually reverts B on top of C — meaning: > 🔁 D = (C + reverse of B)

In summary

  • A is the state before B.
  • B introduces some changes.
  • C builds on top of B.
  • D is like saying “Okay, I want to undo B’s effects — but keeping C.”

Moving Work Around

So far we’ve covered the basics of git – committing, branching, and moving around in the source tree. Just these concepts are enough to leverage 90% of the power of git repositories and cover the main needs of developers.

That remaining 10%, however, can be quite useful during complex workflows (or when you’ve gotten yourself into a bind). The next concept we’re going to cover is “moving work around” – in other words, it’s a way for developers to say “I want this work here and that work there” in precise, eloquent, flexible ways.

This may seem like a lot, but it’s a simple concept.

Git Cherry-pick

The first command in this series is called git cherry-pick. It takes on the following form:

  • git cherry-pick <Commit1> <Commit2> <...>

It’s a very straightforward way of saying that you would like to copy a series of commits below your current location (HEAD). I personally love cherry-pick because there is very little magic involved and it’s easy to understand.

Git Interactive Rebase

Git cherry-pick is great when you know which commits you want (and you know their corresponding hashes) – it’s hard to beat the simplicity it provides.

But what about the situation where you don’t know what commits you want? Thankfully git has you covered there as well! We can use interactive rebasing for this – it’s the best way to review a series of commits you’re about to rebase.

All interactive rebase means is that Git is using the rebase command with the -i option.

If you include this option, git will open up a UI to show you which commits are about to be copied below the target of the rebase. It also shows their commit hashes and messages, which is great for getting a bearing on what’s what.

For “real” git, the UI window means opening up a file in a text editor like vim. For our purposes, I’ve built a small dialog window that behaves the same way.

When the interactive rebase dialog opens, you have the ability to do two things in our educational application: - You can reorder commits simply by changing their order in the UI (via dragging and dropping with the mouse). - You can choose to keep all commits or drop specific ones. When the dialog opens, each commit is set to be included by the pick button next to it being active. To drop a commit, toggle off its pick button.

It is worth mentioning that in the real git interactive rebase you can do many more things like squashing (combining) commits, amending commit messages, and even editing the commits themselves. For our purposes though we will focus on these two operations above.

Merging

git checkout A
  git merge B

  • Git tries to merge the changes from branch B into branch A.

  • If B is a direct descendant of A (meaning A’s HEAD is an ancestor of B’s HEAD), Git will do a fast-forward merge:

    • The HEAD of A will simply move forward to point to the same commit as B’s HEAD.
    • No new commit is created.

  • If B is not a direct descendant of A (there are divergent changes), Git creates a new merge commit:

    • The HEAD of A moves to a new commit whose parents are the previous A HEAD and B HEAD.
    • So the HEAD of A does not become the HEAD of B; it becomes a new merge commit.

git commit --amend

Summary

Command Description
git commit Create a new commit with the currently staged changes
git commit --amend Replace the last commit with a new commit including staged changes and optionally update the commit message

Notes

  • Only modifies the most recent commit (HEAD).
  • Changes the commit hash (it’s a new commit).
  • Useful for fixing or adding forgotten changes before pushing.
  • If the original commit was pushed, you need to force push after amending:
git push --force

git remote set-url upstream https://github.com/a16z/arkworks-algebra

If no upstream remote exists, add it

git remote add upstream https://github.com/a16z/arkworks-algebra

Seeing Who Contributed Where

If you want to see your fork on github what the status is

git shortlog -sne remotes/origin/dev/twist-shout

If you want to know the history on the upstream then

git shortlog -sne remotes/upstream/dev/twist-shout

And locally

git shortlog -sne dev/twist-shout
  • -s — “summary”: show only the number of commits per author (no commit messages).
  • -n — “numeric”: sort the output by number of commits, descending (most commits first).
  • -e — “email”: show author email addresses along with their names.
