What is the cost of overflow?

We are 11% faster. Note is very difficult to pinpoint if it’s due to fewer multiplications or how we wrote the code without using contiguous memory, but with 100,000 random inputs and 100 chained multiplications, we appear to be faster.

Although fast, this code will not pass – we need the answer to be reduced \(\mod p\).

With Two Conditional Subtractions

Now, for starters, ignoring the fact that h-mul actually needs two subtractions , we stick one conditional subtraction for both c-mul and h-mul. We should still have a speed advantage, right? After all, we had one algorithm faster than the second algorithm, and we added the same line of code to both.

    Finished `release` profile [optimized] target(s) in 0.80s
     Running `target/release/examples/ark-multiplication`
100000 Trials of 100 chained multiplications
Benchmarking done
Average Advantage: -5.434536875745394
C-mult    1791.88866
H-mult    1889.26951
dtype: float64

We are 5% slower. And with a little thought and listening Matt Godbolt, this observation is not surprising. The answer is branch prediction. The CPU gets it wrong with h-mul. Why? It’s because the line of code we added was

if a >= p{
    a = p - a
}

Based on the theory we’ve built so far, we know that c-mul overflows much less frequently than h-mul – If things were distributed uniformly1, it would imply that 95% of the time, the if statement evaluates to false for c-mul. So the CPU can pretty much always get rid of this line of code, and be wrong only 5% of the time. Instead, in h-mul we overflow about 65% on average. This makes branch prediction close to impossible.

Aside: Same Code Two Conclusions

As a brief distraction, in this section, we give an example of how finicky performance benchmarking can be.

One of the reasons we embarked on this journey was that preliminary experimentation showed 10-15% speedups. Without the subtractions, we manifested these speedups. However, even if we add the requisite subtractions to the Ingo skyscraper code and run cargo bench, we see something different from what’s discussed above.

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

     Running benches/my_benchmark.rs (target/release/deps/my_benchmark-8968c072d5fb1ae5)
Arkworks CIOS (10 chained c-mul, looped)
                        time:   [1.9783 µs 1.9847 µs 1.9929 µs]
Found 5 outliers among 100 measurements (5.00%)
  3 (3.00%) high mild
  2 (2.00%) high severe

h-mul (10 chained h-mul, looped)
                        time:   [1.8386 µs 1.8411 µs 1.8442 µs]

h-mul is FASTER even with the subtractions!!!!

How can this be? It’s the same code that behaves completely differently in two different repositories. In terms of the body of the algorithms – the two tests run the EXACT same code, yet we draw totally different conclusions. A lazy conclusion might be variance – but that’s strictly not true. In this case, h-mul is actually marginally faster.

The real answer can be found by thinking about the CPU’s branch prediction algorithm and then staring at the inputs to the algorithm.

All of Montgomery’s theory relies on the fact that the initial inputs \(a\) and \(b\) are at most \(p-1\). In the Ingo skyscraper code, the inputs are random \(\mod r^4\). This strips away the overflow prevention property of CIOS. So now the CPU cannot predict the branch, and we are closer to the no-subtraction situation. Of course, we still lose a bit as h-mul needs 2 subtractions and 2 checks as opposed to 1.

In conclusion, something as innocuous as random inputs can lead to completely different conclusions about the real-world performance of code.

So Where Do We Go Now?

At this point, where do we stand? We have a family of algorithms for Montgomery multiplication. If we are not bothered about reducing  mod  p – s-mul` should be the fastest algorithm, owing to its maximal parallelism (allows maximal for out-of-order execution on the CPU). But we need the final answer to be less than p for the rest of the Jolt setup to work. Does this mean that for Jolt, CIOS remains the best algorithm to use?

We try a middle ground. We use the theory we built up to come up with an alternate strategy: – We save 2 multiplications (instead of 3) and play two rounds of CIOS. By our analysis and the actual value of \(p\) in bn-254, we will need at most one subtraction now as opposed to the two from h-mul.

Furthermore, we hope the number of overflows will reduce (it will never be as small as CIOS), therefore, we save on branching. Unfortunately, we do not have a prior implementation of this algorithm that we can fork – so we must write one from scratch. Our implementation can be found here

Without subtractions, we see lose some of the benefits of h-mul (as expected), but the percentage of times we overflow is much smaller.

It’s exactly what we expect. When we force the inputs \(a\) and \(b\) to small values (note small in Montgomery form so \(a = a'r \mod p\) and \(b=b'r \mod p\), \(a'\) and \(b'\) may or may not be small.), We kill overflows, and we get the extreme speedups we were after.

But when we run with random numbers again, we’re back to matching the performance of CIOS. The real bottleneck here is not the number of multiplications, but the number of branches the CPU has to do. The gains from multiplication only kick in if the CIOS algorithm and new algorithm overflows are both small.
