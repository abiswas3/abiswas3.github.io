From Toy Example to Real Jolt: The Bridge

Quick Overview

Pedagogical model: - Simplified witness vector z with ~20 elements per cycle - Register numbers (rs1, rs2, rd) and values in the witness

Real Jolt: - Twist maintains large sparse matrices for memory state - Shout handles bytecode fetching and lookup tables - R1CS witness contains only the interface values (~20 per cycle)

This document shows how execution trace data flows into each module.

The Execution Trace

Real Jolt traces look like this:

ADDI(RISCVCycle {
    instruction: ADDI {
        address: 2147483652,              // PC
        operands: FormatI { rd: 2, rs1: 2, imm: 1248 }
    },
    register_state: RegisterStateFormatI {
        rd: (2147487744, 2147488992),     // (old_value, new_value)
        rs1: 2147487744                   // read value
    },
    ram_access: ()                        // No RAM access this cycle
})

LD(RISCVCycle {
    instruction: LD {
        address: 2147483904,
        operands: FormatLoad { rd: 58, rs1: 20, imm: 152 }
    },
    register_state: RegisterStateFormatLoad {
        rd: (0, 16162939636638469629),    // Loading into rd
        rs1: 2147488248                   // Base address register
    },
    ram_access: RAMRead {
        address: 2147488400,              // RAM address
        value: 16162939636638469629       // Value read
    }
})

Each cycle contains: - Instruction details (opcode, operands) - Register state (before/after values) - RAM access (if any)

From Trace → Twist Inputs

Twist proves: Memory operations are temporally consistent.

Twist’s Internal Witness (Not visible to R1CS)

For T cycles and K memory locations (registers + RAM):

Read access matrix:

ra[j, k] = {
    1  if cycle j reads from memory location k
    0  otherwise
}

Write access matrix:

wa[j, k] = {
    1  if cycle j writes to memory location k
    0  otherwise
}

Memory values:

val[j, k] = value at memory location k at time j

Write values:

wv[j, k] = value being written (if wa[j,k]=1, else 0)

Increments (how memory changes):

inc[j, k] = wa[j,k] · (wv[j,k] - val[j,k])

So memory evolves: val[j+1, k] = val[j, k] + inc[j, k]

Example: ADDI Instruction

From trace:

ADDI {
    operands: { rd: 2, rs1: 2, imm: 1248 },
    register_state: {
        rd: (2147487744, 2147488992),
        rs1: 2147487744
    }
}

Twist’s matrices for cycle j:

// Reading from register 2
ra[j, reg_2] = 1
ra[j, k] = 0 for all other k

// Writing to register 2
wa[j, reg_2] = 1
wa[j, k] = 0 for all other k

// Memory state
val[j, reg_2] = 2147487744        // Before write

// Write value
wv[j, reg_2] = 2147488992         // After write

// Increment
inc[j, reg_2] = 1 · (2147488992 - 2147487744) = 1248

Example: LD Instruction (RAM Read)

From trace:

LD {
    operands: { rd: 58, rs1: 20, imm: 152 },
    register_state: {
        rd: (0, 16162939636638469629),
        rs1: 2147488248
    },
    ram_access: RAMRead {
        address: 2147488400,
        value: 16162939636638469629
    }
}

Twist’s matrices for cycle j:

// Reading from register 20 (base address)
ra[j, reg_20] = 1

// Reading from RAM location 2147488400
ra[j, RAM_2147488400] = 1

// Writing to register 58
wa[j, reg_58] = 1

// All other locations: ra[j,k] = 0, wa[j,k] = 0

// Memory values
val[j, reg_20] = 2147488248
val[j, RAM_2147488400] = 16162939636638469629
val[j, reg_58] = 0                        // Before write

// Write value
wv[j, reg_58] = 16162939636638469629     // After write

// Increment
inc[j, reg_58] = 16162939636638469629 - 0 = 16162939636638469629

What Twist Exports to R1CS Witness

Twist performs sum-checks internally, then provides to R1CS:

// For ADDI example
rs1_read_value: 2147487744      // Read from register 2
rd_write_value: 2147488992      // Write to register 2

// For LD example  
rs1_read_value: 2147488248      // Read from register 20 (base addr)
ram_addr: 2147488400            // Computed: rs1 + imm = 2147488248 + 152
ram_read_value: 16162939636638469629
rd_write_value: 16162939636638469629

Key point: R1CS sees only the VALUES, not the sparse matrices ra, wa, val, wv, inc!

From Trace → Shout Inputs

Shout proves: Correct bytecode fetching and instruction execution.

Shout’s Two Jobs

Job 1: Bytecode Fetching (Read-Only Memory)

Bytecode table is fixed (read-only):

Bytecode[PC] = encoded instruction

For each cycle at PC, Shout proves: “The instruction at this PC is correct.”

Job 2: Instruction Lookup (Read-Only Tables)

For operations like ADD, lookup tables store precomputed results:

ADD_Table[x, y] = x + y (for all 64-bit x, y)

Table size: 2^64 × 2^64 = 2^128 entries (huge but structured!)

Example: ADDI Instruction

From trace:

ADDI {
    address: 2147483652,           // PC
    operands: { rd: 2, rs1: 2, imm: 1248 }
}

Shout’s Job 1 (Bytecode):

Query: Bytecode[2147483652]
Result: Encoded ADDI instruction with rd=2, rs1=2, imm=1248

Shout proves: "PC 2147483652 contains ADDI rd=2, rs1=2, imm=1248"

Shout’s Job 2 (Lookup):

Operands from R1CS:
  - left_input: 2147487744  (from rs1)
  - right_input: 1248       (immediate value)
  
Query: ADD_Table[2147487744, 1248]
Result: 2147488992

Shout proves: "ADD(2147487744, 1248) = 2147488992"

Example: LD Instruction

From trace:

LD {
    address: 2147483904,
    operands: { rd: 58, rs1: 20, imm: 152 }
}

Shout’s Job 1 (Bytecode):

Query: Bytecode[2147483904]  
Result: Encoded LD instruction with rd=58, rs1=20, imm=152

Shout proves: "PC 2147483904 contains LD rd=58, rs1=20, imm=152"

Shout’s Job 2 (Lookup):

LD doesn't need computational lookup!
Address calculation done by R1CS (not lookup table).

Lookup outputs are not used for memory operations.

What Shout Exports to R1CS Witness

// For ADDI example
pc: 2147483652                  // From bytecode fetch
left_input: 2147487744          // Decoded operand
right_input: 1248               // Decoded immediate  
lookup_output: 2147488992       // From lookup table

// For LD example
pc: 2147483904
// No lookup needed - address calc done by R1CS

The Mathematical Formulation

Twist’s Multilinear Extensions (MLEs)

All matrices are expressed as MLEs over log(T) + log(K) variables:

Ra(r_t, r_a) = Σ_{j,k} eq(j, r_t) · eq(k, r_a) · ra[j,k]

Val(r_t, r_a) = Σ_{j,k} eq(j, r_t) · eq(k, r_a) · val[j,k]

Wa(r_t, r_a) = Σ_{j,k} eq(j, r_t) · eq(k, r_a) · wa[j,k]

Wv(r_t, r_a) = Σ_{j,k} eq(j, r_t) · eq(k, r_a) · wv[j,k]

Inc(r_t, r_a) = Σ_{j,k} eq(j, r_t) · eq(k, r_a) · [wa[j,k] · (wv[j,k] - val[j,k])]

Where: - r_t ∈ F^(log T) = random challenge for time/cycle dimension - r_a ∈ F^(log K) = random challenge for address/memory dimension - eq(j, r_t) = Lagrange basis polynomial for cycle j - eq(k, r_a) = Lagrange basis polynomial for address k

Twist’s Sum-Check Claim

Twist proves via sum-check:

Σ_{j,k} eq(r', j) · ra[j,k] · [val[j,k] + γ · (val[j,k] + inc[j,k])]
    = rv_claim + γ · wv_claim

Where: - r' = random challenge from R1CS/verifier - γ = random challenge batching reads and writes - rv_claim = claimed read values from R1CS witness - wv_claim = claimed write values from R1CS witness

Intuition: - First term: Σ ra[j,k] · val[j,k] = sum of read values - Second term: Σ ra[j,k] · (val[j,k] + inc[j,k]) = sum of values after writes - Batched with γ to check both simultaneously

Shout’s Sum-Check (Simplified)

For bytecode:

rv_bytecode[j] = Σ_k ra_bytecode[j,k] · Bytecode[k]

For lookups:

lookup_output[j] = LookupTable[left_input[j], right_input[j]]

Proven via read-only memory checking (no writes, so simpler than Twist).

Connecting to R1CS Witness

The Full Data Flow

│ Execution Trace (per cycle)            │
│                                         │
│ • Instruction: opcode, rs1, rs2, rd    │
│ • Register state: (old, new) values   │
│ • RAM access: address, value           │
└─────────────────────────────────────────┘
            │                  │
            ↓                  ↓
┌──────────────────┐  ┌──────────────────┐
│ Twist            │  │ Shout            │
│                  │  │                  │
│ Matrices:        │  │ Tables:          │
│ • ra[j,k]        │  │ • Bytecode[PC]   │
│ • wa[j,k]        │  │ • LookupTable[]  │
│ • val[j,k]       │  │                  │
│ • wv[j,k]        │  │ Sum-checks over  │
│ • inc[j,k]       │  │ read-only memory │
│                  │  │                  │
│ Sum-check over   │  │                  │
│ T×K hypercube    │  │                  │
└──────────────────┘  └──────────────────┘
            │                  │
            ↓                  ↓
┌─────────────────────────────────────────┐
│ R1CS Witness (interface - ~20 values)  │
│                                         │
│ From Twist:                             │
│ • rs1_read_value, rs2_read_value       │
│ • rd_write_value                        │
│ • ram_addr, ram_read_value             │
│ • ram_write_value                       │
│                                         │
│ From Shout:                             │
│ • pc, decoded operands (rs1,rs2,rd,imm)│
│ • lookup_output                         │
│                                         │
│ R1CS enforces (~60 constraints):       │
│ • Arithmetic: ram_addr = rs1_val + imm │
│ • Routing: lookup_out = rd_write_value │
│ • PC updates                            │
└─────────────────────────────────────────┘

Concrete Example: ADDI

Trace:

ADDI { rd: 2, rs1: 2, imm: 1248 }
register_state: { rd: (2147487744, 2147488992), rs1: 2147487744 }

Twist (internal):

ra[j, reg_2] = 1      (reading register 2)
wa[j, reg_2] = 1      (writing register 2)
val[j, reg_2] = 2147487744
wv[j, reg_2] = 2147488992
inc[j, reg_2] = 1248

Shout (internal):

Bytecode[PC] = ADDI instruction
LookupTable[2147487744, 1248] = 2147488992

R1CS Witness (visible):

pc: 2147483652
rs1_read_value: 2147487744      // From Twist
imm: 1248                       // From Shout (decoded)
lookup_output: 2147488992       // From Shout (lookup)
rd_write_value: 2147488992      // To Twist
flags[WriteLookupToRd]: true    // Control flag

R1CS Constraints:

1. lookup_output = rs1_read_value + imm
   2147488992 = 2147487744 + 1248 ✓

2. rd_write_value = lookup_output  
   2147488992 = 2147488992 ✓

Key Differences: Pedagogical vs Real

Aspect Pedagogical Model Real Jolt
Witness size z vector: 16 elements Twist: T×K matrices, Shout: bytecode + lookup tables
Memory tracking Values shown directly Sparse matrices ra, wa, val, wv
Register addresses In z vector (z[2]=rs1, z[3]=rs2) Decoded by Shout, not in R1CS
Multiple reads z[6]=rs1_val, z[7]=rs2_val Separate sum-checks or batched
Write tracking z[8]=rd_write inc[j,k] = wa[j,k]·(wv[j,k]-val[j,k])
Lookup tables Conceptual “query” Actual 2^128-sized structured table
Math formulation Explicit z[i] values MLEs in Lagrange basis

Summary

The execution trace is processed in parallel:

  1. Twist extracts memory operations:
    • Builds sparse access matrices ra[j,k], wa[j,k]
    • Tracks memory evolution via val[j,k] and inc[j,k]
    • Performs sum-checks over T×K hypercube
    • Exports read/write VALUES to R1CS witness
  2. Shout extracts instruction semantics:
    • Fetches from bytecode table (read-only)
    • Queries lookup tables (read-only, 2^128 size)
    • Performs sum-checks for both
    • Exports decoded operands and lookup results to R1CS witness
  3. R1CS enforces consistency:
    • Receives ~20 interface values per cycle
    • Enforces arithmetic (address calculations)
    • Routes values between Twist and Shout
    • ~60 constraints per cycle

The pedagogical z vector is the R1CS witness interface! Twist and Shout’s internal witnesses (matrices and tables) are never directly visible to R1CS - only their boundary values cross module boundaries.
