These notes are loosely based on the Foundations post by the author of rayon, Niko Matsakis.

One of the standout features of rayon is how easy it makes writing parallel code. You essentially, write sequential code, change a few words here and there, and voila, you get speedup. Thus, a good place, to start is start by describing the sequential code, which we aim to parallelise.

Sequential Iterators

The main trait of study here is the Iterator trait, see Line 139 of rustlib/src/rust/library/core/src/iter/traits/iterator.rs for a full definition. We will only be interested in the next method, and the base type T of the thing we are iterating on.

Consider the following code snippet, which we intentionally write in a more verbose manner, than seen in the wild.

pub fn sequential_dot_product(vec1: &Vec<u64>, vec2: &Vec<u64>) -> u128 {
    let slice_iter1: std::slice::Iter<'_, u64> = vec1.iter();
    let slice_iter2: std::slice::Iter<'_, u64> = vec2.iter();
    let zip_iter = slice_iter1.zip(slice_iter2);
    let map_iter = zip_iter.map(|(i, j)| (*i as u128) * (*j as u128));
    map_iter.sum::<u128>()
}

Slice Iterators

let slice_iter1: std::slice::Iter<'_, u64> = vec1.iter();
let slice_iter2: std::slice::Iter<'_, u64> = vec2.iter();

As vec1 (and vec2 as well) is a slice, it has a method called iter() which returns slice/Iter struct. The actual description can be found in Line 69 of rustlib/src/rust/library/core/src/slice/iter.rs, which we briefly preview below.

pub struct Iter<'a, T: 'a> {
    /// The pointer to the next element to return, or the past-the-end location
    /// if the iterator is empty.
    ///
    /// This address will be used for all ZST elements, never changed.
    ptr: NonNull<T>, // <-- This acts like the self.slice object from Nikos blog
    /// For non-ZSTs, the non-null pointer to the past-the-end element.
    ///
    /// For ZSTs, this is `ptr::without_provenance_mut(len)`.
    end_or_len: *const T,
    _marker: PhantomData<&'a T>,
}

See Line 154 of rustlib/src/rust/library/core/src/slice/iter/macros.rs for how theIterator trait, and especially the next function is implemented for this struct to satisfy the Iterator trait bounds. The code looks complicated owing to all the low level optimisations, but at it’s core, it just returns the thing at the address to which ptr points to, and increments the ptr by the size of T (with the error checking). More importantly, at this moment of time next is never called, all we have done is return a slice/Iter struct.

Something to note, is that in Niko’s original blog, this struct looks simpler. I’m not sure if that was a simplification was for pedagogical reasons, or the actual Rust library was different back then. One could quite easily find out, but I did not bother. The difference I speak of is that in the original blog, instead of ptr field, the struct stores a field called field: &'a [T] More specifically,

pub struct SliceIter<'iter, T: 'iter> {
    slice: &'iter [T],
}

A word about the life time notation, more like a note to myself:

  • The 'iter in angle brackets declares a named lifetime parameter for the struct. You can read 'iter as: the Iter struct holds a reference valid for the lifetime 'iter.

  • slice: &'iter [T]: This means the field slice is a **reference to a slice of T.

  • T: 'iter — is a lifetime bound on the type T. It means: Every value of type T stored in this slice must live at least as long as 'iter.

In summary – we have a struct that stores a reference to something that lives as long as iter. The thing it references is stored in the field called slice, which is a reference to an unsized list of type T things. These things inside the list which are of T must also live at most for iter lifetime.

Zip Iterators

The next object of study is

let zip_iter = slice_iter1.zip(slice_iter2);

the zip function shown below, returns a Zip struct that also implements the Iterator trait, where self.

fn zip<U>(self, other: U) -> Zip<Self, U::IntoIter>
    where
    Self: Sized,
    U: IntoIterator,

where Zip is as defined


pub struct Zip<A, B> {
    a: A,
    b: B,
    // index, len and a_len are only used by the specialized version of zip
    index: usize,
    len: usize,
}

and it implements the trait Iterator

impl<A: Iterator, B: Iterator> Zip<A, B> {
    #[inline]
    fn next(&mut self) -> Option<Self::Item> {
        ZipImpl::next(self)
    }
}

for which next is implemented quite simply

#[inline]
default fn next(&mut self) -> Option<(A::Item, B::Item)> {
    let x = self.a.next()?;
    let y = self.b.next()?;
    Some((x, y))
}

Quite straight forward so far. NOTE: We still have NOT called next. We are still just returning structs that implement the Iterator trait.

The Map type winds up with three generic types: - B the return type of the closure F - I the iterator - F the type of the closure that we will apply at each step (in Rust, closures each have their own unique type);

Here the closure type is FnMut it indicates a function that will be called repeatedly in a sequential fashion (notice I said sequential; we’ll have to adjust this later when we want to generalize to parallel execution). It’s called FnMut because it takes an &mut self reference to its environment, and thus it can mutate data from the enclosing scope. A Mini De-tour

A closure’s environment is the data it captures from the surrounding scope.

let mut count = 0;        // ← This is the environment
let x = 5;                // ← Also part of the environment

let mut my_closure = |item| {
   count += 1;           // Mutating captured variable
   item + x + count      // Reading captured variable
};

// The closure "closes over" count and x from the enclosing scope

What is self in a Closure?

When Rust implements a closure, it generates a unique anonymous struct that holds the captured variables:

// Your code:
let mut count = 0;
let mut add_and_count = |x| {
    count += 1;
    x + count
};

// Compiler generates something like:
struct __Closure_add_and_count<'a> {
    count: &'a mut i32,  // The environment!
}

impl<'a> __Closure_add_and_count<'a> {
    fn call_mut(&mut self, x: i32) -> i32 {
        //      ^^^^^^^^^^
        //      This is the "self" - the struct holding the environment!
        *self.count += 1;
        x + *self.count
    }
}

The Big Picture

The Reduce/Sum Method

All we have done so far, is returned a bunch of types that implement iterator traits, which is a very glorified version of saying, we have returned structs whose field is a pointer, and they all have a next function which moves the pointer forward, while returning the thing it was pointing to. Now we will call sum - which looks like this

fn sum<I>(iter: I) -> Option<T>
    where
        I: Iterator<Item = Option<U>>,
    {
        iter::try_process(iter, |i| i.sum())
    }

where i will be a GenericShunt which is also an iterator, which will eventually call the sum() method, which will next

/// Takes an iterator and generates `Self` from the elements by "summing up"
/// the items.
#[stable(feature = "iter_arith_traits", since = "1.12.0")]
fn sum<I: Iterator<Item = A>>(iter: I) -> Self;

What GenericShunt Does: GenericShunt is an iterator wrapper that: through a relatively complex chain of calls, Unwraps Result<T, E> → yields just T, If an error occurs, it stops on the first error. Stores the error in its residual field.

pub(crate) fn try_process<I, T, R, F, U>(iter: I, mut f: F) -> ChangeOutputType<I::Item, U>
where
    I: Iterator<Item: Try<Output = T, Residual = R>>,
    for<'a> F: FnMut(GenericShunt<'a, I, R>) -> U,
    R: Residual<U>,
{
    let mut residual = None;
    let shunt = GenericShunt { iter, residual: &mut residual };
    let value = f(shunt);
    match residual {
        Some(r) => FromResidual::from_residual(r),
        None => Try::from_output(value),
    }
}

Long story short, when everything is good, it iterates through the iterators, gets the pair of numbers, multiplies them as the closure of the Map iterator specified, and then, sums the answers for each pair.

IntoIter Traits

In my example, I created iterators explicitly by calling iter:

vec1.iter()
    .zip(vec2.iter())
    .map(|(i, j)| i * j)
    .sum()

But you may have noticed that in idiomatic Rust code, this explicit call to iter can sometimes be elided. For example, if I were actually writing that iterator chain, I wouldn’t call iter() from within the call to zip:

vec1.iter() 
    .zip(vec2) 
    .map(|(i, j)| i * j) 
    .sum()

Similarly, if you are writing a simple for loop that just goes over a container or slice, you can often elide the call to iter:

for item in vec2{
    process(item)
}

So what is going on here? The answer is that we have another trait called IntoIterator, which defines what types can be converted into iterators:

trait IntoIterator {
    // the type of item our iterator will produce
    type Item;

    // the iterator type we will become
    type IntoIter: Iterator<Item = Self::Item>;

    // convert this value into an iterator
    fn into_iter(self) -> Self::IntoIter;
}

Naturally, anything which is itself an iterator implements IntoIterator automatically – it just gets “converted” into itself, since it is already an iterator. Container1 types also implement IntoIterator. The usual convention is that the container type itself implements IntoIterator so as to give ownership of its contents: e.g., converting Vec<T> into an iterator takes ownership of the vector and gives back an iterator yielding ownership of its T elements. However, converting a reference to a vector (e.g., &Vec) gives back references to the elements &T. In more detail, there are 3 Ways to Iterate

  1. By Value - Consuming the Containeri
let vec = vec![1, 2, 3];

for x in vec {           // Converts Vec<T> → Iterator
    println!("{}", x);   // x is i32 (owned value)
}

// vec is now GONE - it was consumed, as the iterator is gone out of scope.
// println!("{:?}", vec); // ❌ Error: value moved
  1. By Immutable Reference - Borrowing
let vec = vec![1, 2, 3];

for x in &vec {          // Converts &Vec<T> → Iterator
    println!("{}", x);   // x is &i32 (reference)
}

// vec still exists!
println!("{:?}", vec);   // ✅ Works: [1, 2, 3]

What happened:

  • &vec (a reference to the Vec) was converted into an iterator
  • The iterator borrows the Vec
  • Each iteration yields references &i32
  • After the loop, the Vec still exists unchanged
  1. By Mutable Reference - Mutating
tlet mut vec = vec![1, 2, 3];

for x in &mut vec {      // Converts &mut Vec<T> → Iterator
    *x += 10;            // x is &mut i32 (mutable reference)
}

println!("{:?}", vec);   // [11, 12, 13]

Going back to our original example, of why we don’t need to do vec2.iter() The zip helper method uses IntoIterator to convert its argument into an iterator:

fn zip<U>(self, other: U) -> Zip<Self, U::IntoIter>
    where
    Self: Sized,
    U: IntoIterator,

So it just does the conversion anyway.

  1. A container type is a type that holds/stores other values - essentially collections and data structures.↩︎
