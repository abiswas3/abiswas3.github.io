Implementation Projects

As much as I’d like it to be the case, computer science is not just about analysing things on paper. We have to write code to make things work. Below are some projects where you use your algorithms knowledge to implement things.

Remark

You may use AI tools to help write code, but you should understand the code you submit. In your presentation, explain how the algorithms work, why they are correct, and the main design choices in your implementation. Show how you checked correctness and use your experiments to explain when each method works well.

The required parts below are enough for a complete project; the extensions are optional.

Project 1: Google Maps lite: route planning on real road data

Build a system that finds the fastest route between two points in a city using OpenStreetMap data.

  • Build the graph. Use a small city extract from Geofabrik to build a weighted, directed graph. Handle one-way streets and estimate travel times from road types and speed limits. You may use existing libraries to load and prepare the map data.
  • Route search. Implement Dijkstra’s algorithm and A*. For A*, use straight-line distance divided by an upper bound on road speed as a travel-time heuristic. Explain why your heuristic never overestimates the remaining travel time.
  • Simple interface. Provide a command-line tool or notebook that takes a start and an end point and returns the route and its estimated travel time.

Benchmarking and analysis

Compare the two algorithms on the same set of at least 100 reachable start and end pairs:

  • Check that both algorithms return the same travel times. Also test small graphs where you can work out the answer by hand, including one-way roads and unreachable destinations.
  • Measure query time and the number of nodes explored. Include both short and long routes.
  • Explain when A* helps and when it does not. Include the queries or a script so that your comparison can be repeated.

Optional extensions

  • Try bidirectional Dijkstra, ALT (A* with landmarks), or Contraction Hierarchies. Compare the extra work and storage with the improvement in query time.
  • Build a web interface that displays the route and the nodes explored by each algorithm.

Resources

Use the survey by Bast et al. for background, then read the papers for the algorithms you implement. The references for bidirectional Dijkstra, ALT, Contraction Hierarchies and web maps are for the optional extensions.

Project 2: File compression: build your own compressor

Build a lossless compression tool that compresses files and restores them exactly. Compare Huffman coding with one more compression approach.

  • Baseline compression. Implement Huffman coding on byte frequencies. Write an actual compressed binary file, including the information needed to decode it. Your tool must handle arbitrary files, not just text.
  • Choose one more approach. Either implement LZ77 using a sliding window and combine it with Huffman coding, or implement the Burrows–Wheeler transform followed by move-to-front encoding and Huffman coding. Implement the corresponding decoder too. A straightforward implementation with a fixed window or block size is enough.
  • Simple interface. Provide a command-line tool that lets the user choose a method, compress a file and decompress it again.

Use a documented file format of your own. A compressed file must contain everything your decoder needs; decompression must work in a fresh process without access to the original file. Implement the compression algorithms yourself; existing compression libraries may be used for benchmarking.

Benchmarking and analysis

Show, with evidence, when each approach works well and what it costs:

  • Check that decompression reproduces every input byte for byte. Include empty files, repeated single bytes, arbitrary binary data and random data.
  • Benchmark on a small selection of files from the Canterbury Corpus and include an already compressed file.
  • Measure compressed size and compression and decompression time for both methods and gzip. Count the complete output file, including headers and code tables. Provide a script that repeats the comparison.
  • Explain the differences between the methods, including cases where compression makes a file larger. Which method would you use for which kinds of files, and why?

Optional extensions

  • Implement the other compression approach and add it to your comparison.
  • Try hashing to speed up LZ77 match finding, or investigate different window or block sizes.
  • Build a web interface or a visualisation of the compression steps.

Resources

Start with Huffman coding, then read the paper for your chosen compression approach. The DEFLATE specification is a useful implementation reference if you choose LZ77 with Huffman coding; compatibility with its file format is not required. The Silesia Corpus and bzip2 are there if you want to extend your benchmarks.

  • Huffman coding: Huffman, D. A. (1952). A method for the construction of minimum-redundancy codes. Proceedings of the IRE, 40(9), 1098–1101. pdf
  • LZ77: Ziv, J., & Lempel, A. (1977). A universal algorithm for sequential data compression. IEEE Transactions on Information Theory, 23(3), 337–343. pdf
  • Burrows–Wheeler transform: Burrows, M., & Wheeler, D. J. (1994). A block-sorting lossless data compression algorithm (SRC Research Report No. 124). Digital Equipment Corporation. pdf
  • LZ77 with Huffman coding: Deutsch, P. (1996). DEFLATE compressed data format specification version 1.3 (RFC 1951). specification
  • Benchmark files: Canterbury Corpus and Silesia Corpus.
  • Reference compressors: gzip and bzip2.
