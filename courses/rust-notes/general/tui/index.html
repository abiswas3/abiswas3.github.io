TUI Tutorial

AB 2026-02-07
rustratatui

A hands-on guide using a real codebase — a research paper manager TUI that searches a SQLite database, displays results in a scrollable list, lets you edit metadata inline, and shells out to vim. Every concept is illustrated with actual code from this project.

Prerequisites: Basic Rust knowledge. No TUI experience needed.

Table of Contents

1. The Mental Model

A TUI app is a loop that redraws the entire screen every frame. There is no persistent widget tree, no DOM, no diffing algorithm you manage. Every iteration:

loop {
    draw_everything_from_scratch();
    read_one_input_event();
    update_state();
}

This is called immediate mode rendering. It's the same pattern used in game engines (Dear ImGui, etc.). It sounds wasteful, but ratatui uses double-buffering internally — it diffs the previous frame against the new one and only sends the changed cells to the terminal. You don't need to think about this.

The architectural pattern this maps to is The Elm Architecture (TEA), also known as Model-View-Update:

              ┌──────────────┐
    Event ──► │    UPDATE     │ ──► State changes
              │  (app.rs)     │
              └──────────────┘
                     │
                     ▼
              ┌──────────────┐
    State ──► │    RENDER     │ ──► Terminal output
              │  (ui.rs)      │
              └──────────────┘
  • State lives in a single App struct. All mutable data in one place.
  • Update is a function that takes an event + current state and produces new state.
  • Render is a function that takes current state and draws the UI. It never mutates state.

This separation is not enforced by ratatui — you could put everything in one file. But keeping update logic (app.rs) separate from rendering (ui.rs) makes the codebase dramatically easier to reason about.

2. Project Setup

Dependencies

# Cargo.toml
[dependencies]
ratatui  = "0.29"     # The TUI framework — widgets, layout, styling
crossterm = "0.28"     # Terminal backend — raw mode, events, colors

Why two crates? Ratatui handles what to draw (widgets, layout). Crossterm handles how to talk to the terminal (escape codes, key events, raw mode). Ratatui supports multiple backends (crossterm, termion, termwiz), but crossterm is the most popular and works on all platforms.

You'll also want whatever crates your app needs. Ours uses:

rusqlite = { version = "0.32", features = ["bundled"] }  # SQLite
toml     = "0.8"                                          # Config files
open     = "5"                                            # Open files in system viewer

File Structure

A clean TUI project splits into four files:

src/
  main.rs      # Terminal setup, main loop, teardown
  app.rs       # App struct, Mode enum, all event handling
  ui.rs        # All rendering (draw functions)
  db.rs        # Data access (database, files, etc.)

This isn't required — you can put everything in main.rs for a toy project. But the moment your app has more than one "screen" or mode, the separation pays for itself immediately.

3. Taking Over the Terminal

A normal terminal does things you don't want in a TUI: it buffers input line-by-line, echoes typed characters, and lets Ctrl+C kill your process. You need to disable all of this and take full control.

// main.rs
use crossterm::{
    execute,
    terminal::{EnterAlternateScreen, LeaveAlternateScreen,
               disable_raw_mode, enable_raw_mode},
};
use ratatui::{Terminal, backend::CrosstermBackend};
use std::io;

fn main() -> io::Result<()> {
    // STEP 1: Enable raw mode.
    //   - Keys are delivered immediately (no waiting for Enter)
    //   - No echo (typed characters don't appear)
    //   - Ctrl+C doesn't kill the process — you get a KeyEvent instead
    enable_raw_mode()?;

    // STEP 2: Enter the alternate screen.
    //   Terminals have two buffers: the "normal" screen (your shell history)
    //   and the "alternate" screen (a blank canvas). TUI apps draw on the
    //   alternate screen. When you leave, the terminal restores the normal
    //   screen — your shell history is untouched.
    let mut stdout = io::stdout();
    execute!(stdout, EnterAlternateScreen)?;

    // STEP 3: Create the ratatui Terminal.
    //   CrosstermBackend adapts crossterm's API to ratatui's Backend trait.
    //   Terminal wraps this and provides draw(), which double-buffers for you.
    let backend = CrosstermBackend::new(stdout);
    let mut terminal = Terminal::new(backend)?;

    // ... run your app ...

    // STEP 4: ALWAYS restore the terminal.
    //   If you skip this (crash, panic, early return), the user's terminal
    //   is stuck in raw mode with no echo. They'll have to type `reset` blind.
    disable_raw_mode()?;
    execute!(terminal.backend_mut(), LeaveAlternateScreen)?;
    terminal.show_cursor()?;

    Ok(())
}

The cardinal rule: always restore the terminal. Structure your code so that teardown runs even if the main loop panics. The pattern from our codebase:

fn main() -> io::Result<()> {
    // setup...
    let result = run_loop(&mut terminal, &mut app);  // might panic/error

    // teardown ALWAYS runs:
    disable_raw_mode()?;
    execute!(terminal.backend_mut(), LeaveAlternateScreen)?;
    terminal.show_cursor()?;

    result  // propagate the error after cleanup
}

4. The Main Loop

The loop is three lines of logic:

fn run_loop(
    terminal: &mut Terminal<CrosstermBackend<io::Stdout>>,
    app: &mut App,
) -> io::Result<()> {
    loop {
        // 1. RENDER: Draw the UI based on current state.
        terminal.draw(|frame| ui::draw(frame, app))?;

        // 2. UPDATE: Read events, modify state.
        app.handle_events()?;

        // 3. CHECK: Should we quit?
        if app.should_quit {
            return Ok(());
        }
    }
}

terminal.draw() takes a closure that receives a Frame. The Frame is your canvas — you render widgets onto it. Ratatui double-buffers: it compares this frame to the previous one and only sends the diff to the terminal. This is why redrawing everything every frame is efficient.

app.handle_events() polls for keyboard/mouse events and updates the App struct. We'll cover this in detail in section 7.

The loop runs at whatever rate events arrive, with a 50ms poll timeout as a floor (~20fps). This is fast enough to feel responsive without burning CPU.

5. Application State — The App Struct

All mutable state lives in one struct. This is the "Model" in Model-View-Update. Here's ours (simplified for teaching):

// app.rs
pub struct App {
    // What mode are we in?
    pub mode: Mode,

    // The data being displayed
    pub papers: Vec<Paper>,
    pub selected: usize,

    // Search state
    pub search_query: String,
    pub search_filter: SearchFilter,

    // Edit state
    pub edit_field: EditField,
    pub editing_active: bool,
    pub edit_paper: Option<Paper>,

    // UI state
    pub status_message: Option<String>,
    pub should_quit: bool,

    // External resources
    pub conn: Connection,         // SQLite
    pub editor_request: Option<PathBuf>,  // request to open vim
}

Why one big struct? Because the render function needs to see everything to draw the UI, and the update function needs to modify anything in response to input. Splitting state across multiple structs creates borrow checker pain with no architectural benefit.

Initialization loads data from the database:

impl App {
    pub fn new(conn: Connection) -> Self {
        let papers = db::list_all(&conn);
        Self {
            mode: Mode::Browse,
            papers,
            selected: 0,
            search_query: String::new(),
            // ... all other fields initialized to defaults ...
            conn,
        }
    }
}

6. Modes — How TUIs Handle Context

A TUI can't show modal dialogs the way a GUI can. Instead, it uses modes — different interpretations of the same keys depending on context. Think vim: pressing j in Normal mode moves down, but in Insert mode it types the letter "j".

#[derive(Debug, Clone, Copy, PartialEq)]
pub enum Mode {
    Browse,  // Navigating the list. j/k move, Enter opens, q quits.
    Search,  // Typing into the search box. Characters are input.
    Edit,    // Editing metadata. Navigate fields, type values.
}

Modes affect two things:

  1. Key handling — the same key does different things in different modes.
  2. Rendering — the UI changes visually to show which mode you're in (highlighted borders, different status bar text, etc.).

The mode is just a field on the App struct. Switching modes is a simple assignment:

// Enter search mode when the user presses '/'
KeyCode::Char('/') => {
    self.mode = Mode::Search;
}

// Leave search mode when they press Escape
KeyCode::Esc => {
    self.mode = Mode::Browse;
}

Design tip: Keep mode transitions explicit and obvious. The user should always know what mode they're in. Use visual cues: change border colors, show mode-specific keybindings in the status bar, show/hide cursor indicators.

7. Handling Keyboard Input

Event handling is the UPDATE step. We poll for events, dispatch by mode, and modify state:

pub fn handle_events(&mut self) -> std::io::Result<()> {
    // Poll with 50ms timeout. If no event arrives, we return and re-render.
    // This timeout controls your "frame rate" when idle.
    if event::poll(Duration::from_millis(50))? {
        if let Event::Key(key) = event::read()? {
            match self.mode {
                Mode::Browse => self.handle_browse_key(key),
                Mode::Search => self.handle_search_key(key),
                Mode::Edit   => self.handle_edit_key(key),
            }
        }
    }
    Ok(())
}

Each mode gets its own handler. Here's Browse mode:

fn handle_browse_key(&mut self, key: KeyEvent) {
    match key.code {
        KeyCode::Char('q') => self.should_quit = true,

        // Navigation: support both arrow keys and vim keys
        KeyCode::Down | KeyCode::Char('j') => {
            if !self.papers.is_empty() {
                self.selected = (self.selected + 1).min(self.papers.len() - 1);
            }
        }
        KeyCode::Up | KeyCode::Char('k') => {
            self.selected = self.selected.saturating_sub(1);
        }

        // Mode transitions
        KeyCode::Char('/') => self.mode = Mode::Search,
        KeyCode::Char('e') => self.enter_edit_mode(),
        KeyCode::Enter     => self.open_selected_pdf(),

        _ => {}
    }
}

Navigation pattern: Use min() and saturating_sub() to clamp the selection index. Never let it go negative or past the end. This is a bug in almost every TUI tutorial — they forget to bounds-check.

Search mode treats most keys as text input:

fn handle_search_key(&mut self, key: KeyEvent) {
    match key.code {
        KeyCode::Esc       => self.mode = Mode::Browse,
        KeyCode::Enter     => self.mode = Mode::Browse,
        KeyCode::Backspace => { self.search_query.pop(); self.refresh_search(); }
        KeyCode::Char(c)   => { self.search_query.push(c); self.refresh_search(); }
        KeyCode::Tab       => { self.search_filter = self.search_filter.next();
                                self.refresh_search(); }
        _ => {}
    }
}

Notice refresh_search() is called on every keystroke — this is what makes search results update live.

Modifier keys (Ctrl, Alt, Shift) are checked via the modifiers field on KeyEvent:

KeyCode::Char('s') if key.modifiers.contains(KeyModifiers::CONTROL) => {
    self.save_edit();
}

8. The Layout System — Dividing the Screen

Ratatui's Layout splits a Rect (a rectangle: x, y, width, height) into smaller Rects. You compose layouts vertically and horizontally to create your screen structure.

//   ┌──────────────────────────────┐
//   │ Search bar          (3 rows) │  ← Constraint::Length(3)
//   ├──────────────────────────────┤
//   │                              │
//   │ Paper list        (flexible) │  ← Constraint::Fill(1)
//   │                              │
//   ├──────────────────────────────┤
//   │ Detail panel        (8 rows) │  ← Constraint::Length(8)
//   ├──────────────────────────────┤
//   │ Status bar          (1 row)  │  ← Constraint::Length(1)
//   └──────────────────────────────┘

let layout = Layout::vertical([
    Constraint::Length(3),   // Search bar: exactly 3 rows
    Constraint::Fill(1),     // Paper list: all remaining space
    Constraint::Length(8),   // Detail panel: exactly 8 rows
    Constraint::Length(1),   // Status bar: exactly 1 row
])
.split(frame.area());

// layout[0], layout[1], layout[2], layout[3] are now Rects
// you can pass to widget rendering functions.
draw_search_bar(frame, app, layout[0]);
draw_paper_list(frame, app, layout[1]);
draw_detail_panel(frame, app, layout[2]);
draw_status_bar(frame, app, layout[3]);

Constraint Types

ConstraintBehavior
Length(n)Exactly n rows/columns. Use for fixed-size elements.
Min(n)At least n, but can grow.
Max(n)At most n.
Percentage(n)n% of the parent.
Fill(weight)Takes remaining space. Multiple Fills share proportionally by weight.

Nesting layouts: You can split horizontally inside a vertical section. For example, to put a search box and a filter selector side by side:

let row = Layout::horizontal([
    Constraint::Fill(1),      // Search box takes most space
    Constraint::Length(10),   // Filter selector is fixed width
])
.split(layout[0]);

Key insight: Layouts are computed, not stored. You call split() every frame, which returns fresh Rects. This means your layout automatically adapts when the terminal is resized — no resize event handling needed.

9. Rendering Widgets

Ratatui provides built-in widgets. The most important ones:

WidgetUse case
BlockBorders, titles, background colors. Wraps other widgets.
ParagraphText display. Supports styled spans, wrapping, alignment.
ListScrollable list with selection.
TableTabular data with columns.
GaugeProgress bars.
TabsTab selector.

Rendering a widget is a single call:

frame.render_widget(some_widget, some_rect);

The widget draws itself into the given Rect. That's it.

Block — The Universal Container

Almost every element starts with a Block. It draws borders, a title, background color, and padding. Then you render your content into the Block's inner area:

let block = Block::default()
    .borders(Borders::ALL)
    .border_style(Style::default().fg(BORDER))
    .title(" Details ")
    .style(Style::default().bg(BG_SECONDARY))
    .padding(Padding::horizontal(1));

// block.inner(area) returns the Rect INSIDE the borders and padding.
let inner = block.inner(area);
frame.render_widget(block, area);

// Now render content into the inner area.
frame.render_widget(Paragraph::new("Hello"), inner);

Important: Render the Block first, then your content. The Block fills its area with the background color. If you render content first, the Block overwrites it.

Paragraph — Styled Text

Paragraph renders text with rich styling. The key concept is Spans and Lines:

  • A Span is a styled piece of text: Span::styled("hello", Style::default().fg(Color::Red))
  • A Line is a sequence of Spans (one row of text)
  • A Paragraph is a sequence of Lines
let line = Line::from(vec![
    Span::styled("Title: ", Style::default().fg(TEXT_SECONDARY).bold()),
    Span::styled("Attention Is All You Need", Style::default().fg(TEXT_PRIMARY)),
]);
frame.render_widget(Paragraph::new(line), area);

This is how you get mixed styling on a single line — each Span has its own colors and modifiers.

10. Styling — Colors, Borders, and Themes

Every visual element in ratatui is controlled by Style. A Style has:

  • fg — foreground (text) color
  • bg — background color
  • Modifiers: BOLD, ITALIC, UNDERLINED, DIM, etc.
Style::default()
    .fg(Color::Rgb(124, 111, 239))  // Purple accent
    .bg(Color::Rgb(30, 30, 46))     // Dark background
    .add_modifier(Modifier::BOLD)

Defining a Color Palette

Define your colors as constants so they're consistent everywhere:

// Catppuccin-inspired dark theme
const BG_PRIMARY: Color   = Color::Rgb(30, 30, 46);      // #1e1e2e
const BG_SECONDARY: Color = Color::Rgb(37, 37, 54);      // #252536
const BG_INPUT: Color     = Color::Rgb(42, 42, 60);      // #2a2a3c
const BORDER: Color       = Color::Rgb(58, 58, 78);      // #3a3a4e
const ACCENT: Color       = Color::Rgb(124, 111, 239);   // #7c6fef
const TEXT_PRIMARY: Color  = Color::Rgb(224, 222, 244);   // #e0def4
const TEXT_SECONDARY: Color= Color::Rgb(144, 140, 170);  // #908caa
const TEXT_MUTED: Color    = Color::Rgb(110, 106, 134);   // #6e6a86

Use 3-4 surface colors for depth (primary, secondary, input/elevated). Use one accent color for focus indicators and interactive elements. Use 2-3 text colors for hierarchy (primary, secondary, muted).

Filling the Background

By default, the terminal's own background shows through. To get a consistent dark background:

// First thing in draw(): fill the entire screen.
frame.render_widget(
    Block::default().style(Style::default().bg(BG_PRIMARY)),
    frame.area(),
);

Dynamic Borders

Change border colors based on mode to give visual feedback about focus:

let border_color = if app.mode == Mode::Search { ACCENT } else { BORDER };
let block = Block::default()
    .borders(Borders::ALL)
    .border_style(Style::default().fg(border_color));

11. Building a Search Bar

A search bar is a Block with styled text inside. The trick is showing a cursor when the user is typing.

fn draw_search_bar(frame: &mut Frame, app: &App, area: Rect) {
    let block = Block::default()
        .borders(Borders::ALL)
        .border_style(Style::default().fg(
            if app.mode == Mode::Search { ACCENT } else { BORDER }
        ))
        .style(Style::default().bg(BG_SECONDARY))
        .padding(Padding::horizontal(1));

    let inner = block.inner(area);
    frame.render_widget(block, area);

    // Show a cursor character when in search mode.
    let cursor = if app.mode == Mode::Search { "▎" } else { "" };

    let line = Line::from(vec![
        Span::styled("Search: ", Style::default().fg(TEXT_SECONDARY)),
        Span::styled(
            format!("{}{}", app.search_query, cursor),
            Style::default().fg(TEXT_PRIMARY),
        ),
        Span::raw("  "),
        Span::styled(
            format!("[{}]", app.search_filter.label()),
            Style::default().fg(ACCENT).add_modifier(Modifier::BOLD),
        ),
    ]);

    frame.render_widget(Paragraph::new(line), inner);
}

The cursor trick: We don't use the terminal's real cursor (it's hidden). Instead, we append a unicode block character ▎ after the query text. Simple, effective, and avoids the complexity of managing cursor position.

The filter badge [All] / [Title] / [Authors] tells the user which column they're searching. It cycles with Tab. The accent color makes it stand out.

12. Building a Scrollable List with Selection

The List widget is one of ratatui's most powerful. It handles scrolling, selection, and multi-line items.

fn draw_paper_list(frame: &mut Frame, app: &App, area: Rect) {
    // Build ListItems from data. Each item can have multiple Lines.
    let items: Vec<ListItem> = app.papers.iter().enumerate().map(|(i, paper)| {
        let is_selected = i == app.selected;

        let title_style = if paper.pending {
            Style::default().fg(WARNING).add_modifier(Modifier::ITALIC)
        } else if is_selected {
            Style::default().fg(TEXT_PRIMARY).add_modifier(Modifier::BOLD)
        } else {
            Style::default().fg(TEXT_PRIMARY)
        };

        ListItem::new(vec![
            Line::from(Span::styled(&paper.title, title_style)),
            Line::from(Span::styled(
                format!("  {}", paper.authors),
                Style::default().fg(TEXT_MUTED),
            )),
        ])
    }).collect();

    let list = List::new(items)
        .block(
            Block::default()
                .borders(Borders::ALL)
                .title(format!(" Papers ({}) ", app.papers.len()))
        )
        .highlight_style(Style::default().bg(BG_INPUT).add_modifier(Modifier::BOLD))
        .highlight_symbol("▸ ");

    // ListState tracks selection and scroll offset.
    let mut state = ListState::default().with_selected(Some(app.selected));

    // render_stateful_widget — the List reads/writes the ListState.
    frame.render_stateful_widget(list, area, &mut state);
}

Key concepts:

ListItem can contain multiple Lines. We use two lines per paper: title on top, authors below. This gives a clean, airy layout.

highlight_style is applied to the entire selected item. We use a slightly lighter background (BG_INPUT) so the selection is visible but not jarring.

highlight_symbol draws a character to the left of the selected item. ▸ (a small right-pointing triangle) is a clean choice.

ListState is the "stateful" part. It tracks which item is selected and the scroll offset (which item is at the top of the visible area). We create it fresh each frame with with_selected(Some(app.selected)) — the List widget does the math to keep the selection visible.

render_stateful_widget vs render_widget: Use the stateful version when the widget needs to read or write auxiliary state (like scroll position).

13. Building a Detail Panel

A read-only panel showing the full metadata of the selected item. It's just a Block with Paragraphs inside:

fn draw_detail_panel(frame: &mut Frame, app: &App, area: Rect) {
    let block = Block::default()
        .borders(Borders::ALL)
        .title(" Details ")
        .style(Style::default().bg(BG_SECONDARY))
        .padding(Padding::horizontal(1));

    let inner = block.inner(area);
    frame.render_widget(block, area);

    if let Some(paper) = app.papers.get(app.selected) {
        let lines = vec![
            detail_line("Title", &paper.title),
            detail_line("Authors", &paper.authors),
            detail_line("DOI", &paper.doi),
            detail_line("Tags", if paper.tags.is_empty() { "—" } else { &paper.tags }),
            detail_line("Notes", if paper.notes.is_empty() { "—" } else { &paper.notes }),
        ];
        frame.render_widget(Paragraph::new(lines), inner);
    }
}

/// Helper: "Label: Value" with styled label.
fn detail_line<'a>(label: &'a str, value: &'a str) -> Line<'a> {
    Line::from(vec![
        Span::styled(format!("{label}: "), Style::default().fg(TEXT_SECONDARY).bold()),
        Span::styled(
            if value.is_empty() { "—" } else { value },
            Style::default().fg(TEXT_PRIMARY),
        ),
    ])
}

The em-dash trick: When a field is empty, show — instead of nothing. This is clearer than a blank space and looks polished.

The pattern: Block → inner → content. You'll use this dozens of times. Get comfortable with it.

14. Building an Inline Editor

This is the most complex widget. The editor replaces the detail panel when the user presses e. It shows each field with a selection indicator and cursor.

State Design

Edit mode uses three pieces of state:

pub edit_field: EditField,          // Which field is focused (Title, Authors, ...)
pub editing_active: bool,           // Are we typing into the field? Or just navigating?
pub edit_paper: Option<Paper>,      // A CLONE of the paper being edited (staged changes)

The clone is essential. We don't edit the original paper in the list — we edit a copy. If the user presses Escape, we discard the copy and nothing changes. If they press Ctrl+S, we commit the copy to disk and DB.

Two Sub-States

Edit mode has two layers, like vim's Normal/Insert within its own Command mode:

Edit mode, editing_active = false:
  ↑↓ or j/k → move between fields
  Enter     → start typing into the focused field
  Ctrl+S    → save all changes
  Esc       → cancel, discard changes

Edit mode, editing_active = true:
  Characters → typed into the field
  Backspace  → delete last character
  Enter      → stop typing this field
  Esc        → stop typing this field
  Ctrl+S     → save (even while typing)
fn handle_edit_key(&mut self, key: KeyEvent) {
    if self.editing_active {
        self.handle_edit_typing(key);
    } else {
        self.handle_edit_navigate(key);
    }
}

The Borrow Checker Challenge

You'll hit this when trying to mutate a field of self.edit_paper while reading self.edit_field:

// THIS WON'T COMPILE — borrows self mutably and immutably at the same time:
if let Some(ref mut paper) = self.edit_paper {
    let field = self.get_edit_field_mut(paper);  // borrows self AND paper
    field.push(c);
}

Solution: Extract the field accessor into a free function that takes the enum and the paper, avoiding any borrow of self:

// Free function — no &self involved
fn get_field_mut<'a>(field: EditField, paper: &'a mut Paper) -> &'a mut String {
    match field {
        EditField::Title   => &mut paper.title,
        EditField::Authors => &mut paper.authors,
        EditField::Doi     => &mut paper.doi,
        EditField::Tags    => &mut paper.tags,
        EditField::Notes   => &mut paper.notes,
    }
}

// Now this works:
if let Some(ref mut paper) = self.edit_paper {
    get_field_mut(self.edit_field, paper).push(c);
}

This is a common Rust pattern in TUI code: when methods need to access two fields of self simultaneously, extract one access into a standalone function.

Rendering the Editor

The visual trick: show a ▸ marker on the focused field, a cursor ▎ when typing, and different colors for focused vs unfocused:

let fields = EditField::all();
let lines: Vec<Line> = fields.iter().map(|&field| {
    let is_focused = field == app.edit_field;
    let is_typing = is_focused && app.editing_active;

    let marker = if is_focused { "▸ " } else { "  " };
    let cursor = if is_typing { "▎" } else { "" };

    let label_style = if is_focused {
        Style::default().fg(ACCENT).bold()
    } else {
        Style::default().fg(TEXT_SECONDARY)
    };

    let value_style = if is_typing {
        Style::default().fg(TEXT_PRIMARY).bg(BG_INPUT)  // highlight active field
    } else if is_focused {
        Style::default().fg(TEXT_PRIMARY)
    } else {
        Style::default().fg(TEXT_MUTED)
    };

    Line::from(vec![
        Span::styled(marker, Style::default().fg(ACCENT)),
        Span::styled(format!("{}: ", field.label()), label_style),
        Span::styled(format!("{value}{cursor}"), value_style),
    ])
}).collect();

The background color change on the actively-typed field (BG_INPUT) is subtle but important — it tells the user exactly which field their keystrokes are going to.

15. The Status Bar — Contextual Help

The status bar is the single most impactful UX element in a TUI. Without it, users have to memorize keybindings. With it, the app teaches itself.

Show different hints for each mode:

fn draw_status_bar(frame: &mut Frame, app: &App, area: Rect) {
    let hints = match app.mode {
        Mode::Browse => " /search  ↑↓navigate  enter:open  e:edit  o:vim  q:quit ",
        Mode::Search => " type to search  tab:filter  enter:accept  esc:cancel ",
        Mode::Edit   => " ↑↓fields  enter:edit  ctrl+s:save  esc:cancel ",
    };

    // Show status messages (like "Saved!") alongside the hints
    let line = if let Some(ref msg) = app.status_message {
        Line::from(vec![
            Span::styled(hints, Style::default().fg(TEXT_MUTED).bg(BG_SECONDARY)),
            Span::styled(
                format!(" {msg} "),
                Style::default().fg(SUCCESS).bg(BG_SECONDARY),
            ),
        ])
    } else {
        Line::from(Span::styled(hints, Style::default().fg(TEXT_MUTED).bg(BG_SECONDARY)))
    };

    frame.render_widget(
        Paragraph::new(line).style(Style::default().bg(BG_SECONDARY)),
        area,
    );
}

Design principles:

  • Keep hints terse — e:edit not Press 'e' to edit the selected paper
  • Use a muted color so hints don't compete with content
  • Show status messages in green (success) — they're ephemeral and important
  • Change hints when the mode changes — this is how the user learns the app

16. Shelling Out to External Programs

Sometimes your TUI needs to hand control to another program (vim, less, a web browser). This is the terminal handoff pattern:

fn spawn_editor(
    terminal: &mut Terminal<CrosstermBackend<io::Stdout>>,
    path: &Path,
) -> io::Result<()> {
    // 1. RELEASE: Give the terminal back to the child process.
    disable_raw_mode()?;
    execute!(terminal.backend_mut(), LeaveAlternateScreen)?;

    // 2. SPAWN: Run the external program. It gets full terminal control.
    let editor = std::env::var("EDITOR").unwrap_or_else(|_| "vim".to_string());
    let status = std::process::Command::new(&editor)
        .arg(path)
        .status();

    // Handle errors...
    match status {
        Ok(s) if s.success() => {}
        Ok(s) => eprintln!("Editor exited with: {s}"),
        Err(e) => {
            eprintln!("Failed to launch {editor}: {e}");
            std::thread::sleep(std::time::Duration::from_secs(1));
        }
    }

    // 3. RECLAIM: Take the terminal back.
    enable_raw_mode()?;
    execute!(terminal.backend_mut(), EnterAlternateScreen)?;

    // 4. REDRAW: The screen is blank after re-entering alternate screen.
    terminal.clear()?;

    Ok(())
}

Why this is tricky: Both your TUI and vim need exclusive terminal access. You can't run them simultaneously. The sequence must be: release → spawn → wait → reclaim.

The editor_request pattern: The App struct can't directly call spawn_editor because it doesn't own the Terminal. Instead, it sets a flag:

// In app.rs — just set the flag
KeyCode::Char('o') => {
    self.editor_request = Some(toml_path);
}
// In main.rs — check the flag and handle it
if let Some(path) = app.editor_request.take() {
    spawn_editor(terminal, &path)?;
    app.after_editor_return();  // re-index, refresh
}

This separation of "request" from "execution" is a clean way to handle actions that need resources the App doesn't own.

17. Connecting to a Database

Our TUI reads from SQLite using rusqlite. The connection is opened once and stored in the App struct:

// db.rs
pub fn open_db() -> Connection {
    let path = PathBuf::from("../research.db");
    if !path.exists() {
        eprintln!("research.db not found. Run the server first to create it.");
        std::process::exit(1);
    }
    Connection::open(path).expect("Failed to open research.db")
}

Search queries run on every keystroke (live filtering):

pub fn search(conn: &Connection, query: &str, filter: &SearchFilter) -> Vec<Paper> {
    if query.is_empty() {
        return list_all(conn);
    }

    let pattern = format!("%{query}%");
    let where_clause = match filter {
        SearchFilter::All    => "title LIKE ?1 OR authors LIKE ?1 OR tags LIKE ?1",
        SearchFilter::Title  => "title LIKE ?1",
        SearchFilter::Authors => "authors LIKE ?1",
        SearchFilter::Tags   => "tags LIKE ?1",
    };

    let sql = format!(
        "SELECT ... FROM papers WHERE {where_clause} ORDER BY added DESC"
    );

    let mut stmt = conn.prepare(&sql).unwrap();
    stmt.query_map(params![pattern], |row| {
        Ok(Paper { /* map all columns */ })
    })
    .unwrap()
    .filter_map(|r| r.ok())
    .collect()
}

Performance note: SQLite LIKE queries on a few hundred rows take microseconds. You won't notice any lag on keystrokes. For thousands of papers, add an FTS5 virtual table for full-text search.

18. Persisting Edits to Disk

When the user saves an edit (Ctrl+S), we write to two places:

  1. TOML file (ground truth) — using toml::Table for forward compatibility
  2. SQLite (derived index) — for fast searching
fn save_edit(&mut self) {
    let paper = match self.edit_paper.take() {
        Some(p) => p,
        None => return,
    };

    // Step 1: TOML first (ground truth)
    let toml_path = db::toml_path(&paper);
    if let Err(e) = editor::save_to_toml(&toml_path, &paper) {
        self.status_message = Some(format!("Failed to save TOML: {e}"));
        self.mode = Mode::Browse;
        return;
    }

    // Step 2: DB second (derived)
    db::update_paper(&self.conn, &paper);

    // Step 3: Refresh the display
    self.refresh_search();
    self.mode = Mode::Browse;
    self.status_message = Some("Saved!".into());
}

Forward-Compatible TOML Editing

The critical design decision: never deserialize TOML into a fixed struct when editing. Use toml::Table (a dynamic map) instead:

pub fn save_to_toml(path: &Path, paper: &Paper) -> Result<(), String> {
    // Read existing file as a dynamic Table.
    let mut table: toml::Table = if path.exists() {
        let content = std::fs::read_to_string(path)?;
        content.parse::<toml::Table>().unwrap_or_else(|_| toml::Table::new())
    } else {
        toml::Table::new()
    };

    // Update only the keys we know about. Everything else survives.
    table.insert("title".into(), toml::Value::String(paper.title.clone()));
    table.insert("authors".into(), toml::Value::Array(/* ... */));
    // ... more fields ...

    // We intentionally do NOT touch "added", "venue", "year", or any
    // future fields. They pass through the Table untouched.

    let toml_string = toml::to_string_pretty(&table)?;
    std::fs::write(path, toml_string)?;
    Ok(())
}

Why this matters: If someone adds venue = "STOC 2026" to a TOML file by hand (or a future version of the server adds it), and then the TUI edits the title, the venue field must survive. With a fixed struct, it would be silently dropped. With toml::Table, it passes through untouched.

19. Common Pitfalls

1. Forgetting to Restore the Terminal

If your app panics, the terminal stays in raw mode. The user sees no echo, no Ctrl+C.

Fix: Always structure cleanup outside the main loop:

fn main() {
    setup();
    let result = run();   // might panic
    teardown();           // always runs
    result.unwrap();
}

For extra safety, install a panic hook that calls teardown.

2. Selection Index Out of Bounds

When the list shrinks (search filters results), the selection index may point past the end.

Fix: Always clamp after changing the list:

fn refresh_search(&mut self) {
    self.papers = db::search(&self.conn, &self.search_query, &self.search_filter);
    if self.papers.is_empty() {
        self.selected = 0;
    } else {
        self.selected = self.selected.min(self.papers.len() - 1);
    }
}

3. Borrow Checker Fights with self

You want to read self.mode and write self.data in the same method. Rust says no.

Fix: Use free functions for accessors, or copy small values (self.mode is Copy) before the mutable borrow.

4. Blocking the Event Loop

Don't do I/O (network, disk) synchronously in the main loop. The UI freezes.

Fix: For short operations (SQLite queries: <1ms), it's fine. For slow operations, use a background thread and send results via a channel.

5. Rendering Outside the Area

If you render a widget into a Rect that's too small, ratatui silently clips. Nothing crashes, but content disappears.

Fix: Use Constraint::Min(n) to guarantee minimum sizes. Check area.height before rendering multi-line content.

6. Forgetting terminal.clear() After External Programs

After LeaveAlternateScreen + EnterAlternateScreen, the screen is blank. If you don't call terminal.clear(), ratatui's diff algorithm thinks nothing changed (previous buffer matches current buffer = both blank) and doesn't redraw.

Fix: Always terminal.clear() after reclaiming the terminal.

The data flow:

  • State lives in App (one struct, one owner)
  • ui.rs only reads state to render
  • app.rs only writes state in response to events
  • db.rs handles persistence (SQLite = fast queries, TOML = ground truth)
  • editor.rs handles the TOML write-back with forward compatibility
  • main.rs owns the Terminal and orchestrates the loop

This architecture scales. You can add new modes (Help screen, Tag browser, Note editor) by adding variants to the Mode enum, a new handler, and a new draw function. Nothing else changes.
